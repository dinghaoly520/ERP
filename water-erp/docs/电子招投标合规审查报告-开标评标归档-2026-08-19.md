# 电子招投标合规审查报告——开标·评标·归档全流程

> 审查日期：2026-08-19
> 审查方式：4 个独立审查 agent 并行深挖代码（开标段 / 评标段 / 归档留痕段 / 招标投标横切面），每条结论须附 `文件:行号` 证据；主会话对全部 P0 与关键 P1 逐条复核（见附录 A）。
> 审查对象：`water-erp/` monorepo 磁盘当前状态（含未提交改动）。
> 性质：独立合规审查——对照《电子招标投标办法》等法规逐条比对代码行为，与既往工程/架构审计互补。

## 一、总体结论

**合规骨架扎实、法定形式要件大面积缺席。** 全流程的程序性闸门（截标拒收、不足三家、解密窗口、评标准入、签字闭环、归档棘轮、哈希防篡改）实现严谨且有审计留痕意识，但**证据法层面的法定要件普遍缺位**：无投标人自有密钥/CA、平台持密钥且留存投标文件明文（开标前技术上可解密提取）、开标时间与截标时间系统性分离、法定时限（20 日/5 日/公示 3 日）零校验、开标记录不签名不公开、评标报告以手写扫描回传替代电子签名、操作日志 180 天物理销毁与 15 年保存要求冲突。此外存在两处「证据销毁通道」：删除公告可级联抹除进行中项目的开标/评分数据，归档文件删除端点无引用保护。

**发现统计：P0 × 5、P1 × 14、P2 × 26（共 45 项），符合项 22 条。**

若按「电子招标投标交易平台」定性（对接依法必须招标项目），P0/P1 合计 19 项为**不满足法定形式要件**的硬伤；当前系统更接近「内部采购管理 + 演示级电子化辅助」形态。上线真实依法必须招标项目前，P0 五项必须先行处置。

## 四、P0 发现（5 项）

### P0-1 平台持有全部密钥且留存投标文件明文——开标前技术上可解密提取任何投标文件
- **依据**：办法第26条（未加密应拒收）、第27条（截止前任何单位和个人不得解密、提取）。
- **现状**：①服务端代加密分支：明文上传→服务端读出明文加密写 `sealedPath`，**原明文对象不删除**（注释明言不覆盖）；②E2EE 分支虽浏览器端加密，但 **DEK 明文随提交 body 交给平台**，平台用单一 `KMS_SECRET` 封口——平台随时可解；③「一键重新封标」（解密失败补救主路径）**直接从留存明文恢复**。
- **证据**：`apps/api/src/supplier-portal/supplier-portal.service.ts:911-925`（明文加密后无 removeObject）；`apps/api/src/bid/bid.service.ts:2372-2375`（注释「从系统内存储的原始明文（FileAsset.key，供应商上传时存入、未删除）恢复」）、`:2452-2455`；`apps/supplier-portal/src/views/bid/BidSubmit.vue:272`（`clientDeks` 随 body）；`apps/api/src/common/crypto/envelope-crypto.ts:33-52`。
- **影响**：开标前投标保密完全依赖代码门控+运营纪律而非密码学隔离。MinIO/DB 凭据或 KMS_SECRET 任一泄露，全部未开标投标文件可被明文提取——直接违反第27条，也是全系统最重的合规风险。
- **建议**：投递后即删服务端明文（明文仅存在于供应商端）；DEK 改门限分片（主持人+监督人）或第三方托管；「未加密拒收」落地；reseal 补救改走供应商补传（SHA-256 闸门已具备）。

### P0-2 开标时间与投标截止时间系统性分离
- **依据**：《招标投标法》第34条：开标应在投标截止时间的**同一时间**公开进行。
- **现状**：`openTime`/`deadline` 独立建模、无相等约束；:3005 面板业务规则明示「投递截止=开标前12小时」；流标重启兜底「开标=截标+2小时」。
- **证据**：`apps/web/src/components/projects/bid-confirm-panel.tsx:400-402`（12小时业务规则）；`apps/api/src/bid/bid.service.ts:1115-1117`（`fallbackOpenTime = fallbackDeadline + 2h`）；`apps/api/src/bid/dto/create-bid-project.dto.ts:6-7`（两独立字段，无相等校验）。
- **影响**：截止后12小时（重启项目2小时）窗口内投标文件已定稿却未开标，属程序违法，可致中标结果被质疑无效。
- **建议**：若确有集团/水利行业制度依据，必须在模型与 UI 显式引用并留痕；否则服务层强制 `openTime === deadline`（或单字段建模）。

### P0-3 「发出招标文件至截标≥20日」「发售期≥5日」零校验，缺省仅7天
- **依据**：《招标投标法》第24条；《实施条例》第16条。
- **现状**：公告创建/发布、公告直建项目（N16）、BidProject 创建三条路径均无时限校验；公告直建缺省截标=开标+7天；前端向导提供「3天/5天」截标快捷项。
- **证据**：`apps/api/src/bid/bid.service.ts:616`（`?? new Date(openTime.getTime() + 7 * 86400000)`）；`apps/api/src/announcement/announcement.service.ts:516-524`（deadline 仅 `type:'string'`）；`apps/web/src/components/projects/announcement-publish-wizard.tsx:995-997`（`{[3,5].map(...)}`）。
- **影响**：公开招标项目可合法建出 3-7 天即截标，20 日/5 日法定时限完全落空。
- **建议**：服务端按采购方式强制校验（公开招标≥20日、发售期≥5日），直建默认值改为法定下限。

### P0-4 删除已发布招标公告会级联销毁进行中项目的开标/评标过程数据
- **依据**：办法第49条（不得伪造、篡改、损毁）、第40/42条（应存档）。
- **现状**：staff 角色删除 BID_NOTICE 时，若关联项目处于 SUBMIT/OPENING/EVALUATING，直接 deleteMany 开标会话/开标记录/评分记录/评标结果/废标记录，复位供应商与专家状态，并删除 MinIO 密封投标文件；stage 裸重置回 DOWNLOAD，完全绕过 `assertBidStageTransition`。
- **证据**：`apps/api/src/announcement/announcement.service.ts:410-449`（五类 deleteMany+复位）、`:486-492`（MinIO 密封文件删除）；`apps/api/src/announcement/announcement.controller.ts:242-247`（`@Delete(':id') @Roles('admin','leader','staff')`）。
- **影响**：评标中的项目（专家已打分、已确认报告）可被一名 staff 的公告删除操作不可逆摧毁；与单向棘轮冲突的旁路销毁通道，且无归档备份兜底。
- **建议**：项目进入 SUBMIT 后禁止删除来源公告（仅软删除/留档）；或要求 admin 双人审批并先导出归档包。

### P0-5 归档证据文件删除无引用保护，admin/bid_host 可永久损毁
- **依据**：办法第49条（不得损毁）。
- **现状**：`DELETE /api/upload/:key` 仅校验「admin/bid_host 或上传者本人」+ 只查 `SupplierBidSubmission` 四列引用；开标文件包/评标完整性包/回流包/签字包 PDF/专家签字扫描件**均不在保护内**；`handoverAssetId` 等为无外键裸 String；哈希链的 hashDigest 是元数据指纹，文件本体被删后验证依然「通过」——损毁不可发现。
- **证据**：`apps/api/src/upload/upload.service.ts:291-326`；`apps/api/prisma/schema.prisma:460`（无 @relation）、`:2696-2713`；`apps/api/src/upload/upload.controller.ts:77-82`。
- **影响**：任意 bid_host/admin 账号可直接删除已归档项目的核心证据文件，数据库无引用完整性兜底。
- **建议**：delete() 增加「被任何归档链/会话/签字包引用即拒绝」；ARCHIVED 阶段 bid 类 category 一律 409；FileAsset 增加软删除。

## 五、P1 发现（14 项）

### P1-1 无投标人自行解密入口，主持人代解密且无投标人授权记录
- **依据**：办法第30条（提示招标人和**投标人**按时在线解密，按招标文件规定方式）。
- **现状**：全仓仅 bid.controller 有解密端点（单条 admin/bid_host、批量含 leader/staff）；供应商门户无解密调用；唯一的「确认」是主持人勾选自查框，投标人侧无任何授权/委托记录。
- **证据**：`apps/api/src/bid/bid.controller.ts:351-355`、`:261-264`；`apps/bid-portal/src/components/decrypt-confirm-dialog.tsx:68-78`。
- **建议**：招标文件范本明确解密方式条款；保留平台代解密则投标人投递时勾选「同意平台开标环节代解密」落库为授权记录。

### P1-2 解密失败不区分「撤销/撤回」归因，通知不告知权利
- **依据**：办法第31条。
- **现状**：所有解密失败统一 `DANGER`+`EXCEPTION`，无归因字段（全仓 grep「视为撤销|视为撤回」零命中）；通知仅「请联系主持人」，未告知撤回与索赔权利。
- **证据**：`apps/api/src/bid/bid.service.ts:2089-2094`、`:2148-2171`。
- **建议**：DANGER 定性增加归因字段（投标人原因/平台原因/无法判定），按归因分流撤销/撤回，通知中告知权利。

### P1-3 开标记录无电子签名、不向社会公众公布
- **依据**：办法第32条。

## 八、存疑 / 需线下确认（8 项）

1. **招标文件范本是否规定「平台代解密」方式**（办法第30条允许「按招标文件规定方式」）——若未写明，P1-1 应升级 P0。
2. **「投递截止=开标前12小时」的制度依据**——仅见 UI 注释，未见集团/水利行业规则引用；若无依据，P0-2 为确定法定偏离。
3. **开标记录的线下签名与线下公布渠道**——线上无签名是确定的，但线下是否由主持人签纸质件、是否经人工发布公告，代码不可考。
4. **办法第34条「电子签名」的适用性**——取决于本平台是否被定性为电子招标投标交易平台；若定性成立，纸面扫描签字不满足，P1-11 应升级 P0。
5. **生产短信通道**——verification.service 非 debug 模式仅写 Redis，无短信服务商调用；可能依赖仓库外组件。
6. **公示期起算口径**——实现为发布时刻 +72h 自然日，未按「次日零时起算」惯例，是否满足「不少于3日」有解释空间。
7. **MinIO 生产侧 retention/SSE**——若生产在 compose 之外启用 KES/object-lock，无法从仓库证实。
8. **评标时限与招标文件载明的评标安排是否联动**——`evaluationDeadline`（缺省72h）为平台内部管控，未见与招标文件条款的对应。
