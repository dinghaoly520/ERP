## 2. 闸门判定（v2：复用既有 validator，round 感知，none 免校验）

- **轮次**：按**被完成 stage 行的 `round`** 解析 BidProject（`ProjectManagementStage.round`，`(pmiId, stageKey, round)` 唯一；再次采购每轮各有 03 行）。禁止裸 `round=1`。
- **已配置** =
  1. 按 (pmiId, round) 只读解析 BidProject；
  2. **评标办法 = `none`（不评分，直接采购/直接委托/续约）→ 免评分项校验，直接放行**。BidProject 缺失时回退用 `PMI.procurementMethod` 经 `getEvaluationDefault()` 推导（`bid/evaluation-method.config.ts`）——直接采购无 BidProject 也能完成 03，不死锁；
  3. 办法 ≠ none 时：BidProject **必须存在**（不存在 → 拦截，见下方指引），且评分标准完整 = **复用 `ScoreStandardValidator.assertScoreStandardComplete(bpId)`**（`bid/score-standard-validator.service.ts:45`：打分类 Σ=100±0.05、通过性类 QUALIFICATION/RESPONSIVE 豁免、每个打分类项 ≥1 得分点且满分>0、得分点 Σ≤项满分）——发布（`bid-score-standard.service.ts:380`）与启动评标 G9（`bid.service.ts:2099`）已用同一校验，此处为第三处同一口径，**不另写谓词副本**。
- **最高限价不必填**（`ceilingPrice` 可空，最低价法正常）；**`scoreStandardPublishedAt` 不作闸门**（发布后开标前仍可改、改即作废——现行语义不动）。
- **拦截指引（按采购方式分叉）**：BidProject 缺失时——公告型（竞价/询比/邀请/公开）→「请先在信息发布中心发布公告并**关联本项目**，再回到本卡片完成评分标准配置」；谈判采购（无公告阶段，BidProject 由供应商邀请创建）→「请先发送供应商邀请（或在信息发布中心发布公告并关联本项目），关联开评标项目后完成评分标准配置」。⚠️ 必须提示**关联项目**：不关联的直建发布会走 N16 新建独立 PMI+BidProject，本项目仍无关联、闸门照拦（双 PMI 陷阱）。
- 闸门仅 03 步生效；其他步骤不加；↺ 拨回 03 再完成时闸门再次生效（`updateStage` 补录语义「后续实质闸门照常校验」一致）。
- **与 DA/T 103 归档材料闸（`ARCHIVE_GATE_MISSING`，可 `waiveArchiveGate` 豁免）的关系**：两闸独立并存；评分闸**不可豁免**（评分标准即本阶段产物本身，不是归档材料）。提示顺序：评分闸先于归档材料闸抛出。

## 3. 前端改造（apps/web）

1. 从 `bid-confirm-panel.tsx`（`:870-920` SectionCard）抽出卡片为独立组件 `ScoreStandardCard`，含三子块（`EvaluationBasisFields`/`ScoreStandardEditor`/`PriceFormulaFields`）与现行锁定逻辑；**共享高危文件**：开工前 `git status` 确认并行会话无未提交改动。
2. 步骤条 03 行：删「采购文件修改」按钮块，原位改「**评分标准**」按钮（`onOpenScoreStandard(entry.round)`，任何阶段可点）——点击弹出评分标准面板（project-detail-panel 内 scorePanelRound overlay）；无 BidProject → 面板内卡片空态「尚未关联采购公告（或供应商邀请）」。
3. ⚡ **数据获取（只读，严禁懒创建）**：抽屉打开即拉新增的 `GET /api/project-management/{pmiId}/bid-project-refs`（**只读解析、不创建**；现有 `GET :id/bid-project` 是 ensure-or-create（`ensureBidProject` 无则建 SUBMIT 项目+自动评标办法），**不得**用于抽屉级轮询）；按 03 行 `entry.round` 取该轮 ref，存在时再拉 `GET /api/bid/projects/{id}`（详情）+ `GET /api/bid/projects/{id}/score-items`（徽标用）。`ScoreStandardEditor` 的 `bidProject` prop **必须显式传入**（其内部 `bidProject ?? ensureBidProject(...)` 兜底在 BP 缺失时不可触达——空态分支不渲染编辑器）。
4. 「标记本阶段完成」onClick（03 步）：徽标状态为未配置时前端先拦（`setErrorMessage` 指引文案，与 `INITIATION_NOT_APPROVED` 同款呈现，不用 toast）+ 不调推进端点；后端闸门兜底（见 §4）。
5. ⚡ 03 行状态徽标：「评分标准：未配置 / ✓已配置」——由抽屉级 score-items 数据粗算（打分类 Σ 与项数），**指示性**（权威判定在服务端）；BidProject 缺失或办法=none 时显示对应态（none=「不评分·免配置」）。
6. 开标确认面板移除该卡（三子块整卡），横幅/脚注文案微调；深链 `?projectId&panel=bid-confirm` 兼容（面板其余区块不动）。

## 4. 后端改造（apps/api，两处小改）

1. ⚡ **只读解析端点**：`GET /project-management/:id/bid-project-refs` → `[{ id, round, projectCode, stage }]`（`findMany` 按 `projectManagementItemId`，不创建）；类级 `@Roles('leader','admin','staff')` + `PmiOwnershipGuard` 自动继承（个人隔离）。
2. ⚡ **阶段闸门**：`updateStage`（`PATCH /project-management/:id/stages/:stageKey`，**不是** `POST :id/complete`——那是整项目归档）在 `status==='COMPLETED' && stageKey==='TENDER_DOCUMENT'` 时：按 §2 谓词校验，未过 → **400 BadRequestException `{ error, code: 'SCORE_STANDARD_REQUIRED' }`**（与同端点 `INITIATION_NOT_APPROVED`/`ARCHIVE_GATE_MISSING` 惯例一致；v1 的 409 不采用——409 是 bid 模块状态机冲突惯例，非本端点惯例）。位置：INITIATION 闸之后、归档材料闸之前。
3. ⚡ DI 接线：`BidModule.exports` 补 `ScoreStandardValidator`（`bid.module.ts:52`）；`ProjectManagementModule` imports 加 `BidModule`（已核 BidModule 不反向依赖 ProjectManagementModule，无循环）。
4. **无 schema 改动、无迁移**；score-items 家族端点与守卫一律不动。

## 6. 验收用例（v2：结合当前种子库实况）

当前库（09-22 清库后）：竞价采购 PMI 停 03 + BidProject ARCHIVED（已发布、合计 100、最低价法）；谈判采购 PMI 立项 + BidProject SUBMIT；直接采购 PMI 立项、无 BidProject。

1. 竞价项目（停 03，BP ARCHIVED）：03 行见卡片（锁定态、文案同现行）；徽标 ✓；「标记本阶段完成」→ 谓词通过（validator 口径放行）。
2. 直接采购项目（无 BP，办法推导 none）：03 完成不被评分闸拦截（归档材料闸照旧）。
3. 新项目（或拨回 03 的竞价项目删空评分项）无 BP 且办法≠none：卡片空态 + 指引文案（公告型 vs 谈判分叉）；点标记完成被拦（前端先拦 + 后端 400 兜底）。
4. 有 BP 但评分项 Σ≠100 / 打分项无得分点：拦截（validator 文案透传）。
5. ↺ 拨回 03 再完成：闸门再次生效；已发布项仍锁（现行锁不受影响）。
6. 面板内卡片消失、其余区块与深链 `?projectId&panel=bid-confirm` 正常；03 行无「采购文件修改」、「采购文件编写」仍在；StageFileList 逐行「编辑」仍可打开 docx 编辑器。
