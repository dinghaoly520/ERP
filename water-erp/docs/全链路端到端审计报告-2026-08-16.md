## 〇、总体结论

**后半段（开标→评标→签字→归档）工程质量很高**：实测开标会话幂等、解密真实 AES-GCM+SHA-256、E2EE 与服务端双路加密并存、评分独立性、结果生成五重闸门、签字包 SHA-256+失效联动、归档哈希链全部按设计工作；08-14 同房间审计 P0/P1 清单（实时协同、专家间可见性、签字包失效、匿名化）均已落地且实测生效。

**但整条链路在「真实创建」（非种子）条件下目前走不通**——本轮实测连续踩中 5 个 P0，全部集中在**上游**（邀请→投递准入→:3005 入口→专家签到），彼此叠加导致：不手工改库/发 API，谈判采购项目无法从公告走到归档。种子数据把这些问题全部掩盖了。

**实测打通过程中手工干预清单**（每一条对应一个 P0/P1）：
1. 手工 POST 公告 API 发布 BID_NOTICE 并挂 relatedProjectCode（因为谈判采购无公告阶段）；
2. SQL 修正 openTime/deadline（因为 ensureBidProject 兜底产生已过期 deadline）；
3. SQL 手工建 3 条 BidSupplier（因为回执「确认参加」500 后未 upsert 候选）；
4. 深链 `?panel=bid-confirm` 打开开标确认面板（因为流程卡入口被 isBidLocked 拦死）；

6. API 手工补得分点（种子模板得分点被 07-14 会话删空，发布评分标准被 SCORE_ITEM_HAS_NO_POINTS 拦截——此项属种子数据问题非代码缺陷）。

## 一、P0：阻断真实链路（5 项）

### P0-1 供应商回执「确认参加」必然报错且不进候选名单 ✅ 已修（fd4a95c9）
- **位置**：`apps/api/src/supplier/rsvp.service.ts:81-88`（respond 内 upsert）、`rsvp.controller.ts:33/51`（错误转译）。
- InvitationRsvp.projectId 写入的是 **PMI id**（`cmsujj1ld…`），respond() 拿它当 **BidProject id** 去 upsert BidSupplier → FK violation → 非 HTTP 异常 → 控制器统一误报为「回执链接无效或已被篡改」（RSVP_TOKEN_INVALID）。
- 回执状态更新与 BidSupplier upsert **不在一个事务**：状态已写成 ACCEPTED（看板显示"参加"），但供应商没进项目候选——半成功。
- 读侧已打补丁（bid-confirm-panel 双查两个 id 空间），**写侧未修**。实测供应商端点返回 400，`:3005` 回执列显示 1 参加 / 2 未回执。
- **修法**：respond() 内先 `ensureBidProject(pmiId)` 解析真实 BidProject id 再 upsert；整个 respond 包事务；控制器把 Prisma P2003 与「篡改」区分开。

### P0-2 谈判采购（及一切无 PUBLIC_ANNOUNCEMENT 阶段的采购方式）投递准入死锁 ✅ 已修（9a3ca400）
- **位置**：`project-management.service.ts:124-129`（REPROC_STAGE_SEGMENTS 谈判采购无公告阶段）；`supplier-portal.service.ts:680-686`（assertCanSubmitBid 无条件要求已发布 BID_NOTICE 且 relatedProjectCode=projectCode）。
- 谈判采购的阶段流是 采购文件→供应商邀请→专家抽取→开标评标（**无公告公示阶段**），邀请向导也不创建公告/BidDocument → G3 闸门 `BID_NOTICE_REQUIRED` 永不满足 → **供应商无法投递**。
- 旁证：:3005 信息发布中心「新建信息」只能建政策法规/平台通知（采购公示只能从公告阶段向导创建——谈判采购没有该阶段）。
- **修法**（择一）：谈判/邀请类项目以「邀请名单（RSVP ACCEPTED）」替代公告作为投递准入；或邀请向导「确认配置」时自动生成并发布程序性公告。

### P0-3 :3005「开标确认」面板流程卡入口被锁死（fcf8f6dc 回归）✅ 已修（341cae8a）
- **位置**：`apps/web/src/components/projects/project-detail-panel.tsx:429`（isBidLocked = BID_EVALUATION 阶段 IN_PROGRESS **或** COMPLETED）+ `:1118`（onStageAction 顶部无条件 return）。
- 阶段推进到「开标评标」后 PM 阶段状态=IN_PROGRESS（正常态）→ isBidLocked=true → 点流程卡「开标确认」直接 return（toast「开标已确认，前置步骤已锁定」）。**实测本项目与种子项目（TP-2026070802）都无法打开面板**，只有 :3007 回流通知的深链 `?panel=bid-confirm`（autoOpenBidConfirm，绕过守卫）能进。
- 守卫本意是锁定前置阶段内容，误伤了 BID_EVALUATION 自身的入口。
- **修法**：`if (isBidLocked && stageKey !== 'BID_EVALUATION')`；回归测试应覆盖「阶段进行中可打开面板」。

### P0-4 新抽取专家签到死锁（身份核验空壳的真实链路表现）✅ 止血（00529d3a）
- **位置**：`expert.service.ts:380-384`（signIn 硬闸门 phoneVerified）；extract 创建的 BidExpert 默认 false；验证码端点前端零接线（08-10 已记录为死代码）。
- 实测：5 位新抽取专家 phoneVerified 全 false → 签到 403 PHONE_NOT_VERIFIED「请先完成手机验证」，**而 :3006 没有任何入口能完成手机验证**。种子专家预置 true 掩盖此问题；真实抽取链路下评标无法开始，72h 后评标超时。
- 与 08-14 决策「身份核验整体后期升级」冲突点在于：升级之前真实流程就是死的。临时止血：抽取确认时把 phoneVerified 置 true（或签到闸门改为「拍照留痕 + 主持人现场核验」组合）。

### P0-5 ensureBidProject 时间兜底产生「已过期 deadline」+ 双套时间数据不通 ✅ 已修（17744eb8；双套时间源合并未做，兜底已不致过期）
- **位置**：`project-management.service.ts:288-292`：openTime = parseBidOpeningTime(bidOpeningTime) ?? initiationDate ?? **now**；deadline = **openTime − 12h**。
- 项目基本信息未填「开标时间」时（新建项目默认待补充；邀请向导里填的「采购文件获取时间/开标时间」**不写** bidOpeningTime，存在另一套 NegotiationConfig 数据里）→ openTime=now、deadline=now−12h → **项目一创建就过截标**，供应商立即 DEADLINE_PASSED，且 :3005 面板显示「截标已过」令人困惑。
- **修法**：兜底改为 deadline=now+一个正窗口；或 ensureBidProject 读取邀请向导已确认的时间；两处时间源合并。
