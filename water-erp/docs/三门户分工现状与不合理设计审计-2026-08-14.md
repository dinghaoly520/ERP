## 二、不合理设计清单

### 🔴 A. 鉴权与门户边界 —— 分工 v3 只有「约定」，没有「强制」

**A1. 后端没有「门户」概念，:3005 与 :3007 在后端是同一个门户。**
两门户都发 `X-Portal: web`、共用 `token_web`（`apps/api/src/auth/portal-cookie.ts:28-34`、`apps/bid-portal/src/proxy.ts:15-16`），全部 RBAC 只有 `@Roles` 没有来源校验。「不同的人在不同的地方」完全靠前端路由 + 文档维持：任何 bid_host 账号从 :3005 也能调 `start-evaluation`/`decrypt`/签字包全部端点；leader 的端点从 :3007 一样能调。

**A2. :3007 中间件允许 leader/staff 进入**（`apps/bid-portal/src/proxy.ts:45-46`），与「现场端=主持人/admin」矛盾；且该数组与 `bid.controller` 的 `@Roles`、专家门户 `WEB_ROLES` 三处**靠注释手工同步**（`apps/expert-portal/src/app/login/page.tsx:104-106` 自述）。:3005 的 proxy 则完全不做角色校验（只有 token 检查）。

**A3. 监督视图形同虚设。** `apps/bid-portal/src/components/bid/supervision-view.tsx` 的「监督权限边界/禁止干预评分」只是文字横幅——tab 无任何角色校验（`bid/project/[id]/page.tsx:191` 任何过门者可见），同一账号也能在评标管理 tab 点启动评标、生成结果。监督者与操作者是同一个人时，监督失去意义。

**A4. cookie 按「解析出的角色」而非「来源门户」命名**（`apps/api/src/auth/auth.controller.ts:47-48`，`portalForRole(result.role)` 优先）→ 同浏览器里 :3005 的 leader 与 :3007 的 bid_host 互相顶掉登录态（演示走查都要 isolatedContext）。

**A5. 登录入口碎片化，leader/staff 没有一条正经的回家路。**
从公共门户登录 → `landingURL('leader')` 落回 public '/'（`packages/config/src/urls.ts` 的 `ROLE_PORTAL` 没有 leader/staff/procurement_staff，`apps/public-portal/src/app/home-client.tsx:78`）；从专家门户 admin tab 登录 → 跳 :3007；只有 :3005 自己的登录页能回 :3005（且 leader/staff 落到 `?? "/work-arrangements"` 兜底而不是 /dashboard，`apps/web/src/lib/login/login-routing.ts:18`）。CLAUDE.md 的角色路由表（procurement_staff → web /dashboard）与代码不符。

**A6. 同名账号「陈源远」×3 角色 + 门户优先级解析**（`apps/api/src/auth/auth.service.ts:15-21`）：登录身份取决于从哪扇门进，而非你要用哪个身份——从 :3005 登录永远拿不到 mall 身份。另外 `auth.service.ts:13` 的注释「:3005 已改用 ./procurement 账户体系」是**过期错误注释**（auth/ 下无此体系，web 登录仍走优先级）；`procurement_staff` 角色全系统无优先级支持，只能靠 `candidates[0]` 兜底（`auth.service.ts:56-57`）。

### 🟡 B. 分工 v3 落地残留（迁移不干净）

**B1. :3005 仍保留「确认开标结果 → startEvaluation」。**
`apps/web/src/components/projects/bid-confirm-panel.tsx:369-376` + `apps/web/src/components/projects/bid-confirm/opening-progress-block.tsx:172-187`（openingDone 时显示按钮）。spec 明确「启动评标（:3007，OPENING→EVALUATING）」——:3005 这个按钮会抢先推进阶段，直接破坏分工。

**B2. 迁走的三区块原件没删，双份维护且已开始分叉。**
:3005 的 `evaluation-block.tsx`(837 行)/`dispute-block.tsx`(265)/`clarifications-block.tsx`(421) 零引用死代码；:3007 有改名版 `evaluation-view.tsx`(841) + 同名副本。两边的 ownership 注释互相矛盾（web 说「移植自 bid-portal」，portal 说「自 :3005 迁回」）。

**B3. 最危险的复制：`use-bid-websocket.ts` 两门户各一份且已分叉演化。**
:3007 版有 R9 延迟解引用修复而 :3005 没有；:3005 版有 EvaluationStarted/Clarification 事件处理而 :3007 没有。同样的还有 `lib/api/evaluation.ts`（从 :3005 `lib/api/bid.ts` 725 行复制）、`:3007 lib/api/supplier.ts`（整份拷贝供应商管理 API，实际只用了通知子集，`notification-bell` 还在开标现场每 30s 轮询供应商审批通知）。

**B4. :3007 三处 stale 文案与 v3 相反。**
`apps/bid-portal/src/components/opening-hall.tsx:347-363` 横幅仍写「评标管理与归档请在 :3005 操作」；`ai-analysis-card.tsx:8-10` 注释「只读评标管理 tab」；`app-shell.tsx:60` 注释还提已不存在的 `/bid/open`。现场主持人会被这些文案误导。

**B5. :3005 `opening-progress-block.tsx` 名不副实 + 数据陈旧。**
开标进度和「评标资料已接收·下载回流包」混在一个组件里（:191-205）；回流数据 `getSignPacket` 只在挂载时拉一次（:67-71），没有 socket、没有 onChanged 触发——:3007 闭环生成回流包后，:3005 页面不刷新就永远看不到（走查时就是 reload 才出现）。

**B6. :3007 每个 tab 都常驻「评分标准编制在采购管理工作台（:3005），本 tab 只读」提示**（`bid/project/[id]/page.tsx:182-184`）——即使当前在开标大厅/评标签字 tab 也显示，与上下文无关的永久横幅。

## 三、总结

**架构层**：分工 v3 在代码里是「三处手工同步的角色数组 + 前端路由约定」，后端与中间件完全没有门户边界——这是最值得先修的结构问题（A1-A3）。

**工程卫生层**：:3005→:3007 的迁移用了「复制不删除」策略，已经出现 4 组漂移副本和 3 处互相矛盾的文案（B1-B4），继续修哪边都会加剧分叉，建议尽早抽 `packages/ui` 或至少删掉死原件、统一所有权。

**文档层**：CLAUDE.md 至少有 5 处与代码不符（向导 5 步实为 7 步、工作区 4 tab 实为 6 tab、监督视图「大厅内嵌」实为独立 tab、角色路由表、种子账号表）。
