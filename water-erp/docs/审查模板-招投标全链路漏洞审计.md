# 独立严格审查任务：招投标全链路漏洞审计（投标→异议/解密→开标→评标→签字/回流→归档）

## 0. 被审对象与需求基准（先读再开工）

- 审查对象：当前工作区代码（含未提交改动；如需固定基线先记录 git rev-parse HEAD）。
  〔若本次审查某次具体改动：在此粘贴任务说明、验收标准、提交/分支范围，审查改为「以该改动为锚点向全流程辐射」〕
- 流程主线：供应商投标与异议、解密（:3004）→ 开标（:3007 现场执行；评标前准备/按时开标在 :3005）→
  专家评标（:3006，含平板配对）→ 评标结果生成、异议裁决、澄清答疑、评标签字包、评标回流包（:3007）→
  归档、公示、中标通知书（:3005）。
- 需求基准（判断"缺失/错误"的依据，按优先级）：
  1. 招标投标法及实施条例、电子招标投标办法的硬性要求（澄清须应邀、不足三家流标、评标保密等）；
  2. 仓库 CLAUDE.md 的口径与用户裁定；
  3. docs/superpowers/specs/ 下 bid 相关设计 spec；
  4. 通用正确性（状态机、并发、单位、权限、事务）。

## 1. 角色与铁律（违反任何一条＝审查无效）

你是独立的严格审查者，只审不改：

1. **只读纪律**：不得修改任何代码/配置/文档。允许只读取证：检索、读文件、SELECT 查库、跑已有测试。
2. **证据先行**：每条结论必须附 `文件:行号` 与关键代码摘录。禁止凭注释、文档、CLAUDE.md 描述下结论——
   文档与代码漂移是本仓库已知现象，一切以代码为准；文档声称的守门要在代码里找到才算存在。
3. **逐项对账**：第 4 节每个分支点必须给出三态结论之一——✅ 无问题 / ❌ 有漏洞 / ⚠️ 无法确认（注明缺什么
   证据、如何补验）。对账表随修复清单一并交付，不得静默跳过任何一项。
4. **追调用链**：不因"写了守卫/校验"就放行。守卫可能漏端点、挂错层（Controller 有 Service 无）、条件写反、
   或在镜像处漂移（历史实例：启动评标闸门与 evaluation-view 镜像漂移）。关键闸门必须追到实际执行路径与全部调用方。
5. **可复现**：每条 ❌ 附触发操作序列（API 调用序列或 UI 步骤，含前置数据状态），可直接当测试脚本执行。
6. **不空谈**：不输出"建议加强安全/完善测试"类无 actionable 内容的条目。

## 3. 流程地图（对账基准；本节本身也须以代码核实，不符即为发现）

- **阶段机**：DOWNLOAD→SUBMIT→OPENING→EVALUATING→ARCHIVED，另有 ABORTED（流标）。单向棘轮：只许前进、
  允许跳步、同阶段幂等；回退或离开 ARCHIVED 必须 409。阶段只是进度标记，**实质准入闸门下沉在各写端点**
  （投递=OPENING 前+截标未到+已发布公告；解密=OPENING+解密窗口内）——审查重点是端点级闸门，不是 stage 字段。
- **分工 v3**：评标前准备与按时开标=:3005；开标/评标现场全过程=:3007（现场执行权跟随主持人指派
  AssignedHostGuard）；评标后收尾（回流接收、完整归档、公示、通知书）=:3005。complete-opening 生成开标
  文件包并 WS 回传，幂等、不改 stage、不是启动评标的前置闸门。
- **金额铁律**：开标记录侧=万元（amount 裸数字+amountUnit 落戳，四处写入点）；BidQuote/评标结果/中标通知=元。
  跨侧换算仅两座桥：syncMultiRoundPrices（元→万元）与 generateEvaluationResults（万元→元）。读端唯一入口
  opening-amount-unit.util；任何裸读裸算 amount/decryptedPrice 的读端都是缺陷。
- **收尾冻结链**：专家确认报告→SCORE_LOCKED（个人评审写端点）；结果生成→RESULTS_FROZEN（迟到报价/新轮次）；
  PMI 归档→PMI_NOT_ACTIVE。动议/异议/澄清/签字链动作依法保持开放。
- **完整归档闸门**＝签字闭环（全员签字登记）＋评标回流包已生成/接收。
- **守卫清单**：AuthGuard→RolesGuard 全局链（默认拒绝）、AssignedHostGuard、PairingScopeGuard、
  PmiOwnershipGuard、专家端启动前只读闸——守卫覆盖面本身是对账内容。
- **2026-11-23 新面增补**：①采购方式已扩为**六方式**（+公开招标 PUBLIC_BIDDING——公告公示组织供应商、
  邀请招标同构 8 阶段、统计分列「采购项目/招标项目（公开）/（邀请）」三行口径）；②**PMI 附件双轨**
  （attachment-object-store：本地 uploads/ 主轨→MinIO 副本双写、读取本地→MinIO 回退、双失 404、
  删除双清、存量回填脚本）；③**变更采购文件**（BidDocument.supersededBy 版本链、变更公告换源、
  旧文件禁下载指回）；④**专家生命周期**（shared/expert-lifecycle 状态机）与**评分计算器 v3**
  （shared calculator-core + expert-portal 浮窗）；⑤**供应商三级审批严格化**（admin 禁代审、
  全级理由必填、业务标签审批公司隔离）；⑥**只读镜像门户**（:3011 mobile/:3010 大屏——
  x-portal-source 豁免公司隔离的读面）。以上各面在 v1.0 对账表(2026-11-20)中不存在，须按 H 组补审。

## 4. 分支点与兜底行为核对清单（验收线，逐项三态对账）

**A. 供应商投标与截标（:3004 / supplier-portal+ca+bid）**
- A1 截标后投递：服务端拒绝（deadline 校验位置、是否信任客户端）；截标瞬间并发投递/撤回的竞态窗口。
- A2 撤回：仅 DOWNLOAD/SUBMIT 允许；OPENING 后必拒；撤回后重投的状态/密钥复位。
- A3 dual-v3 CA 轨：验签失败、证书过期（CERT_EXPIRED/BIND_CERT_EXPIRED）、白名单外主体、PoP 失败的拒绝路径与留痕。
- A4 双信封：C_outer 哈希/完整性校验失败；解密窗口外解密；某一家解密失败时其余家不受阻、失败留痕。
- A5 大文件分块链路：中断重试、分块乱序、500MB 上限边界。
- A6 资格与可见性：未受邀/跨公司供应商获取文件与投递（归属∪受邀闸、CROSS_COMPANY_INVITE）；临时/待审批供应商投递。
- A7 投递后公告删除/项目终止的联动（BID_IN_PROGRESS 禁令、终止→公告回收站、投递数据保留）。
- A8 多轮报价：未开轮报价、closed 后报价、结果生成后迟到报价（RESULTS_FROZEN）、事后新建轮次闸；BidQuote=元。
- A9 供应商异议通道：开标异议/评标异议各走哪里、谁处理、未处理能否推进。
- A10（v1.1）金额字段隐式单位·PMI 半区：金额铁律地图止于中标通知书——PMI 预算/合同额、保证金台账
  （bidAmount vs ledger.amount）、award/公示零散读端的单位口径；「新增金额字段禁造隐式单位」的执行面。

**B. 开标（:3007 大厅 + :3005 准备）**
- B1 现场执行权：AssignedHostGuard 覆盖全部主持端点（含 WS 事件面）；未指派/非本人必 403 NOT_ASSIGNED_HOST。
- B2 开标会话：重复组建幂等；解密窗口必填；监督人缺省路径。
- B3 延时开标：截标随最新开标时间重算（开标−10min）；已按旧截标投出的投标如何处理。
- B4 家数门槛：开标时 0/1/2 家投递——是否校验法定三家、引导流标/重新招标，还是照常开标。
- B5 解密兜底：部分/全部供应商未解密、解密超窗——如何推进、留痕、是否影响唱标。
- B6 唱标：万元单位录入闸（PRICE_UNIT_SUSPECT 双向）；已确认记录禁覆盖（H11）；漏唱某家能否补；
  唱标值与解密明文不一致以谁为准。
- B7 开标异议：处理中能否推进开标/确认；成立与驳回两分支的后续动作与留痕。
- B8 完成开标·移交：重复触发幂等；文件包 SHA-256 指纹；WS opening:completed 丢失时 :3005 的兜底。
- B9 开标前流标（:3005）时 :3007 已组会话/已有解密数据的联动收敛。
- B10 投标文件下载越权矩阵：C_outer 本人拒收、C_inner 成员放行、bid_decrypted 仅指派对象。
- B11 监督视图只读性；会场交流数据隔离。

**C. 评标启动与专家评标（:3006 + :3007 评标管理）**
- C1 启动评标闸门：与 evaluation-view 镜像一致；边界因子（none 组合）能否误启动。
- C2 专家替换：窗口=开标后、启动评标前、未签到（四闸）；confirmed 与 isLead 转移；窗口外必拒；候补递补链路。
- C3 评标中专家无法履职（重点分支）：中途回避申报后其已交评分如何处置、法定人数是否校验、是否留痕；
  退库/失联的兜底。
- C4 操作窗口：签到前只读双闸、签到→报告确认窗口外操作全拒；评标室口令错误重试上限与轮换。
- C5 单设备与配对：评标期他处登录 409 ACCOUNT_EVALUATING；配对票 90s 单次、烧票、PAIRING_REVOKED/
  SESSION_REPLACED/PAIRING_PROJECT_MISMATCH；受限令牌写面白名单外默认拒绝；平板只存草稿。
- C6 草稿双槽合并：per-entry savedAt 取新者的正确性（同键回声、时钟回拨）。
- C7 标书获取：谈判项目走 Redis 配置轨（BidDocument 恒空）+公告轨回退；文件缺失/解封失败的降级与留痕。
- C8 AI 辅助评标：worker 不在/LLM 失败时评标能否继续、重试入口、失败可见性。
- C9 打分：五类分值越界/缺项/负数；免评与豁免在五个消费面口径一致；专家间评分互见的时点（保密期）。
- C10 澄清：仅应邀回复通道（不得存在供应商主动发起入口）；澄清不受评标超时闸拦截；答复送达专家的可见性。
- C11 评标中异议与流标：受理→裁决→维持/流标两分支；流标时专家侧/供应商侧/PMI 状态收敛与通知。
- C12 动议表决链（发起/表决/决议执行/留痕）。
- C13 冻结链：confirmReport 后个人评审写端点全拒（SCORE_LOCKED，含空草稿清空豁免口径）、重复确认 409。
- C14 评标时限：EVALUATION_OVERDUE 只拦 submitScores/confirmReport/generateEvaluationResults；
  extend-evaluation 的监督+审计留痕。
- C15（v1.1）Prisma Json 列形状契约：writer/consumer 形状一致性专项——N13-B 死代码实录模式
  （reader 读 result.files、writer 恒写 canonical 字符串、测试夹具伪形状空转绿）：凡新增 Json 列
  消费端，必须对**真实 writer 形状**断言（追写入点逐字段对表），禁以想象形状写测试。

**D. 评标结果与废标（:3007）**
- D1 个别投标无效/废标（重点分支）：是否有个别投标人符合性否决机制？废标一家后剩余家重新排名、价格分
  是否重算、废标原因留痕与该供应商可见性。
- D2 全部无效/有效标不足三家时生成结果：应流标而非生成空结果/单一结果。
- D3 存在未 closed 报价轮时生成结果的闸。
- D4 金额桥：generateEvaluationResults 万元→元唯一换算点；结果/通知书=元；新读端裸读裸算即缺陷。
- D5 同分/并列处理规则是否存在且一致。
- D6 结果重生成闸（SIGN_PACKET_CLOSED）；重生成后下游（通知书/公示）同步。

**E. 评标签字包与回流（:3007→:3005）**
- E1 签字包内容完整性（评标报告十项法定内容+签字页+个人评分确认表+异议工单+澄清纪要+动议决议）；
  生成时专家已退库/数据缺失的兜底。
- E2 签字登记三态（已签/拒绝须附书面不同意见/视为同意）的判定与必填校验。
- E3 回传扫描件登记错误的校验；multipart 文件名必须过 normalizeMultipartFilename（latin1 铁律）。
- E4 全员闭环判定：含已替换/已退库/候补专家的边界；未闭环能否生成回流包。
- E5 回流包生成重复/失败的幂等与重试；:3005 接收校验（指纹/完整性）。

**F. 归档·公示·通知书（:3005）**
- F1 archive-all 的 scope×stage 矩阵：穷举组合验证（EVALUATING+opening、ABORTED+full 等历史漏洞模式的
  同类组合是否还有漏网）。
- F2 完整归档双闸（签字闭环+回流已接收）不可绕过。
- F3 PMI 归档与投标归档两扇门：BID_IN_PROGRESS 闸；流标项目归档不受阻；终止项目下游联动。
- F4 归档后写路径冻结的漏网扫描：已知 SCORE_LOCKED/RESULTS_FROZEN/PMI_NOT_ACTIVE 之外，是否还有能扰动
  已归档数据的写端点（附件、评分、澄清、文件类）。
- F5 公示期计算与公示期满/手动下线提示页；公示期内的信息可见范围。
- F6 中标通知书：元口径、与结果/迟到报价脱钩；未中标供应商的通知。
- F7 归档后证据链可回看：开标文件包/回流包/签字包/监督日志可下载且不可删。

**G. 横切面（跨阶段自由挖掘）**
- G1 权限矩阵：相关模块全部端点逐个核对角色标注与守卫；横向越权（跨项目/公司/供应商/专家）与纵向提权。
- G2 状态机：每个写端点是否校验合法来源阶段；找出能造成回退、跨阶段写、脏中间态的端点组合。
- G3 并发与幂等：双主持人并发、专家并发提交、重复请求、WS 重复事件的幂等破坏。
- G4 事务与一致性：多表写部分失败；DB+MinIO+Redis 跨存储不一致；冗余字段漂移（amountUnit vs envelopeVersion）。
- G5 保密性：开标前任何端点能否探到他家报价/家数；解密前明文是否落库/落日志；专家评分暴露时点。
- G6 通知与留痕：关键节点通知漏发/错发；WS 断线轮询兜底；法定动作 AuditLog/OperationLog/监督日志缺失。
- G7 前后端镜像：前端按钮露出/禁用与后端闸门漂移；409/4xx 的前端处理与用户可见性。
- G8（v1.1）锁序一致性：全库行锁族（BidProject→Record→Packet→Expert…）锁序审计——找锁序环/死锁面；
  「事务内 .catch 吞错=毒化事务」模式（F3 实录）。
- G9（v1.1）多通道通知完整性：短信通道（融易达）失败留痕/计费分段（>70 字分段）/对账迁移欠账
  （NotificationDeliveryLog P2022 类）；G6 站内+WS 之外的外发轨。

## 5. 已知设计裁定（勿当漏洞误报；但须核实实现与裁定一致）

## 7. 建议工作法

1. 建底册：先检索列出四域全部相关 controller 路由（方法+路径+角色标注+守卫+主要写表），作为对账底册。
2. 走主线：挑一个 DB 既有项目沿状态机从头走一遍真实数据流。
3. 逐项对账：按第 4 节 A→G 逐项落到具体端点/组件，给三态结论。
4. 横切扫描：拿底册过一遍 G 组各轴。
5. 产出四件套。若用子代理分域并行，每条发现必须回主线程亲自验证 file:line 后才能进清单。
