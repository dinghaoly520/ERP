# 金仓（KingbaseES PG 模式）生产部署 · 数据库初始化教程

> **适用场景**：全新金仓库（空库），项目已部署、登录报 500（前端转发失败或 Prisma `P2021`/`P1001`）。
> **两种部署形态，本文分轨给命令**：
> - **形态 A · 宿主机部署**——项目文件 + Node 在生产机上
> - **形态 B · Docker 镜像部署 + 远程数据库服务器**（应用/数据分离）——应用在部署机容器里，金仓在专门数据库服务器上（本形态为 2026-10 实际生产形态：金仓 `10.60.1.10:54321`，库 `test`，用户 `ssyc`，PG 模式）
>
> **核心原则**：迁移落到哪，由连接串 `DATABASE_URL` 指向的那台数据库决定——在能连通目标金仓的任何机器上跑都行（部署机容器内 / 部署机宿主机 / 甚至开发机）。
> **背景**：本机开发栈 2026-10-21 起已切金仓（`localhost:54321`）；旧 PostgreSQL（`localhost:5432`）停用，全程不参与。
> 迁移链于 2026-10-21 在本地金仓（V008R006C009B0014，与公司版本同系）完整验证；当时链长 214 条，截至 2026-10-23 已增至 **221 条**（新增迁移同路径自动重放）。

## 0. 出发前核对

**形态 A（在生产机器、项目根 `water-erp/` 下）：**

```bash

ls apps/api/prisma/migrations/ | wc -l     # ② 迁移 SQL 在（应输出 220+ 个条目，是建表的数据来源）
node -v                                    # ③ Node 24.x
ls apps/api/node_modules/.bin/prisma       # ④ prisma CLI 可用（缺则先 pnpm install）
```

**形态 B（在部署机上，先探 API 容器）：**

```bash
docker ps -a | grep -i api                          # API 容器状态（一直 Restarting = 连不上库，正常现象）
docker logs <api容器> --tail 50                     # 找 Prisma 报错码定诊断（P1001=连不上 / P2021=表不存在）

docker exec <api容器> sh -c "ls apps/api/prisma/migrations | wc -l && ls node_modules/.bin/prisma"  # 迁移SQL+CLI 在容器内是否齐
```

镜像里没带 prisma CLI（属 devDependencies）时：改在宿主机/开发机装项目后跑迁移（连得通目标库即可），不必重打镜像。

## 1. 金仓实例参数（数据库服务器侧）

金仓在专门服务器上由 DBA 管理，应用侧只需确认三件事：

| 项 | 要求 | 说明 |
|---|---|---|
| 模式 | `DB_MODE=pg` | PG 兼容模式（验证：`show database_mode;` → `pg`） |
| 网络放行 | 部署机 IP 可达 54321 | 金仓 `listen_addresses` 含外部、`sys_hba.conf` 放行部署机网段、防火墙开端口 |
| 用户权限 | 项目用户（如 `ssyc`）对目标库有建表权 | **普通用户无权 CREATE EXTENSION**——见第 3 步让 DBA 预建 kbcrypto |

若需自行以 Docker 起金仓（测试形态），三坑：`DB_MODE=pg`、`ENABLE_CI=no`（默认 yes 会 initdb 失败）、密码变量是 `DB_PASSWORD`；`ksql` 不认 `PGPASSWORD`，TCP 测试须口令内嵌连接串。

## 2. 应用侧连接配置

**⚠ 密码 URL 转义（必踩坑）**：密码含 `#` `@` 等字符时，直接拼进 `postgresql://user:密码@host...` 会解析错位（`@` 是主机分隔符、`#` 是 fragment 符），症状为连接失败且极迷惑。URL 内必须转义：`#`→`%23`、`@`→`%40`。例：`Ss2026#yc@` → `Ss2026%23yc%40`。

成品连接串（按实际替换）：

```
postgresql://ssyc:Ss2026%23yc%40@10.60.1.10:54321/test
```

**协议前缀就是 `postgresql://`**——金仓 PG 模式兼容 PostgreSQL 线协议，Prisma 规定这么写，指的不是 PG；区分后端看 IP/端口。

配置注入方式：

- **形态 A**：改 `apps/api/.env` 的 `DATABASE_URL` / `DIRECT_URL`（`DIRECT_URL` 供 Prisma CLI 直连，勿带 pgbouncer 参数）。
- **形态 B**：镜像里烤死的开发 `.env` **不用重打镜像**——compose `environment:` 注入即可覆盖（进程环境变量优先于 `.env` 文件）：

```yaml
# API 服务
environment:
  DATABASE_URL: postgresql://ssyc:Ss2026%23yc%40@10.60.1.10:54321/test
  DIRECT_URL: postgresql://ssyc:Ss2026%23yc%40@10.60.1.10:54321/test
  REDIS_URL: redis://redis:6379            # compose 网络内用服务名
  MINIO_ENDPOINT: <生产MinIO地址>
  PGVECTOR_ENABLED: "false"                # 金仓无向量能力，不用 RAG 审查就关
# 每个前端门户容器（web/supplier/expert/bid/public/mall/assistant…）都必须：
  API_ORIGIN: http://<api服务名>:4001      # 不设=容器内 localhost:4001=门户自己→全部API 500
```

> 容器内 `localhost` 是容器自身：`localhost:4001`、`localhost:6380`、`localhost:8100` 等全部不可达。完整「localhost 系列」清单见第 7 节。

若 `.env` 从开发机打包带去，其中 dev 指向的生产替换见第 7 节表。

生产守卫（`NODE_ENV=production` 时）：`JWT_SECRET` ≥32 字符否则拒绝启动；`CORS_ORIGINS` 列前端真实域名；`TRUST_PROXY=1`；`KMS_SECRET`、`FIELD_ENC_SECRET`（≥32 字符）必填。

## 3. 建库与扩展（数据库服务器上，DBA 一次性操作）

**迁移只需要一个空库，不需要任何预置数据。** 让 DBA（system 用户）在 10.60.1.10 上执行：

```sql
-- 目标库若未建（test 为金仓默认库，通常已存在；建议为项目专建新库更干净）：
-- CREATE DATABASE water_erp OWNER ssyc;

-- 关键：预建 kbcrypto 扩展（迁移链的 gen_random_uuid() 依赖；
-- 普通用户 ssyc 无权 CREATE EXTENSION，不预建则迁移脚本自动重试也会失败）
\c test
CREATE EXTENSION IF NOT EXISTS kbcrypto;
```

已建库/已建扩展（`already exists`）无害。

## 4. 跑迁移（核心步骤）

先测连通（任何将执行迁移的机器上）：

```bash
# 部署机容器内（镜像有 node，不用装 nc）：
docker exec <api容器> node -e \
  "require('net').connect(54321,'10.60.1.10').on('connect',()=>{console.log('通');process.exit(0)}).on('error',e=>{console.log('不通:',e.message);process.exit(1)})"
```

不通 → 找 DBA/网管放行（`sys_hba.conf`、防火墙），这是运维问题。

> ⚠ **Prisma CLI（migrate deploy/status/db execute）加载 `.env` 时会覆盖 shell 环境变量（2026-10-26 实测：shell 传入不可达 IP 仍连 `.env` 指向的库）**。与 NestJS 运行时相反（`@nestjs/config` 不覆盖进程环境变量 → compose `environment:` 只对运行时 API 有效）。**因此跑迁移前必须先让 `apps/api/.env` 的 `DATABASE_URL`/`DIRECT_URL` 实际指向目标库**；命令里的 shell 前缀传参仅为满足脚本闸门，值须与 `.env` 一致，否则不生效。

**形态 A（部署机宿主机）**：

```bash
# ① 先改 apps/api/.env 两行（密码 URL 转义见第 2 节）：
#    DATABASE_URL=postgresql://ssyc:Ss2026%23yc%40@10.60.1.10:54321/test
#    DIRECT_URL=postgresql://ssyc:Ss2026%23yc%40@10.60.1.10:54321/test
# ② 再跑脚本：
cd water-erp
DATABASE_URL='postgresql://ssyc:Ss2026%23yc%40@10.60.1.10:54321/test?schema=public' \
DIRECT_URL='postgresql://ssyc:Ss2026%23yc%40@10.60.1.10:54321/test' \
./scripts/db-migrate-kingbase.sh
```

**形态 B（API 容器内）**——容器里烤死的开发 `.env` 指向 `localhost:54321`（容器内必死路），**先改容器内 `.env` 再跑**：

```bash
# ① 改容器内 .env 两行（路径按第 0 步探到的项目根替换）：
docker exec <api容器> sed -i \
  -e 's|^DATABASE_URL=.*|DATABASE_URL=postgresql://ssyc:Ss2026%23yc%40@10.60.1.10:54321/test|' \
  -e 's|^DIRECT_URL=.*|DIRECT_URL=postgresql://ssyc:Ss2026%23yc%40@10.60.1.10:54321/test|' \
  <项目根>/apps/api/.env

# ② 跑迁移：
docker exec <api容器> sh -c "cd <项目根> && \
  DATABASE_URL='postgresql://ssyc:Ss2026%23yc%40@10.60.1.10:54321/test?schema=public' \
  DIRECT_URL='postgresql://ssyc:Ss2026%23yc%40@10.60.1.10:54321/test' \
  ./scripts/db-migrate-kingbase.sh"
```

**形态 B 兜底**（镜像只拷了 `apps/api`、容器内无 `scripts/` 时用裸命令，效果等价）：

```bash
docker exec <api容器> sh -c "cd apps/api && \
  DATABASE_URL='postgresql://ssyc:Ss2026%23yc%40@10.60.1.10:54321/test?schema=public' \
  DIRECT_URL='postgresql://ssyc:Ss2026%23yc%40@10.60.1.10:54321/test' \
  npx prisma migrate deploy"
# 若报 vector.control 相关失败（金仓无 pgvector，属预期差异）：
docker exec <api容器> sh -c "cd apps/api && \
  DATABASE_URL='…同上…' DIRECT_URL='…同上…' \
  npx prisma migrate resolve --applied 20260727020000_add_document_chunk_embedding"
# 然后重跑上面的 migrate deploy 直到全绿
```

脚本行为：`prisma migrate deploy` 在空库上**全量重放整条迁移链**（截至 2026-10-23 为 221 条，以打包内 `apps/api/prisma/migrations/` 条目数 − 1 个 lock 文件为准），并自动处置两处金仓差异：

1. 缺 `gen_random_uuid()` → 尝试 `CREATE EXTENSION kbcrypto` 后重试（ssyc 无权时靠第 3 步 DBA 预建兜底）；
2. pgvector 迁移（`20260727…`）→ 主库跳过（`migrate resolve --applied`）。

其余类型的失败原样上抛终止——**保留输出贴回来人工分析，不要反复盲跑**。

**成功判据**：输出 `✔ 全部迁移已应用`。

## 5. 验证

SQL 对账（在数据库服务器上，或任何 ksql 客户端连 10.60.1.10）：

```sql
select count(*) from "_prisma_migrations" where finished_at is not null;  -- 预期 = 迁移目录条目数 − 1（2026-10-23 时为 221）
select count(*) from pg_tables where schemaname='public';                 -- 预期 170+ 张表
```

行为验证（**无需重启 API**——Prisma 不缓存表结构；形态 B 需确保容器此刻能连上库）：点一次登录 → 返回 **401「用户名或密码错误」**（不再是 500）。

> **401 是预期成功信号**：表结构已就位，只是库里还没有用户。到此「登录 500」问题即告解决。

**终极验证：结构总校验和（2026-10-27 实战定稿）**——计数对了也可能「错位对不上」，md5 错一个字符都藏不住。与权威库比对（生产侧跑，期望值随迁移链演进变化，以权威库现算为准；2026-10-27 基准 = `7ca6f3fba9ccb3f1ea19de55f19b892d`）：

```sql
select md5(string_agg(line, E'\n' order by line)) from (
  select format('COL %s|%s|%s|%s', table_name, column_name, data_type, is_nullable) as line
  from information_schema.columns
  where table_schema='public' and table_name not like 'sys_stat_statements%'
  union all
  select format('ENUM %s=%s', t.typname, string_agg(e.enumlabel, ',' order by e.enumsortorder))
  from pg_type t join pg_enum e on e.enumtypid=t.oid
  join pg_namespace n on n.oid=t.typnamespace
  where n.nspname='public' and t.typname not like 'sys_stat_statements%'
  group by t.typname
) s;
```

> 注意：`NOT LIKE 'sys_stat_statements%'` 排除是**生产库装有 DBA 监控扩展**（本机没有）时的对齐前提，别去掉。另可用 `prisma migrate diff --from-url <库> --to-schema-datamodel prisma/schema.prisma --exit-code` 做 Prisma 裁判级比对——已知固有差异（OperationLog 复合主键系分区表设计、DocumentChunk.embedding 由 sidecar 承载、companyId 索引/FK 短名/phoneIdx 约束为历史声明漂移）属预期，勿按 diff 「修复」。

## 6.（可选）灌种子数据——需要登录账号时才做

迁移只建表结构（零数据）。要用测试账号登录时执行（形态 A 在项目 `apps/api/` 下；形态 B `docker exec` 进容器后同命令）：

```bash
ALLOW_PROD_SEED=1 \
DATABASE_URL='postgresql://ssyc:Ss2026%23yc%40@10.60.1.10:54321/test?connection_limit=1' \
npx tsx --env-file=.env prisma/seed.ts
```

每个旗标都是实测坑，含义：

- `ALLOW_PROD_SEED=1`：生产守卫放行。⚠️ **seed 会 TRUNCATE 全部业务表——库里有真实数据后严禁再跑**。
- `npx tsx` 直跑而非 `pnpm db:seed`：后者的 run 前自检在 apps/api 下会炸 workspace 解析。
- `?connection_limit=1`：多核机器 seed 并发跳连坑。
- `--env-file=.env`：seed 依赖 `KMS_SECRET` 等一串环境变量；命令行前置的 `DATABASE_URL` 不会被它覆盖（Node 语义：不覆盖已设变量）。若 tsx 版本不认该旗标，改用 `set -a; source .env; set +a` 后再跑。（形态 B 容器内若无 .env，需显式带上 seed 所需 env，或临时挂载。）

## 7. 「localhost 系列」清单（Docker 部署必查）

**A. 后端 API 容器（`.env` 带进镜像的 dev 指向）：**

| 变量 | dev 值 | 用途 | 不通的症状 | 生产替换 |
|---|---|---|---|---|
| `DATABASE_URL` / `DIRECT_URL` | `localhost:54321` | 主库 | API 起不来（P1001） | `10.60.1.10:54321/test`（密码 URL 转义） |
| `REDIS_URL` | `redis://localhost:6380` | BullMQ 队列、缓存 | 重连告警、AI 分析不出队 | compose 内 `redis://redis:6379` |
| `MINIO_ENDPOINT` | 开发机 IP | 全部文件上传/下载 | 上传下载全挂 | 生产 MinIO 地址（:9000） |
| `OCR_SERVICE_URL` | `localhost:8100` | OCR 识别 | 扫描件解析报错 | 部署 `services/ocr` 后指它 |
| `EMBEDDING_BASE_URL` / `VECTOR_DATABASE_URL` | `localhost:8003` / `:5434` | RAG 语义审查 | 语义审查挂 | `PGVECTOR_ENABLED=false` 即不触发 |
| `SUPPLIER_PORTAL_URL` / `EXPERT_PORTAL_URL` | 开发机 `:3004`/`:3006` | 邀请链接基址 | 邀请链接指到开发机 | 生产门户地址 |

**B. 前端门户容器——API 转发地址（每个门户必设）**：门户经容器内服务端转发 API 请求，目标默认 = 容器内 `localhost:4001` = 门户自己 → **全部 API 500（登录 500 的常见直接机理）**。三个相关变量（2026-10-26 源码核对）：

| 变量 | 作用域 | 说明 |
|---|---|---|
| `API_ORIGIN` | 所有门户 | `@water-erp/config` 的 `apiOrigin()`（rewrites/proxy 上游），设 `http://<api服务名>:4001` |
| `API_SERVER_URL` | web / supplier | `src/proxy.ts` 优先读它（兼容别名，设 API_ORIGIN 后可不设） |
| `API_BASE_URL` | public-portal | 首页 RSC 直连读它（绕过 rewrites），**单独必设**，否则首页公告列表为空 |

> ⚠ `NEXT_PUBLIC_*` 系列是**构建时内联**变量——运行时 compose 注入无效。已知一处兜底为绝对地址：web 门户「电子商城管理→中央目录」页（`NEXT_PUBLIC_API_URL`，兜底 `localhost:4001`），生产该页会挂；正解是改代码兜底为 `'/api'` 随下次打包，或构建镜像时传该变量。其余 `NEXT_PUBLIC_*` 兜底均为 `'/api'` 相对路径（走同源代理），无需处理。

**C. 出公网外呼（内网需确认出口）**：`api.deepseek.com`（AI 全家）、`testmicrosrv.scca.com.cn:9527`（CA/U盾）、阿里云 SMS（注册验证码）。

**D. 仓库自带 `docker-compose.yml` 陷阱**：基础设施默认含 pgvector PG16 + pgbouncer（PG 时代遗产）——生产别起这两个（连的是金仓），Redis/MinIO 服务可直接用。

## 8. 常见报错对照

| 症状 | 根因 | 处置 |
|---|---|---|
| 登录 500（前端返回） | 门户容器 `API_ORIGIN` 未设，转发打到容器自身 | 第 7 节 B |
| API 容器 Restarting / `P1001 Can't reach database` | 库连不上（地址/网络/金仓没放行） | 第 4 步连通测试 → 找 DBA 放行 |
| 连接报错且 host 显示怪异 | 密码含 `#`/`@` 未 URL 转义 | 第 2 节转义规则 |
| API 起来了，登录 500 + `P2021` | 表未建（迁移没跑） | 第 4 步 |
| 登录 401「用户名或密码错误」 | 表已建、无数据 | **正常**；要登录跑第 6 步 |
| 迁移报 `permission denied to create extension` | 项目用户无权建 kbcrypto | 第 3 步让 DBA 预建 |
| 迁移报 `gen_random_uuid() does not exist` | 扩展未建 | 同上（脚本自动重试也需权限） |
| initdb 报 `case-insensitive should only be enabled in oracle mode` | `ENABLE_CI` 未设 `no` | 重建实例补 `ENABLE_CI=no` |
| `@prisma/client did not initialize yet` | client 未生成 | `cd apps/api && npx prisma generate` |
| 核对清单缺迁移 SQL / Node / CLI | 打包漏带 | 回开发机重新打包 |
| KStudio「执行 SQL 文件」2ms 显示成功、实际零导入 | 工具未真执行（大文件解析/编码问题） | 改用「打开到编辑器→全选→执行脚本」；首选命令行 `ksql -v ON_ERROR_STOP=1 -f` |
| 可视化工具报错后继续执行，重导报 `already exists` | 遇错继续留下半成品 | 执行前开「遇错即停」；重导前先跑清场 DO 块（表/枚举/序列/视图循环 + **排除 `sys_stat_statements%`**——DBA 监控扩展对象无权也不应删） |
| `CREATE SCHEMA/EXTENSION IF NOT EXISTS` 报 `must be owner` / `to update extension` | 金仓怪癖：已存在分支仍做 owner/版本检查（报错文案误导） | 删掉该句（库自带 public 即无需建）；或 DBA `ALTER SCHEMA public OWNER TO ssyc` 一劳永逸 |
| 报 `function gen_random_uuid() does not exist`（导入/验证时） | 库缺 kbcrypto 扩展 | DBA 对目标库 `CREATE EXTENSION kbcrypto;`（装完用 `select gen_random_uuid();` 验货） |
