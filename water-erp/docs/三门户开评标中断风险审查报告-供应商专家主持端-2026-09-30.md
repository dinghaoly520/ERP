# 三门户开评标流程中断风险审查报告（:3004 供应商门户 / :3006 专家门户 / :3007 开评标管理端）

- **审查日期**：2026-09-30（五路结果合并完成）；**落档日期**：2026-10-08
- **审查目标**：三端代码与 UI 中可能导致开标/评标流程「进行不下去」的意外情况（含专家异议无法解决、专家失联、解密/确认卡死等），逐项确认是否存在现场出口
- **方法**：主会话亲读后端（apps/api/src 的 bid/、expert/、expert-admin/、supplier-portal/ 核心文件全量或关键段）与三端前端关键组件（bid-portal 任务板/评标管理/异议裁决/签字/开标大厅、expert-portal 桌面评审向导、supplier-portal 解密卡/开标大厅/提交页），全部承重结论带亲核 file:line；另 4 个探索代理独立审查交叉补充（承重引用均经主会话抽查复核，无失实；1 个代理因会话工具缺失如实报告未产出）。本会话无 Write/Bash，本文件经 Monitor shell 通道落盘。

## 总体结论

主链路（dual-v2 加密投递→取包解密→唱标→供应商确认→启动评标→打分/核对/报告确认→组长末签→生成结果→签字闭环→回流→归档）的断点出口设计**总体完善**：异议裁决矩阵、解密失败归因（BIDDER/PLATFORM/RESET_PENDING）、评标延期、拒签视为同意、评标中断点续评、单设备互踢的解锁通道、WS 断连重连全量补拉等均验证健康（负结果清单见文末）。

但发现 **P1×8（流程级死锁）、P2×约14、P3×约15**。所有 P1 的最终兜底均为「流标→重启」（`abortBidProject` 走单向棘轮、EVALUATING→ABORTED 合法，`bid.service.ts:1378`；`reopenFromAborted` 可重启新轮）——**不存在连流标都无法执行的状态死局**，但对合法有效投标整体作废，应急出口过重。

## P1 清单（8 项）

### P1-1 供应商解密成功但拒不/无法确认唱标 → 开标永久卡死，主持人无出口
- **证据**：H4 完成度守卫（`bid.service.ts:1866-1870` openingRowNotReady：SUCCESS 且非 CONFIRMED/EXCEPTION 即阻塞 startEvaluation 与 completeOpening）；`overrideDispute` 只收 DISPUTED/EXCEPTION（`bid-opening-record.service.ts:427`）；`acceptSupplierDanger` 只收 DANGER 或（窗口过期+未解密）（`bid-decrypt.service.ts:774-777`）；`resolveOpeningDispute` 只收异议态（`bid-opening-record.service.ts:323`）；供应商确认强制 U盾 SM2 签名（`supplier-portal opening-confirm` 端点）；无确认时限（`disputedSince` 仅异议时设置）。
- **场景**：供应商解密成功后，确认时刻 U盾不可用/人员离场/浏览器崩溃不回 → confirmStatus 永停 PENDING → 无法启动评标/移交 → 只能整标流标。
- **修复建议**：`overrideDispute`（或新端点）增加 PENDING→CONFIRMED「缺席视为无异议」通道（admin/leader+书面理由+高风险监督日志）；或唱标录入起算确认时限、超时自动视为确认并告警。

### P1-2 价格公式缺最高限价：生成 400 + EVALUATING 配置锁定 + 前端误导文案，三重合围
- **证据**：`generateEvaluationResults` 400 CEILING_PRICE_REQUIRED（`bid-evaluation-results.service.ts:348-354`）；`updatePriceConfig` EVALUATING 锁定（`bid.service.ts:4188-4191`）；前端预警文案引导去 :3005 设限价但该操作必撞 409（`bid-portal evaluation-view.tsx:1345-1349`）；`startEvaluation` G9 不预检该组合（`bid.service.ts:2095`）。
- **场景**：带激活公式（基准价偏离法）但漏设限价的项目，专家全部评完后点生成 → 400 → 按提示去改配置 → 409 → 死局。
- **修复建议**：startEvaluation 增同口径前置校验；允许 EVALUATING 期间仅补设缺失 ceilingPrice（不放开公式类型变更）；修正引导文案。

### P1-3 解密窗口过期后，「延长/重置/重组会话」恢复入口整体消失（纯前端渲染条件）
- **证据**：`opening-hall.tsx:822`（延长/暂停/恢复包在 `remaining > 0` 内）；`:1151`（RESET_PENDING 按钮 `!windowExpired`）；`:751-766`（组建会话按钮仅 `!session` 时渲染）；`:300-302` toast 却提示「请先延长窗口」。后端 `startOpeningInternal` 同阶段幂等更新可延长过期窗口（`bid.service.ts:1553,1670-1681` 只禁缩短）。
- **场景**：dual-v2 平台责任家待重置解密机会时窗口到期 → 三入口全无 → 只能错裁 BIDDER 或维持终局（供应商丧失本可恢复的投标）。
- **修复建议**：`:822` 的 `remaining > 0` 放宽为 OPENING 阶段即渲染。

### P1-4 前端「开标完成度」镜像未排除「待提交」名册行 → 启动评标伪阻塞 + 错位定性诱导
- **证据**：`opening-hall.tsx:393` / `evaluation-view.tsx:581-585` activeSuppliers 仅排「已撤回」；后端 `isSubmittedRow`（`bid.service.ts:1852-1870`）以 submitted 为准、显式排除未投递家——前端镜像滞后。连带：大厅对「待提交」行渲染解密按钮（`:1081`）、「全部解密」计数污染（`:363-366`）、窗口过期后「定性异常」按钮对未投标家可用（`:1120-1133`，后端 `acceptSupplierDanger` 亦不查投递态）→ 诱导把从未投标的供应商定性为解密异常（后端 H4 修复注释点名要杜绝的错位定性）。
- **场景**：邀请招标 5 受邀 3 投递 → 「完成开标」横幅永不出现、启动评标按钮禁用并误列未投标家；后端本可放行。
- **修复建议**：两处镜像加「已提交」过滤；未投递行隐藏行级操作按钮；定性按钮收口。

### P1-5 专家申报回避 → progress 分母不排回避供应商 → 永远无法确认报告（且跨项目锁签到窗口）
- **证据**：`submitScores` 拦截回避供应商评分 AVOIDANCE_CONFLICT（`expert.service.ts:1340-1350`）；`recomputeExpertProgress` 分母=全部活跃供应商不排 conflictedSupplierIds（`score-recalculate.helper.ts:15-25`）；`confirmReport` 要求 progress=100 + 全部活跃供应商 verified（`expert.service.ts:2201,2209-2221`）；UI 却鼓励「评审过程中可随时补充回避」（`expert-portal evaluate/[id]/page.tsx:1847`）。连锁：该专家跨项目评标窗口永开（`expert-room.util.ts:16-31` EXPERT_WINDOW_CONFLICT）→ 别的项目也无法签到。
- **场景**：专家评完 2/3 家后依法补报与第 3 家的利害冲突 → progress 卡 66% → 永不能核对/确认报告 → 全项目 EXPERT_REPORTS_NOT_CONFIRMED 死锁。自解仅剩清空回避申报（法律上不当）或流标。
- **修复建议**：recompute/verifyScoreReview/confirmReport 统一「可评集合 = 活跃 − 该专家回避集」；连带核对聚合计票口径。

### P1-6 供应商被多数票废标 → 未评分该家的专家 progress 分母不排 invalid → 同样永不 100%（前后端双实证）
- **证据**：后端 `recomputeExpertProgress` 不滤 `bidValidity`（同上 helper）；`verifyScoreReview`/`confirmReport` 活跃集合含废标家（`expert.service.ts:1861-1875,2209`）；官方聚合 activeSuppliers 却排除 invalid（`bid-evaluation-results.service.ts:182-184`）——口径分裂。前端整卡锁死（`evaluate/[id]/page.tsx:1275-1280` canScoreActiveSupplier 排 invalid、`:2060-2064` pointer-events-none、`:2344-2347` 提交禁用；平板 `:455-461/:997-1000` 同款）。
- **场景**：5 专家中 3 人早投「不通过」判废供应商 X → 其余 2 名未评分 X 的专家 UI 锁死、progress 卡 N-1/N → 项目无法生成结果。逃生口=废票专家改票（确认报告后须 host 逐人重开）或流标。
- **修复建议**：与 P1-5 同一修复点——「可评集合」单一来源化（活跃 − 回避 − 废标）；连带核对废标「严格过半」计票与去极值分母不把缺席票当否决票。

### P1-7 撤回后重投 = 服务端 500 死胡同（撤回删除 C_outer 本体，前端回显「已上传」诱导直接提交）
- **证据**：dual-v2 轨 sealedPath==asset.key（`supplier-portal.service.ts:1988`）；重投读该对象（`:1994` getObject → NoSuchKey → `:2003-2008` 清理后 rethrow 500）；撤回后事务清理删除该对象（`:3051-3062`）；提交页回读 withdrawn 行恢复文件引用并显示「已上传」（`supplier-portal-next submit/page.tsx:463-477,924-929`）。
- **场景**：截标前撤回改价 → 回提交页改价提交 → 反复 500 无「请重传」提示 → 憋到截标 → 该家缺席（连锁签到 quorum 不足）。
- **修复建议**：withdraw 不删 C_outer（或仅删备份件）；或 submitBid 预检对象存在性给明确 400；或前端检测 withdrawn 清引用并提示重传。

### P1-8 供应商解密卡可见性单点静默依赖 getOpeningRecord → 一次瞬时失败整卡消失零提示
- **证据**：`my-bids/[projectId]/opening-hall/page.tsx:170-171` 失败吞为 null → submitted=false → `opening-decrypt-card.tsx:298` 整卡 return null；卡内 10s 轮询因 submitted=false 不启动；大厅页无定时刷新（仅 WS+手动刷新按钮）。
- **场景**：开标瞬间请求抖动失败 → 供应商无解密入口、无报错干等；主持人只能电话指挥其点「刷新」碰运气。
- **修复建议**：失败与「确无记录」区分（错误态+重试）；或解密卡自行探测 opening-package（其错误码体系完备）。

## 交叉洞察（修复时的系统性模式）
1. **「分母/许可集口径分裂」**：P1-5 与 P1-6 同根——progress 分母、verify 集合、确认闸与「实际可评集合（活跃−回避−废标）」分裂；同一修复点（可评集合单一来源化）一次清两项，须连带核对 aggregate-supplier-scores 计票与去极值分母。
2. **「状态变更无广播」**：延期、口令轮换、重开确认、签字闭环四处同病，专家/主持端全部依赖手动刷新；一次广播基建修复收益面大。
3. **窗口过期是放大器**：P1-3 与 quorum/RESET/DANGER 恢复链叠加成复合死路，先修 P1-3 收益最大。
