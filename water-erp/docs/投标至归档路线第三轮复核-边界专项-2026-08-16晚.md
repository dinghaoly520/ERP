## 二、新发现问题

### P1 级

**N1 解密并发抢占失效——`RUNNING` 在抢占条件内，双击双跑**（`bid.service.ts:1849-1852`）
- claim 写的是 `updateMany({ where: { id, decryptStatus: { in: ['PENDING','RUNNING'] } }, data: { decryptStatus: 'RUNNING' } })`。第二笔并发请求匹配 RUNNING→RUNNING 同样 count=1 通过。**事务内 SQL 实测**：同 where 两笔 UPDATE 均返回 `UPDATE 1`。
- 单测 `bid.service.spec.ts:456-461` mock 了 `count: 0`，掩盖了谓词错误（mock 验证不了真实 PG 行为）。
- 后果：并发双跑 → 监督/审计日志双份、WS 事件双发；phase③ 开标记录 findFirst-then-create **非原子**且 `BidOpeningRecord` 无 `(projectId, bidSupplierId)` 唯一约束 → 「解密即唱标」路径双跑可**双建开标记录**。
- 根因二义：RUNNING 纳入 where 本意是崩溃恢复（卡 RUNNING 可重试），但破坏了互斥。**修法**：新抢占只允许 `PENDING→RUNNING`；接管需附加条件（如 `updatedAt` 超过 N 秒的 RUNNING 才可重占）。

**N2 签字扫描件同格式重传必 500——`storeScan` 注释与实现相反**（`bid-sign-packet.service.ts:247-265`）
- 注释写「同 key 覆盖，无孤儿对象」，实际用 `fileAsset.create`，key 固定为 `bid-sign-packet/${projectId}/expert-${expertId}.${ext}`。同一专家同格式重传（现实场景：扫歪/漏页重传）→ 撞 `FileAsset.key @unique` → P2002 → 500。`unregister` 只重置状态不删 FileAsset 行，无自愈。
- P1-17（b333e27c）只修了主包 generate 的 upsert，漏了 storeScan 与回流包（见 N16）。

**N3 评标完整性快照：结果重生成时静默失败 + 指纹与内容分叉**（`bid.service.ts:3416-3443`）
- 每次生成结果都向固定 key `bid-evaluation-handover/${projectId}.json` `fileAsset.create`。首次成功；**重生成**（未闭环时合法操作，会删旧签字包）时 MinIO 对象已被新内容覆盖，但 create 撞唯一约束抛错被 `catch` 吞成一条日志「评标快照生成失败（不阻塞结果生成）」。
- 后果：FileAsset 行保留**旧 sha256/size** 指向**新内容**——完整性指纹失真；`verifyArchiveIntegrity` 若校验该资产将误判；旧下载链接内容被悄悄换掉。与 P1-17 同类，修法同为 upsert。

**N4 流标建议口径硬编码 3 家 + 已出结果不收口**（`apps/bid-portal/src/components/workspace/dispute-block.tsx:55-57,84,139`）
- `suggestAbort = !archived && validSuppliers.length < 3`：①不区分采购方式——**直接采购后端 `getMinBidders`=1，前端却按 <3 建议流标**（1~2 家有效即误报）；②已生成官方结果仍显示「建议流标」+「执行流标」（实测英雄项目结果已出、横幅仍在）；③confirm 文案不提示「已存在官方评标结果」；④后端 `abortBidProject`（`bid.service.ts:959`）不检查结果状态——有结果的 EVALUATING 项目可被一键流标且无复核。
- 同根：家数口径三处不一致——开标准备 checklist（`:1150`）数 **BidSupplier 行数（含受邀未投递）**、启动评标（`:1442`）数**解密成功家数**、流标建议（前端）数**解密成功+未撤回+未废标**。开标闸门放行的项目可能被启动评标闸门拦死（出口只剩流标）。

### P2 级

**N5 `reopenFromAborted` 重启项目继承已过期时间**（`bid.service.ts:1046-1048`）：原样复制 `openTime/deadline/downloadDeadline`——流标主因就是截标已过，新项目（DOWNLOAD）一出生即过截标，供应商立即 DEADLINE_PASSED。须改写为「now+正窗口」并提示重新设定时间（P0-5 同类残余）。

**N6 RSVP 过期文案「15分钟」与实际 TTL 2 小时不符**（`expert.controller.ts:160` 报错文案、`expert-admin.service.ts:911` 注释同样写 15 分钟；实际 `EXPERT_RSVP_TTL_HOURS` 默认 '2'，`expert-admin.service.ts:43`）。另外 2h TTL 本身对专家现实响应时间偏紧，过期后须重新进抽取向导步骤 6 才能重生成链接（`prersvpLinks`）。

**N7 专家婉拒/过期后的候补递补路径不一致**：公开 RSVP 链接婉拒 → 自动递补（`expert.controller.ts:173`）✓；管理员通道 `declineInvitation`（`expert-admin.service.ts:1055`，注释声称「自动递补候补」但 `promoted` 恒 null）与 `getProjectInvitations` 过期清扫（`:912-920` 置 declined）均**不递补** → 评委缺员只能靠人工发现。

**N8 「评分进度 50%」与「报告确认 3/3」同屏矛盾 + AI 卡片对存量项目永久等待**（实测英雄项目）：进度卡 50% 评分进行中、报告卡 3/3、可生成结果=是三者互斥矛盾（进度分母口径未随 ⑧ 修复对齐全部项目形态）；AI 辅助评标卡停在「评标已启动，等待分析任务创建…」——种子/早于该特性创建的项目无 AiBidAnalysisTask 且无补建路径，文案误导现场。

## 四、没有考虑到的边界情况（按环节）

**投递**：客户端倒计时用本地时钟、服务端 `Date.now()` 权威，无时钟偏移提示；临时供应商评标期过期的处置仅监督日志告警（R-2），无强制动作。

**抽取**：正选+候补全部婉拒/过期（`allDeclined` 有 flag）后的决策指引缺失（重抽？顺延开标？）；专家同名 username 撞车（[username,role] 复合唯一在 expert 角色内不防同名）。

**开标**：解密 phase①②之间进程崩溃/DB 抖动 → 行卡 RUNNING（靠 claim 含 RUNNING 才能重试恢复——与 N1 同根因，窗口关闭后只能走异常定性）；**OPENING 阶段流标的 UI 入口归属未定义**（API 合法、:3005 口径只写「开标前」、:3007 只写「评标中」，解密后家数不足时两端口径都没提谁操作）；解密窗口到期已修（P1-1 定性通道 ✓）。

**评标/签字**：闭环后发现扫描件漏传——上传通道随闭环全锁死，无解锁/补传通道（「管理员通道」文案无实现）；报告确认后撤销（unconfirmReport）与已签字状态的联动未定义；重生成→旧签字包失效联动 ✓ 但旧评标快照指纹分叉（N3）。

**归档后**：中标公示发布纯人工、公示期异议无流程承载；中标通知书 `deliverAwardLetter`（`bid.service.ts:4251`）存在但未在本轮覆盖。

**运维**：ai-bid worker 与主 API 分进程的「改码不重启=旧行为」风险持续（今晨已实证一次旧 dist 在跑）。
