## 二、逻辑正确性（按业务域）

### 2.1 投标域（A-87/88/89/90/94/98/100/101 + P0 A-143）

- **A-143 澄清在线答复（P0）**：供应商答复走「canonical → U盾签名 → 服务端验签 → TOCTOU 条件 updateMany」范式，实测三次复用零缺陷。
- **A-89 PDF 版式强制**：双层防线（accept 过滤 + 加密前 JS 守卫）+ 后端投递扩展断言（`.enc` 剥离后 `pdf|zip|rar`）。**zip/rar 裁决正确**：计划全局约束「整包维持允许」是唯一自洽解，Office-in-zip 属既定接受面（已在报告披露）。
- **A-87 要点端点**：发布即入队（幂等闸强化为「requirements 存在且无 PENDING bidderResult」——经独立核验为必要：字面闸会饿死 bidder 分析全链）；终审修复波补齐**邀请制名册门控**（非 OPEN 含无文档情形 → NOT_INVITED，PENDING/READY 双态零泄漏）。
- 逻辑亮点：`ensureTenderAnalysis` 三调用点（发布/启动评标/rerun force）单一来源，F7+确定性 jobId 至多一个在途任务。

### 2.2 开标域（A-106~114 + 波3 A-109/111）

- **A-109 quorum 闸**：四解密入口统一前置（解密窗口校验后、任何状态突变前），无 RUNNING 楔可能（单测断言 updateMany 零调用）。
- **A-111 decryptedAt 生命周期封闭**：2 处 SUCCESS 终局写、4 处重置清空、外层解密不触碰——grep 级清点实证；旧轨抢占要求 PENDING，陈旧时间戳不可达。
- **A-114 开标确认电子签名（波2）**：canonical 含 purpose 防交叉、单端点双语义（确认/补签）、主持端剥壳。

### 2.3 评标域（A-129/132/136/151/152 + P0 A-153）

- **A-152 电子签名（本批最重）**：四路一致性全部实证——esign 事务原子抢占（updateMany where PENDING）↔ 闭环共享 util 双路等价（diff 级）↔ 重生成 Prisma.DbNull 清签 ↔ 回流包/归档链/getStatus 三处同口径剥壳。**无客户端载荷信任面**（POST 只收 signature，canonical 由 DB 现值重建）。TOCTOU（generate 竞态）经终审修复波在锁内重读 sha256 比对（ESIGN_PACKET_MISMATCH）。unregister 电子签名守卫（拒优于清）封死陈旧签名进归档链的最后入口。
- **A-151 附注**：十节恒等变换经逐字节回归锁定（含末签尾部）；notes 缺省/null 归一（清空亦日志）在修复轮补齐。
- **A-129 配额过滤**：未填不过滤（条件展开，键真不出现）+ 多值并集；merit_best 的 D/E 履职过滤与新档案等级 DB 级过滤正交叠加，无碰撞。
- **A-132 分工**：DTO @IsIn + service 双白名单、名册校验、partial 语义（undefined=不清空）前后端闭环。

### 2.4 保证金链（A-102/104/105）

- 台账登记幂等（projectId+supplierName 唯一键）+ 监督日志留痕；四维比对引擎（金额/到账/支付形式/凭证，hasVoucher 三态）前后端共用单一实现。
- **A-105 pending 谓词**终审统一为共享 util（`已提交+未退还+无不予退还理由`）三处调用——修复波落地并补行为用例。

## 四、代码美观 / 一致性

**好的方面**（评审高频 Strengths 汇总）：
- 范式复用纪律强：签名四件套（canonical→PIN→verify→归档）三次复用零漂移；`pendingBondReturnWhere`/`getMinBiddersForMethod`/`REPORT_NOTE_SECTIONS` 等单一来源导出；
- 提交卫生优秀：55 个提交全部窄提交、显式路径 add、信息结构统一（`feat(p1-waveN): 检测项——要点`），无夹带（多轮 `git show --stat` 核验）；
- 防御性编程意识好：service 层双白名单、`?? []` 归一、`.catch` 与 try/catch 边界清晰、`$transaction` mock 直通等测试基建惯用法一致。

**待改进（Minor）**：
1. `bid.service.ts`（~6000 行）、`expert-admin.service.ts`（~2900 行）持续膨胀——P1 每波都在追加方法而非拆分；建议后续按域拆模块（签字包/保证金/评标结果已具备独立 service 的天然边界）。
2. 个别「测试精度」nit：`not.objectContaining({key: expect.anything()})` 无法区分键缺失与 undefined（Prisma 语义等价）；`stringContaining` vs 全字匹配。
3. 跨门户错误码分叉：`SM2_PUBLIC_KEY_INVALID`（专家）vs `INVALID_PUBLIC_KEY`（供应商）——同语义两码，建议统一映射层。
4. 监督日志留痕风格不一：`.catch(()=>{})` 静默 vs 邻居 `logger.warn`（A-151/A-105 继承仓内旧风格）。

## 五、UI 适配 / 设计系统符合度

**本轮程序化核验**：
- **令牌一致性**：P1 触碰的 7 个前端文件 grep 审计——新增样式全部使用 `var(--*)`/`oklch()` 令牌派生；仅有的 4 处硬编码 hex（`#c00a6b` 等）经 `git log -S` 证实为 2026-08-20 **存量**（阶段色板），非 P1 引入；`#b7791f` 为 `var(--warning, fallback)` 兜底写法（合规）。
- **徽标本证**：电子签名徽标计算样式 `oklch(0.71 0.11 164 / 0.1)`（success 令牌色相）+ 全圆角胶囊 + 10px——与组长/分工徽标几何完全一致（T5/T13 评审同款核验）。
- **表格适配**：:3007 签字专家表（6 列）位于 overflow-x-auto 容器（cgzxui 全表惯例），窄视口横向滚动安全；解密表 7 列同容器。
- **卡片体系**：供应商要点卡落位 overview/content 卡族之间（ov-* 类族）；折叠用原生 details/summary 零 JS 态——符合「信息密度优先」原则。
- **弹窗规范**：报告附注/签字登记/合同逐家退还弹窗均沿用各自门户 dialog 底板（exp-dialog / SpDialog / cgzxui fixed 层），Esc/遮罩/busy 锁行为与存量一致（逐任务评审核验）。
- **四态完备**：要点卡（loading/PENDING+重试/READY/组空）、签署区块（等待包/无证书/可签/已完成）——无假数据兜底，符合仓库「真实数据/加载/空态」铁律。

**Minor（UI 面遗留）**：
1. 要点卡网络错误折进 PENDING 空态（文案略不准；toast+重试兜底）；
2. 专家门户 report 步骤仅桌面端（平板无电子签署入口——设计决策：平板仅评分，已文档化）；
3. 台账面板/要点卡未在 375px 手机宽度专项验证（目标用户为桌面办公场景，风险低）；
4. 存量阶段色板 hex（见上）建议后续收敛到令牌。
