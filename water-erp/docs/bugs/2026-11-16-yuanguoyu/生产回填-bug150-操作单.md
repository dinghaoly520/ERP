# 生产回填操作单 · bug#150 文件名 latin1 mojibake（后端机 10.60.14.14 执行）

> **执行环境**：后端服务器 10.60.14.14（root 可操作，先例=日常部署通道）；生产金仓 10.60.1.10 本机网络不通、DBA 通道仅必要时启用。
> **病理**：multer 2.2/busboy ^1.6.0 栈 multipart `filename=` 恒以 latin1 形态交付，浏览器原始 UTF-8 中文文件名被单次误读（`采购需求申请表` → `éè´­éæ±è¯·è¡¨`）。运行时已换条件式归一（`common/filename-encoding.util.ts`），本单只回填**历史存量行**。
> **工具**：仓库脚本 `apps/api/scripts/fix-filename-mojibake.ts`（2026-11-16 bug#150 扩面版，三表：`TenderClarificationDoc.title`〔本票可见面〕/ `FileAsset.originalName`〔dual-v3 标书获取面既有欠账一并收口〕/ `Attachment.fileName`〔PMI/谈判轨读端〕）。判定=条件式三闸（含>U+00FF 不动／纯 ASCII 不动／高位字节且回转无 U+FFFD 无控制符才修），写入条件 updateMany 幂等。
>
> ⚠️ **为什么不在金仓上写 SQL 直转**：金仓缺 `$libdir/utf8_interconversion_iso8859_1` 转换库，`convert_to/convert(x,'LATIN1',…)` 全族实测（2026-11-16 dev 金仓同版本）直接报 `could not access file` 不可用；字节级 SQL 重构易错不走。**唯一权威路径=跑仓库同一把尺子（编译件入 api 容器，容器内 DATABASE_URL 已指金仓）**。

过目要点：`→` 右侧应为可读中文文件名。右侧仍是乱码的行分两种（2026-11-16 评审二轮口径）：
- 含 U+FFFD/不可见控制符 = 双重损坏行（信息已毁），谓词不会纳入；若竟出现在清单即止步回报。
- 不含上述字符 = 双重编码行（一次回转只到中间态、不毁值）——**再跑一轮第四步 --execute 即收敛为可读原名**，或按附注人工定名单改；不属于「止步回报」情形。
另：已归档项目的 Attachment 行会被脚本自动跳过（输出尾部有跳过计数）——镜像配对保护，勿手工补改 DB 名。
