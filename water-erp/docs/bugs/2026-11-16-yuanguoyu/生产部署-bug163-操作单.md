> **执行环境**：前端机 10.10.7.20（门户镜像构建，日常部署通道）；后端 B 机 10.60.14.14（root，recreate api 容器）。**零网络部门依赖**（不动任何 nginx）。
> **基线 commit**：`0384e1ed6`（含本票修复；自该 commit 起的 main 均已包含）。
>
> **根因回顾**（定谳依据见队列行与浏览器/探针证据）：生产门户 vhost nginx 无 `/socket.io` 反代（请求落门户 Next 应用 → 404/308）+ engine.io 6.6.8 默认只认带尾斜杠（生产前端 bundle 依赖树旧、socket.io-client<4.6 不补斜杠）——双层错位。修复=API 三网关 `addTrailingSlash:false` 双形式兼容 + 四门户（supplier/web/bid/expert）Next 层自代理 `/socket.io`。

## 第一步：构建（前端机 10.10.7.20）

按日常部署通道从当前 main 构建 **5 个镜像**：

| 镜像 | 内容 | 必含改动 |
|---|---|---|
| api | NestJS | 三网关 addTrailingSlash:false（bid/notifications/chat） |
| supplier-portal-next | 门户 | proxy.ts /socket.io 转发分支 |
| web | 门户 | proxy.ts 分支 + 60s 超时档 |
| bid-portal | 门户 | next.config rewrites ×2 + proxy.ts 放行 |
| expert-portal | 门户 | next.config rewrites ×2 + proxy.ts 放行 |

> 门户重建顺带收口前端 bundle 依赖漂移（socket.io-client 回到 4.8.x 锁定版）——#114/#115「测于旧码」疑云同窗解除的可能，部署后一并复验。

## 附注

- **传输形态**：经门户代理的 WS 升级请求不适用（Next 层不转发 Upgrade）——socket.io 自动留**长轮询**（近实时，ping 25s 包裹）。若将来网络部门为门户 vhost 配 `/socket.io` location（无尾斜杠前缀 + Upgrade/Connection 头透传）或启用 api 子域 vhost，无需改码即自动升级回真 WS。
