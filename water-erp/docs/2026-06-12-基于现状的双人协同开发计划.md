> 生成日期：2026-06-12  
> 适用范围：`water-erp/` 当前 pnpm monorepo 主项目

## 2. 双人协作总体分工

### 2.1 分工原则

1. **按功能域闭环分工**：不要一个人只写前端、另一个人只写后端；否则 API 契约等待和联调成本会很高。
2. **共享层集中主责**：Prisma schema、`packages/config`、`packages/shared`、认证、上传返回结构等必须有主责人。
3. **P0 风险优先**：先处理权限、状态机、文件上传、评分隔离、公告动态化，再做界面美化和大模块扩展。
4. **小步 PR**：每个 PR 尽量只覆盖一个业务目标，尤其数据库迁移和共享类型变更要独立提交。
5. **功能验收先于样式完善**：页面视觉升级可以并行，但不得掩盖业务规则缺失。

### 2.2 两人职责划分

| 人员 | 主责方向 | 负责功能域 | 典型文件范围 |
|---|---|---|---|
| 开发者 A | 核心交易链 | 采购管理、招标项目、开标、评标、专家、AI、归档、管理端核心工作台 | `apps/api/src/bid`、`apps/api/src/expert`、`apps/api/src/ai`、拟新增 `apps/api/src/procurement`、`apps/web/src/app/(dashboard)/bid`、`apps/web/src/app/(dashboard)/procurement`、`apps/web/src/app/(dashboard)/expert`、`apps/expert-portal` |
| 开发者 B | 供应商生态与平台运营 | 供应商管理、供应商门户、公告、通知、上传、公开门户、评价、商城 | `apps/api/src/supplier`、`apps/api/src/supplier-portal`、`apps/api/src/announcement`、`apps/api/src/notification`、`apps/api/src/upload`、拟新增 `apps/api/src/mall`、拟新增 / 拆分 `apps/api/src/evaluation`、`apps/web/src/app/(dashboard)/supplier`、`apps/web/src/app/(dashboard)/notice`、`apps/web/src/app/(dashboard)/evaluation`、`apps/web/src/app/(dashboard)/mall`、`apps/supplier-portal`、`apps/public-portal`、`apps/mall` |

### 2.3 共享资源主责建议

| 共享资源 | 建议主责 | 协作规则 |
|---|---|---|
| Prisma schema 与迁移 | A 主责，B 提交相关模型 PR | 新增模型 / 关系前先写迁移说明；同一天避免两人同时改 schema |
| `packages/config` | A 主责 | 端口、URL、角色跳转统一从这里读取，不再硬编码 localhost 端口 |
| `packages/shared` | B 主责 | 状态枚举、接口类型、颜色映射逐步沉淀；新增后需构建 shared 包 |
| 认证与权限矩阵 | A 主责 | B 新增接口时必须套用统一角色策略 |
| 文件上传协议 | B 主责 | A 的招标文件、标书、归档文件也调用统一上传能力 |
| 通知服务 | B 主责 | A 在开标、评分、归档等节点调用通知服务，不自行复制通知逻辑 |
| 管理端 AppShell / 导航 | A 主责 | B 新增菜单项走小 PR，避免多人同时改布局文件 |
| UI 视觉规范 | B 主责 | 登录页、供应商门户、公开门户先统一；A 的业务页按规范落地 |

## 3. 按功能域开发计划

## 3.1 认证、权限与门户入口

### 当前状态

- 后端已有登录、注册、登出、`/auth/me`。
- Cookie JWT 已可用。
- 多门户登录后按角色跳转由 `ROLE_PORTAL` / `landingURL` 控制。
- 四端登录页存在，但视觉尚未完全统一，部分页面仍有测试账号提示。

### 主要问题

- 登录服务未严格校验 `isActive`，供应商待审核或停用状态可能产生权限边界问题。
- 登录失败状态码与测试预期存在不一致风险。
- 生产环境 JWT secret、Cookie secure、CSRF 策略需要明确。
- 许多业务接口仅要求登录，未按角色限制。

### 开发任务

| 优先级 | 任务 | 主责 | 交付物 |
|---|---|---|---|
| P0 | 登录失败统一抛 `UnauthorizedException`，测试同步 | A | 登录错误返回 401，e2e 通过 |
| P0 | 登录时校验用户激活状态与供应商状态策略 | A | 停用用户不能登录；待审核供应商可否登录需业务明确并实现对应限制 |
| P0 | 建立角色权限矩阵 | A | 文档 + `@Roles()` 落地到关键 Controller |
| P1 | Cookie 安全配置环境化 | A | dev / prod 不同 secure、sameSite、secret 校验 |
| P1 | 四端登录 UI 统一升级 | B 主责，A 配合 | 3002 / 3003 / 3004 / 3005 登录页统一风格，去除测试账号展示 |
| P2 | 统一门户入口 URL | B | 公开门户所有入口从配置生成，不再硬编码端口或局域网 IP |

### 验收标准

- 非授权角色不能调用管理端招标、供应商审核、专家评分、公告发布等接口。
- 被停用或黑名单的用户 / 供应商不能继续执行受限业务。
- 登录页视觉统一且不暴露测试账号。

## 3.2 招标项目、开标、评标与归档

### 当前状态

- 后端 `bid` 模块已支持项目 CRUD、阶段流转、供应商、开标会话、模拟解密、评分、澄清、监督日志、归档。
- 管理端已有 `/bid`、`/bid/open`、`/bid/evaluate`、`/bid/supervise`、`/bid/archive`。
- 数据模型已有 `BidProject`、`BidSupplier`、`BidOpeningSession`、`BidOpeningRecord`、`BidExpert`、`BidScoreItem`、`BidScoreRecord`、`BidClarification`、`BidSupervisionLog`、`BidArchiveItem`。

### 主要问题

- 管理接口权限过宽。
- 项目阶段流转、投标提交、开标解密、归档仍偏演示。
- `BidScoreRecord` 缺少数据库唯一约束，评分并发和重复提交风险较高。
- 开标记录、澄清仍有供应商名称弱关联。
- 归档 hash 为模拟值，不是真实文件摘要。

### 开发任务

| 优先级 | 任务 | 主责 | 交付物 |
|---|---|---|---|
| P0 | 补全 `bid` Controller 角色权限 | A | 供应商不能调用管理端开标 / 解密 / 归档接口；专家只能走专家端评分 |
| P0 | 固化项目生命周期状态机 | A | 明确 `DOWNLOAD → SUBMIT → OPENING → EVALUATING → ARCHIVED` 的入口、校验、错误提示 |
| P0 | 统一投标提交规则 | A 主责，B 配合 | 管理端和供应商端不能绕过供应商状态、截止时间、项目阶段 |
| P0 | 修复评分唯一性与供应商隔离 | A | `expertId + supplierId + scoreItemId` 唯一约束或等价事务逻辑；前后端评分按供应商隔离 |
| P1 | 完善开标解密状态机 | A | `PENDING / RUNNING / SUCCESS / DANGER` 状态可追踪，异常原因入库 |
| P1 | 监督日志自动化 | A | 关键操作自动写 `BidSupervisionLog`，监督端可实时或轮询查看 |
| P1 | 归档真实 hash 与确认规则 | A | 归档项绑定真实文件 / 文件 hash；未完成项不能标记完成归档 |
| P2 | WebSocket / SSE 倒计时与日志流 | A | 开标倒计时、解密状态、监督日志实时推送 |
| P2 | 评分异常 / 防串通检测 | A | 专家评分偏差过大时产生风险提示 |

### 验收标准

- 供应商从招标列表到提交标书、开标、评标、归档的主流程可端到端跑通。
- 错误阶段操作会被后端拒绝，而不是只在前端隐藏按钮。
- 专家对不同供应商评分不会互相覆盖。
- 归档数据可追溯到文件和操作日志。

## 5. API 与数据库协作规则

### 5.1 数据库迁移规则

1. 每次 schema 变更必须单独 PR。
2. PR 说明中必须列出：新增模型、修改字段、是否有数据迁移风险、回滚方式。
3. A 和 B 不要同时在长期分支改 `schema.prisma`；若必须同时改，先合并其中一方，再 rebase 另一方。
4. 迁移命名建议：

```text
add-procurement-models
add-file-assets
add-mall-models
link-bid-expert-user
add-score-unique-constraint
```

5. 修改 `packages/shared` 或 `packages/config` 后必须重新构建对应包：

```bash
pnpm --filter @water-erp/shared exec tsc -p tsconfig.json
pnpm --filter @water-erp/config exec tsc -p tsconfig.json
```

### 5.2 API 契约规则

统一响应建议：

```ts
type PageResult<T> = {
  items: T[];
  total: number;
  page: number;
  pageSize: number;
};

type ApiError = {
  error: string;
  code?: string;
  details?: unknown;
};
```

跨功能接口必须先确认契约，重点包括：

- 文件上传返回结构。
- 供应商投标提交 DTO。
- 开标解密状态 DTO。
- 专家批量评分 DTO。
- 公告发布和通知触发 DTO。
- 采购项目和招标项目关联 DTO。

## 8. 风险清单

| 风险 | 影响 | 优先级 | 应对 |
|---|---|---|---|
| 权限过宽 | 供应商或非专家可操作敏感接口 | P0 | 角色矩阵 + e2e 权限测试 |
| Prisma schema 冲突 | 两人同时改模型导致迁移冲突 | P0 | schema 单独 PR，错峰合并 |
| 文件上传仍是模拟 | 标书、资质、归档都无法真实验收 | P0 | 优先接 MinIO 和文件元数据 |

| 公告静态数据 | 管理端发布无法公开展示 | P0 | 公开门户切后端数据 |
| 供应商变更越权 | 可修改敏感字段 | P0 | 字段白名单和类型校验 |
| 路由顺序问题 | 静态接口被 `:id` 捕获 | P0 | 静态路由前置并加测试 |
| 端口文档不一致 | 登录跳转和协作误解 | P1 | 以 `packages/config` 为单一来源，更新文档 |
| UI 优先导致业务缺失 | 页面好看但不能验收 | P1 | 每个视觉任务绑定业务验收点 |

## 11. 最终建议

当前项目已经具备较完整的招采 ERP 雏形，最重要的下一步不是继续堆页面，而是把“演示型流程”升级成“可验收的业务闭环”：

1. **先补 P0 规则和安全**：权限、状态机、事务、字段白名单、评分唯一性。
2. **再补真实资料能力**：MinIO、文件元数据、下载权限、归档 hash。
3. **然后补门户体验**：供应商门户任务化、登录页统一、Dashboard 风险待办。
4. **最后扩展大模块**：采购合同、商城订单、AI 深度分析、实时推送。

两人最适合按“核心交易链 A + 供应商运营链 B”并行推进；共享层由一人主责、另一人 review，能最大限度减少冲突并保证功能闭环。
