## 二、发现清单（按严重度排序）

### P1-1 桌面自动保存缺「已提交过滤」——提交后草稿阴魂不散（误导性横幅）

- **现象**：自动保存把**全部** `scores`（含已提交的 9 条）整体写入草稿。专家提交评分后，任何一次后续修改都会把已提交分连同改动一起重新存为草稿——下一次进入页面横幅再次出现「有草稿」，专家误以为有未提交内容。
- **代码**：`apps/expert-portal/src/app/(app)/evaluate/[id]/page.tsx` L382-395 自动保存 effect——entries 仅判空，未过滤 `committedSupplierId` / 已提交键。
- **建议**：写入前剔除与已提交记录一致的条目（键 + 值同则不存）；全部一致时不写草稿。

### P1-2 进入「专家打分」步会**自动覆写**待恢复草稿——恢复草稿形同虚设

- **现象（实测复现）**：报告步存在带得分点的草稿（savedAt `1789109654104` 未变）→ 切到「专家打分」步 3.5s 后，localStorage 草稿被自动保存覆写（savedAt `1789109690722`），价格项**得分点数据丢失**。此时点「恢复草稿」只能恢复出已提交分（横幅时间戳是挂载时的旧快照，还显示"有 N 项未提交"）——toast 提示"已恢复 N 项"但内容已不完整，**误导专家以为恢复了全部**。
- **根因**：同一自动保存 effect 在 `step === 'scoring'` 且 entries 非空时无条件触发（进入打分步即触发，含已提交项——与 P1-1 同源）；横幅只在挂载时读取一次（L356-378），不随草稿变化刷新。
- **建议**：① 恢复草稿前自动保存需挂起/或被恢复合并覆盖；② 恢复时以服务端最新草稿为准重新拉取而非用挂载快照；③ 恢复后 toast 应如实显示实际恢复条目数。

### P1-3 部分得分点映射 → 通过制卡死「不通过」，再勾选也无法恢复

- **现象（草稿证据实证）**：核对区就地打分时 `points` 以 `cur.points ?? {}` 起种子，只写入**改过的那个点**；切到打分 tab 后，通过制重算 `passed = 全部客观点 checked` 把缺失点当未勾选 → `passed` 恒为 false。实测草稿：`{"score":0,"reason":"","passed":false,"points":{"cmtvfilge000ouu6xiblnrr7k":{"checked":true,"awardedScore":0}}}`——单条目映射，其余 7 个点缺失。此时重新勾选全部点也不能使 `passed` 恢复 true（缺失点永远缺）。逃生口存在（逐一重勾**全部**点可重建完整映射）但不可发现。
- **代码**：`(app)/evaluate/[id]/page.tsx` L426-457（`handlePointChange` 部分映射种子）；L1748-1755（`objectivePts.every(p => points[p.id]?.checked === true)`）。
- **注**：平板自己的 onChange 用 `cur.points ?? pfValueMap`（完整回退），平板内循环安全；部分映射只经**核对区就地打分**或**草稿恢复**进入。
- **建议**：核对区/恢复路径统一用 `cur.points ?? pfValueMap` 完整种子；重算 `passed` 时对缺失点按提交值或默认值回退。

### P1-4 平板防误触确认**首次点击被绕过**

- **现象（实测）**：对回退渲染（无已存 points）的已提交得分点，**第一次**点击直接生效、不弹确认；**第二次**点击才出现「取消/确认修改」弹窗（实测弹窗出现、确认后恢复 ✓通过）。
- **代码**：`(tablet)/tablet/evaluate/[id]/page.tsx` makeTabletOnChange 拦截条件 `cur?.points?.[pid]` 存在（旧值）才判定为修改——首次点击时旧值不存在 → 视为新增 → 绕过确认。
- **建议**：把「回退渲染的已提交值」也纳入旧值判定（`cur.points?.[pid] ?? pfValueMap[pid]`），首点即弹确认。

### P2-1 全局「去打分平板」按钮不带评分项定位 → 平板无闪烁定位

- **现象**：顶部全局「去打分平板」只 POST `{supplierId}`（无 `scoreItemId`），平板只能切供应商，无法像核对区**逐项**「去打分」那样闪烁定位到具体评分项（V12 已验证逐项路径完整可用）。
- **代码**：`requirement-compare-panel.tsx` L677 `onGoScoring()` 无 target；平板 L284-317 仅当 `hint.scoreItemId` 存在才滚动+闪烁。
- **建议**：全局按钮定位到「第一个有问题的评分项」，或弹出评分项选择器再发 hint。

### P2-2 报告确认后草稿**永远无法丢弃**（SCORE_LOCKED 400）

- **现象（本次清理实测）**：`reportConfirmed=true` 后，POST score-draft（含丢弃用的 `{scores:{}}`）返回 400 `SCORE_LOCKED`。若确认前遗留草稿，确认后横幅持续出现而「丢弃」按钮点了报错——**无任何 UI 出路**（本次清理靠直接改库完成）。
- **代码**：`expert.service.ts` L2007-2009。
- **建议**：① 报告确认时服务端顺带清空草稿；或 ② 丢弃端点对 `{scores:{}}` 空载豁免锁定。

### P2-3 PRICE 项得分点清单与已提交分口径不一致（无 pointDecisions 时）

- **现象**：价格评分已提交 99.3/100，但打分 tab 的得分点清单渲染为**未勾选 0/100**——已提交价格分未分解为 pointDecision，编辑态与滚动总分口径不一致；若专家此时动得分点，会按 0 起算重算（有覆盖风险）。
- **建议**：无 pointDecisions 时，得分点清单按已提交分回显（全额勾选/按公式分摊），或明确标注「已提交分未分解」并禁止点级编辑。

### P3-1 通过制项 fullScore=0 时 spinbutton 显示「0 / 0」无意义噪声

- **现象**：资格审查（通过制，满分 0）的得分点行 spinbutton 显示「0 / 0」，纯视觉噪声。
- **建议**：通过制项隐藏 spinbutton，仅显示 ✓ 通过 / ✗ 不通过。

### P3-2 平板确认弹窗文案「从 0 分改为 0 分」无意义

- **现象**：通过制项（分数恒 0）修改时弹窗文案为「从 0 分改为 0 分」，专家看不出改了什么。
- **代码**：`(tablet)/tablet/evaluate/[id]/page.tsx` L788-805——`oldVal.checked && !newVal.checked ? '取消勾选' : \`从 ${oldVal.awardedScore} 分改为 ${newVal.awardedScore} 分\``，勾选→取消勾选方向的文案是对的，反向（分数变化）对 0 分项无效。
- **建议**：通过制项文案改为「通过 → 不通过」「不通过 → 通过」。

## 四、结论

同步性整体扎实：核对区↔打分同屏同步、供应商隔离、跨设备聚焦提示富路径（切供应商+闪烁定位+得分点预选+ACK 回执）全链路可用。易用性短板集中在**草稿生命周期**（P1-1/P1-2/P2-2 同源：自动保存无已提交过滤 + 锁定后无出路）与**部分得分点映射**（P1-3/P1-4）两簇，均会造成专家误判或数据覆盖风险，建议优先修复 P1-1 ~ P1-4。
