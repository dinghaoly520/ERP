# 生产部署服务与配置遗漏清单（2026-10-28）

依据：本机金仓主栈实测盘点 + `backend/` 部署套现状（六服务：api/redis/minio/migrate/seed/外部金仓）对照。
用户裁定：**生产目标国产化（金仓）**；生产机器**麒麟 OS、纯 CPU**。

## 一、缺的容器服务

### 1. ai-worker（AI 投标分析进程）——必补，否则 AI 分析全线停摆

不加它：任务入队后无人消费，卡片永远「逐家分析中」/失败（本机 10-23 事故的生产版）。

```yaml
  ai-worker:
    <<: *infra-common                      # restart: unless-stopped（死了自动拉起）
    image: water-erp-api:1.0.0             # 同 api 镜像，零新构建
    container_name: water-erp-be-ai-worker
    working_dir: /app/apps/api
    command: ["node", "dist/ai-bid-analysis-worker.js"]
    env_file: .env.backend
    environment:
      NODE_ENV: production
      DATABASE_URL: postgresql://<金仓用户>:<转义密码>@<金仓地址>:54321/<库名>?connection_limit=10
      DIRECT_URL:  postgresql://<金仓用户>:<转义密码>@<金仓地址>:54321/<库名>
      REDIS_URL: redis://redis:6379
    depends_on:
      redis:   { condition: service_healthy }
      minio:   { condition: service_started }
      migrate: { condition: service_completed_successfully }
```

不需要 healthcheck（无 HTTP 端口，进程死即容器退，restart 接管）；`backend.yml` 与 `backend-run.yml` 两份都要加。

### 2. pgvector 实例（语义检索向量库）——要语义审查就得有

金仓不带 pgvector（扩展清单已核：仅金仓系统扩展），dev 架构=金仓管业务 + 独立 pgvector @5434 管向量（`water-erp-pgvector` 容器，DocumentChunk 62 行在用）。生产同构：

- compose 加 pgvector 服务（`pgvector/pgvector:pg16`，数据卷持久化），或指向已部署实例
- `VECTOR_DATABASE_URL=postgresql://…@<pgvector地址>:5432/water_erp`、`PGVECTOR_ENABLED=true` 两行必配；不配则回退连金仓主库 → 报 vector 列不存在
- **首次上线要把向量数据初始化**（知识库分块重建：EmbeddingService 向量化写入）

### 3. bge-m3 向量服务——纯 CPU 麒麟方案（最易漏）

约束：麒麟 V10、无 GPU、大概率内网（镜像需离线导入）。vLLM 不支持纯 CPU，dev 借用的 :8003 方案不可搬。

| 候选 | 说明 |
|---|---|
| Xinference | OpenAI `/v1/embeddings` 兼容，CPU 跑 BGE 类成熟，Web 界面便于运维 |
| infinity（michaelfeil/infinity） | 轻量 OpenAI 兼容 embed server，ONNX CPU 后端，单容器即可 |

注意：
- **架构匹配**：先确认机器是海光 x86 还是鲲鹏/飞腾 ARM，镜像 tag 选对应架构，离线 `docker save/load` 导入
- **模型名对齐**：起服务时定 served model 名（如 `bge-m3`），`.env` 写 `EMBEDDING_BASE_URL=http://<地址>/v1` + `EMBEDDING_MODEL=bge-m3`——避免 dev「全路径 model id」的坑（vLLM 未带 served-model-name 时 model 即路径）
- bge-m3 权重文件（约 2GB）需随行拷贝；dense 输出 1024 维，与现网 DocumentChunk 一致
- 验收：`curl <地址>/v1/embeddings -d '{"model":"bge-m3","input":"测试"}'` 返回 1024 维向量
- 无此服务时语义审查静默残废（写入/查询两侧向量化全失败），**必须上线前验**

### 4. OCR 服务——已规划分机，上线验活即可

`OCR_SERVICE_URL=http://10.60.14.14:8100`（分机部署，CLAUDE.md 生产口径）。上线前 curl `/health` 验活；该机同为麒麟 CPU 时按 `services/ocr/start.sh` 离线装依赖（rapidocr 纯 CPU 可跑）。

## 二、缺的 env 配置（.env.backend）

| 项 | 值 | 说明 |
|---|---|---|
| DEEPSEEK_MODEL | `deepseek-flash` | **勿带旧值 `v4.1-flash`（10-28 事故根因，DeepSeek 现仅认 deepseek-flash / deepseek-v4-pro）** |
| DEEPSEEK_API_KEY | 生产密钥 | worker 分析+水叮当共用 |
| KMS_SECRET | ≥32 字符 | worker 解投标密文必需，缺则各家分析报 KMS 未配置 |
| FIELD_ENC_SECRET（+OLD） | ≥32 字符 | PII 国密加密，生产缺失拒绝启动 |
| JWT_SECRET | ≥32 字符 | 生产硬闸 |
| COOKIE_DOMAIN / API_ORIGIN / CORS_ORIGINS / TRUST_PROXY | `.scsfjt.com` 等 | 域名部署四件套（spec 1ee9e4f2） |
| PGVECTOR_ENABLED / VECTOR_DATABASE_URL | true + 指向 §一.2 | 见上 |
| EMBEDDING_BASE_URL / EMBEDDING_MODEL | 指向 §一.3 | 见上 |
| OCR_SERVICE_URL | 10.60.14.14:8100 | 见上 |
| SMS_PROVIDER + RYD_* | rongyida | 通知短信现役通道；密钥分发走 `env/apply-sms-env.sh`（密钥件口令走非 git 渠道） |
| BID_DUAL_ENVELOPE / UPLOAD_SERVER_SEAL | true | 双信封+上传密封（应急回退开关留档） |
| CERT_CHAIN_ENFORCE / TRUSTED_CA_DIR / CERT_POP_REQUIRED | 按 CA 方案 | 真 CA 根证书落 TRUSTED_CA_DIR 才启用链闸 |

## 三、数据与初始化

1. **金仓三步（DBA，一次性）**：实例参数 → 建库建用户装扩展 → 密码 URL 转义（教程《金仓生产部署-数据库初始化教程》§1-3）
2. **迁移**：`scripts/db-migrate-kingbase.sh`（教程 §4；注意 Prisma CLI 读 .env 覆盖 shell 传参的坑，先改 .env 本体）
3. **管理方加密证书首导**：`POST /api/bid/admin-cert/generate`（ADMIN_KEYSTORE_DIR 目录**纳入备份**——丢了历史信封外层永久不可解，见双信封生产启用前清单）
4. `.data/supervision/` 监督签名私钥目录纳入备份（同上）
5. MinIO 桶：API 启动时 `StorageService.ensureBucket` 自建，无需手工

## 四、上线验收

1. `docker compose logs ai-worker` → 「AI 投标分析 worker 已启动（消费 tender/bidder 队列）」
2. 管理端对一项目点「重新分析」→ `docker exec water-erp-be-redis redis-cli ZCARD "bull:ai-bidder-processing:completed"` 增长
3. 招标文件审查页发起一次语义审查 → 无 vector 报错、返回结果
4. `4001/api/health` 三项 ok（database/redis）
