> **审计日期**: 2026-08-10（v2 — 含法律法规交叉验证）
> **审计范围**: 从专家/开标管理员登录 → 身份核验 → 开标(解密/唱标/异议/交流) → 评标(打分/表决/废标/澄清) → 报告生成 → 数据打包流转至 :3005 → 归档

## 🔴 高严重度（P0 — 影响合规性/数据完整性/功能可用性）

### 1. BidInvalidBid 的 FK 约束导致废标功能运行时必崩

**文件**: `bid.service.ts:3744-3748`（resolveExpertDispute）、`bid.service.ts:3808-3812`（manualMarkInvalidBid）、`schema.prisma` BidInvalidBid 模型

BidInvalidBid 表有 FK 约束 `scoreItemId → BidScoreItem.id`（migration `20260716011753` + Prisma schema 均确认，为 `onDelete: Cascade` 强制关系）。但代码中：
```ts
scoreItemId: '__dispute__'   // resolveExpertDispute（line 3745）
scoreItemId: '__manual__'    // manualMarkInvalidBid（line 3809）
```
这两个值在 BidScoreItem 表中不存在。**首次创建（upsert 的 create 分支）必然触发 FK 约束违反，运行时崩溃。** 专家异议裁决带废标联动和手动标记废标功能从未成功执行过。

### 2. 管理端代评（submitScore）绕过专家五步核验链

**文件**: `bid.service.ts:2930-2955` vs `expert.service.ts:995-997`

| 检查项 | 专家自评 | 管理端代评 |
|--------|---------|-----------|
| `signedIn` | ✅ | ❌ |
| `avoidanceConfirmed` | ✅ | ❌ |
| `aiConsentConfirmed` | ✅ | ❌ |
| `confidentialityAgreed` | ✅ | ❌ |
| `disciplineAgreed` | ✅ | ❌ |

管理端代评允许在专家**未完成签到、回避确认、AI声明、保密承诺、评标纪律**的情况下代表该专家提交评分。违反《暂行规定》第十三条（成员应"客观、公正地履行职责"）和评审专家独立评审行为准则。

### 3. 管理端代评不写评分修订历史 + 不重置核对状态

**文件**: `bid.service.ts:3026-3060` vs `expert.service.ts:1186-1198`、`expert.service.ts:1243-1251`

- **不写 History 快照**：专家自评路径在覆盖前写入 `BidScoreRecordHistory`（防篡改取证），管理端代评**不写**。`getScoreHistory`（bid.service.ts:3114）查到的历史完全不包含代评改分。
- **不重置 Review**：专家自评改分后 `BidScoreReview.status` 重置为 `'draft'`，强制重新核对。管理端代评**不重置**——专家的核对状态仍为 `'verified'`，但底层数据已变。专家可在不知情下基于过时核对状态确认报告。

### 4. 比例法价格分公式可产生超满分分数

**文件**: `price-formula.service.ts:138-141`

```ts
return (ceilingPrice / bidPrice) * maxScore;  // bidPrice < ceilingPrice 时 >maxScore
```
限价 100 万、报价 50 万、满分 30 分 → 得 60 分。最终结果 `Math.round(score * 10) / 10` 只做四舍五入不封顶。超满分的价格分直接扭曲总分排名，可能改变中标结果。

### 5. SMS_DEBUG_BYPASS=true 无生产环境守卫

**文件**: `verification.service.ts:158-167`、`apps/api/.env:6`

万能验证码 `"123456"` 可绕过所有专家短信身份核验。与 `simulateDanger`（有 `NODE_ENV === 'production'` 守卫）不同，SMS bypass **无任何生产环境保护**。`.env` 是唯一 env 文件且不区分环境。如果误带入生产，任何人知道专家用户名和密码即可冒充签到，违反《暂行规定》第十四条（评标保密义务）。

### 6. generateEvaluationResults 静默排除 EXCEPTION 供应商

**文件**: `bid.service.ts:2663-2664`

```ts
const activeSuppliers = project.suppliers.filter(
  s => s.decryptStatus === 'SUCCESS' && s.submitStatus !== '已撤回' && s.confirmStatus === 'CONFIRMED' && s.bidValidity !== 'invalid',
);
```
`assertOpeningDone` 允许 `confirmStatus === 'EXCEPTION'` 的供应商进入评标（line 1173），专家可对其完整评分，但 `generateEvaluationResults` 静默排除所有非 `CONFIRMED` 的供应商。EXCEPTION 供应商的所有评分数据在结果汇总中**被丢弃且无显式告警**。

### 7. 未裁决的专家异议不阻塞评标结果生成

**文件**: `bid.service.ts:2630-2645`

`generateEvaluationResults` 的闸门检查包括：阶段、所有专家确认报告、组长末签、多轮报价校验。但**完全没有检查是否有 `status='open'` 的 ExpertDispute**。组长提交异议后采购端未裁决时，只要所有专家确认报告且组长末签，评标结果即可生成——异议被悬置。

---

### 8. 解密事务内执行 MinIO 外部 I/O + 无行锁竞态

**文件**: `bid.service.ts:1562-1734`

两个问题叠加：
- **无 FOR UPDATE 行锁**：并发请求可同时读到 PENDING，都通过检查、都执行解密、都提交 SUCCESS。前端批量解密（`Promise.allSettled`）+ 快速连续点击加剧风险。重复创建开标记录（非 upsert）。
- **事务内执行 MinIO I/O**：DB 事务包裹了 `minioClient.getObject()` + `streamToBuffer()` + AES 解密 + SHA-256 校验。MinIO 慢/不可用时事务长时间不释放连接，pgbouncer 连接池可被耗尽。`decryptAllSuppliers` 串行调用 N 次含外部 I/O 的事务。

---

### 9. 事务内发射 WS 事件——提交前回调不一致窗口

**文件**: `bid.service.ts:1077-1083`（startOpeningInternal）、`bid.service.ts:1631,1635,1688,1692,1702,1730`（decryptSupplier）

在 `$transaction` 回调**内部**调用 `notifyStageChange`/`notifyDecryptStatus`/`notifySupervisionLog`。如果事务后续回滚，客户端已收到"阶段已变更/解密成功"事件，但 DB 实际未变更。对比：`openSubmission`（line 831）和 `startEvaluation`（line 1276）正确地将通知延迟到事务提交后。

---

### 10. claimActiveHost TOCTOU 竞态——无原子抢占

**文件**: `bid.service.ts:2238-2250`

先 `findUnique` 读取 `activeHostId`，检查后 `update` 覆写。两个主持人同时调用：都读到旧值，都通过检查，都覆写。**两个用户都收到 `{ claimed: true }`**，都认为自己拥有主持人控制权，同时操作开标大厅。对比：`checkIn`（line 246）和 `resolveOpeningDispute`（line 2484）正确使用原子 `updateMany` 抢占模式。

### 11. 流标三步流程非原子——部分失败导致不一致状态

**文件**: `apps/web/src/components/projects/bid-confirm/abort-dialog.tsx:31-58`

三步顺序执行：abort → createAnnouncement → archiveAll。步骤 1 成功但步骤 3 失败时，项目处于 ABORTED + 未归档状态。ABORTED 已写入 DB 不可回滚，虽然有"重试"按钮，但用户可能直接关闭对话框，留下不一致状态。

### 12. SSO 端点存在开放重定向

**文件**: `auth.controller.ts:185, 207`

`ssoToMall` 接受用户可控的 `redirect_uri` 查询参数，直接作为 `res.redirect()` 目标。标注为 `@Public()` 无需认证。`GET /api/auth/sso/mall?redirect_uri=https://evil.com` 可进行钓鱼（OWASP A01:2021）。

### 13. `decryptSupplier` 端点缺少方法级 @Roles

该端点只继承类级 `@Roles('admin', 'bid_host', 'leader', 'staff')`，未缩小到 `@Roles('admin', 'bid_host')`。`leader` 和 `staff` 角色都能执行投标文件解密。对比同模块 `reuploadBidFile`（line 340）、`resealBidFiles`（line 356）都显式标注了 `@Roles('admin', 'bid_host')`。

### 14. WS `opening:completed` 事件——:3005 掉线时永久丢失

**文件**: `bid.gateway.ts:267-270`、`apps/web/src/hooks/use-bid-websocket.ts:169`

fire-and-forget，Socket.IO 不保证到达。如果 :3005 WS 客户端此时断连，事件永久丢失。有 30s HTTP 轮询兜底 + `onReconnected` 全量刷新，但**项目页未注册 `onReconnected` 处理器**（`apps/bid-portal/.../project/[id]/page.tsx:106-158`），仅 ExchangeDrawer 有隐式恢复。

### 15. 🆕 评标委员会组成无法律合规校验

**法规依据**: 《暂行规定》第九条——"成员人数为五人以上的单数，其中技术、经济等方面的专家不得少于成员总数的三分之二"

**文件**: `bid.service.ts:1195-1198`（startEvaluation）

代码只检查 `expertCount === 0`（零专家时阻断），但**不校验**：
- 最低人数（依法须 5 人以上单数）
- 奇数要求
- 技术/经济专家占比 ≥ 2/3

系统允许 1 人或 2 人专家组启动评标。`generateEvaluationResults`（line 2908）仅对 `panelSize < 3` 写警告日志，不阻止结果生成。这在实际招投标中属于**程序违法**，评标结果可被投诉撤销。

---

### 16. 🆕 缺少异常低价投标检测机制

**法规依据**: 《暂行规定》第二十一条——报价"明显低于其他投标报价……使得其投标报价可能低于其个别成本的"，应要求投标人书面说明并提供证明材料；不能合理说明的，作废标处理。

**文件**: 全局缺失

代码中 `price-formula.service.ts` 的 `ratio` 公式（line 138-141）注释写"不惩罚异常低价"，整个系统**没有**：
- 异常低价自动检测/告警
- 要求供应商书面说明的流程
- 供应商证明材料上传通道
- 低于成本报价的废标判定逻辑

价格分公式中 `lowest_price` 和 `benchmark_deviation` 只做上偏惩罚（高价扣分），不检测下偏异常。这意味着系统完全依赖专家人工判断，缺乏法定要求的系统级防线。

## 🟡 中严重度（P1 — 影响流程一致性/审计完整性/UX/法律合规）

### 17. 专家控制器全部缺少 @Roles('bid_expert') 显式门控

**文件**: `expert.controller.ts` 全文

无任何 `@Roles` 声明。RolesGuard 对无 `@Roles` 的端点直接返回 `true`。任何已认证用户（mall/supplier/staff）都能调用 `/api/expert/projects/:id`、`/api/expert/projects/:id/report` 等端点。虽然 service 层有 `BidExpert.findFirst({ userId, projectId })` 自然过滤，但缺少纵深防御。

### 18. 回避确认可重复修改冲突名单

**文件**: `expert.service.ts:386-431`

`confirmAvoidance` 是幂等的——每次调用覆盖 `conflictedSupplierIds`。专家可先声明冲突A、查看其他供应商评分情况后、再调用传入不含A的列表撤销回避。自动检测的冲突无法绕过（会重新合并），但**手动声明的回避可被撤回**且后续修改无审计日志。违反《暂行规定》第十三条回避义务的严肃性。

### 19. 自动冲突检测仅基于工作单位名称子串匹配

**文件**: `expert-conflict.service.ts:23-41`

仅比较 `employer` 与供应商名称的归一化子串匹配。不检查法定代表人（`legalPerson` 存在于类型定义但从未使用）、亲属关系、近三年业务往来、持股关系、母子公司等。简称、别名、不同名等变体无法覆盖。

### 20. 签到/phoneVerified 状态永久持久化

**文件**: `expert.service.ts:352-384`、`verification.service.ts:217-227`

一旦设为 `true` 永久保持，无时间戳、无重置逻辑。重新登录、跨天访问、阶段转换都不需重新验证。种子数据中 `signedIn`/`phoneVerified`/`avoidanceConfirmed` 全预设为 `true`。

### 21. KMS_SECRET 缺失时静默解密失败

**文件**: `envelope-crypto.ts:34,53`、`bid.service.ts:1664-1668`

KMS_SECRET 缺失时 `unwrapKey` 抛错 → 被解密流程 catch → 所有供应商标书标记为 DANGER。无启动时强制检查。表现为"投标文件损坏"而非配置错误，难以诊断。

### 22. benchmark_deviation 公式无 ceilingPrice 时全员满分

**文件**: `price-formula.service.ts:122-125`

```ts
if (!ceilingPrice || ceilingPrice <= 0) return maxScore; // 无报错，静默满分
```
3 种默认采购方式映射到 benchmark_deviation，但项目可能未设 ceilingPrice。所有供应商价格分满分，价格分失去区分度。

### 23. manualMarkInvalidBid / createDispute / createMotion 无阶段门控

**文件**: `bid.service.ts:3800`、`expert.service.ts:1772`、`expert.service.ts:1836`

三个方法都不检查 `project.stage`。可在 DOWNLOAD 阶段标记废标、在项目刚创建时提交异议工单或发起表决。

### 24. closeMotion 法定人数计算包含弃权票

**文件**: `expert.service.ts:1891-1913`

`motion.votes.length` 计入 abstain。5 人组：2 approve + 1 reject + 2 abstain = 总票 5 ≥ quorum 3 → 结果 'approved'。但实际只有 2/5 赞成。

### 25. 动议投票/澄清答疑均无超时机制

**文件**: `expert.service.ts:1841`、`bid.service.ts:3181`

- 动议 status='voting' 可永久悬挂（专家不投票 → quorum 永不满足）
- 澄清 status='待回复' 可永久悬挂（供应商不回复 → 不阻塞评标流程）
- tie_deadlock 结果无后续处理路径

### 26. 通过性废标投票基数可能不足

**文件**: `bid.service.ts:2730-2766`

在 5 人专家组中仅 3 人提交评分时，2 票不通过即废标（2 > 3-2=1），而非需要 3 票（严格过半 5 人）。代码写了完整性警告日志但**废标决议仍然执行**。

### 27. enterOpeningRecord 无 actor 归属 + 并发重复创建

**文件**: `bid.controller.ts:386-389`、`bid.service.ts:2425-2443`

- Controller 不捕获 `@CurrentUser`，无法追溯谁录入了唱标记录。
- 事务内 `findFirst` + 条件 `create`/`update` 无行锁，并发调用可重复创建开标记录。

### 28. 双 WebSocket 连接——项目页 + ExchangeDrawer 各持一条

**文件**: `apps/bid-portal/.../project/[id]/page.tsx:106`、`apps/bid-portal/.../exchange-drawer.tsx:129`

两个独立 Socket.IO 连接到同一命名空间、同一项目。双倍认证开销 + 双倍 `join:project` DB 查询 + 双倍事件投递。

### 29. WS 页面可见性断连——关键事件永久丢失

**文件**: `apps/web/src/hooks/use-bid-websocket.ts:196-214`、`apps/bid-portal/.../use-bid-websocket.ts:188-207`

Tab 隐藏时主动断开 WS，恢复时重连触发 `onReconnected` 全量刷新。但断连窗口内的事件永久丢失（Socket.IO 无离线消息持久化）。**项目页未注册 `onReconnected` 处理器**。

### 30. 暂停/恢复开标——仅阻塞解密，不阻塞唱标/异议/交流

**文件**: `bid.service.ts:2261-2334`

`pauseOpening` 设置 `pausedAt`，`decryptSupplier` 检查并拒绝。但唱标录入、异议提出、会场交流等方法**不检查暂停状态**。且 pause/resume 本身无事务包裹，并发 resume 可双倍补偿解密窗口。

### 31. 专家进度计算与结果生成的供应商过滤口径不一致

**文件**: `score-recalculate.helper.ts:12-16` vs `bid.service.ts:2663-2665`

进度计算：`decryptStatus=SUCCESS && submitStatus!=已撤回`
结果生成：额外要求 `confirmStatus==='CONFIRMED' && bidValidity!=='invalid'`

专家进度可达 100%（含 EXCEPTION 供应商），但该供应商不出现在最终排名中。

### 32. 评审报告（getReport）不显示废标状态

**文件**: `expert.service.ts:1592-1622`

`getReport` 遍历 `project.suppliers` 全部供应商，不区分 `bidValidity`。被标记为 `invalid` 的供应商仍正常出现在专家评审报告中（带分数），无废标标识。

### 33. 开标文件包 SHA-256 指纹不具确定性

**文件**: `bid.service.ts:769-770`

`generatedAt: new Date().toISOString()` 纳入指纹计算体。重新生成时新旧指纹不同，无法通过指纹比对验证内容是否被篡改。

### 34. generateEvaluationResults 缺少 FOR UPDATE 行锁

**文件**: `bid.service.ts:2630-2928`

不像 `startEvaluation`/`archiveAll`/`completeOpening` 调用 `lockAndReassertStage`。两个并发调用可互相覆盖结果。

### 35. 解密异常供应商——acceptSupplierDanger 不可逆且无复核

**文件**: `bid.service.ts:417-424`

主持人单方面接受解密失败后不可逆，无监督人确认环节。实际招投标中，解密失败的责任认定（系统故障 vs. 供应商过错）是常见争议焦点，当前缺少第三方见证/复核机制。

### 36. 评分标准 CRUD 无阶段/发布锁守卫

**文件**: `bid.controller.ts:485-506`

Controller 层的 `updateScoreItem`/`deleteScoreItem` 等方法没有检查评分标准是否已发布。可通过直接 API 调用修改已发布评分标准。《暂行规定》第十七条：应"根据招标文件规定的评标标准和方法"评标，标准不得中途变更。

### 37. 实时废标判定非事务化——bidInvalidBid 与 bidValidity 可暂时不一致

**文件**: `expert.service.ts:1269-1301`

`submitScores` 事务提交后执行：upsert `bidInvalidBid` → count → update `bidValidity`。三步非事务化，异常被 try/catch 静默吞掉。

### 38. replyClarification 无操作人留痕

**文件**: `bid.controller.ts:627-629`

Controller 不传 `@CurrentUser`，Service 不接收 `actorId`。谁回复了澄清完全无审计痕迹。《暂行规定》第十九条要求澄清"应以书面方式进行"且留痕。

### 39. 评标时限 72 小时仅通知不强制

**文件**: `bid.service.ts:1244`、`scheduler.service.ts:254-285`

定时任务只写监督日志和发通知，不自动流标/归档/锁定评分。评标可无限期拖延。

### 40. WS Gateway 无消息限流

**文件**: `bid.gateway.ts`

无 `@Throttle`。`join:project`/`leave:project` 每次触发 DB 查询，恶意客户端可高频调用造成 DB 负载。

### 41. 同分排名以供应商名字母序裁决——缺业务依据

**文件**: `bid.service.ts:2845-2849`

中国招标实务中同分通常按更低报价优先或抽签。名称以"A"开头的供应商在同分时恒优，可被质疑不公正。

### 42. 交流控制状态无 REST 源——仅事件驱动

**文件**: `apps/bid-portal/.../exchange-drawer.tsx:92,228`

`control` 状态仅通过 WS 事件更新，无 REST 端点查询当前状态。新加入/重连的用户不知道当前是 MUTED 还是 CLOSED。

### 43. 🆕 评审报告内容不符合法定要求

**法规依据**: 《暂行规定》第四十二条——评标报告应如实记载十项内容（基本情况和数据表、评标委员会成员名单、开标记录、投标一览表、废标情况说明、评标标准/方法一览表、经评审的价格或评分比较一览表、排序、推荐中标候选人名单、澄清说明补正纪要）

**文件**: `expert.service.ts:1509-1649`（getReport）、`bid.service.ts:2626-2928`（generateEvaluationResults）

`getReport`（个人评审报告）仅包含：项目名/编号、专家名/进度、本人评分明细、核对状态。**缺少**：开标记录、废标情况说明、经评审的排序、推荐中标候选人名单、澄清纪要。

`generateEvaluationResults`（评标结果汇总）仅存储排名/总分/均分/报价。**未生成**包含十项法定内容的完整评标报告文档。

### 44. 🆕 专家评审报告缺少正式书面不同意见机制

**法规依据**: 《暂行规定》第四十三条——"对评标结果有不同意见的评标委员会成员应当以书面方式阐述不同意见和理由"

**文件**: `expert.service.ts:1652`（confirmReport）

`confirmReport` 接受 `comment` 参数，但仅存入监督日志的 `result` 字段（一行文本）。**无**：
- 正式的"不同意见"标记（与"同意"区分）
- 不同意见的书面阐述结构化存储
- 拒绝签字的记录机制
- 法条要求的"拒绝签字且不陈述理由的，视为同意评标结论"逻辑

### 45. 🆕 澄清答疑不验证是否改变投标文件实质性内容

**法规依据**: 《暂行规定》第十九条——澄清"不得超出投标文件的范围或者改变投标文件的实质性内容"

**文件**: `bid.service.ts:3181-3197`（createClarification）、`bid.service.ts:3137`（replyClarification）

系统记录澄清问题和回复，但**无任何机制**验证或限制供应商回复是否超出了投标文件范围或改变了实质性内容。供应商理论上可以通过澄清环节补充投标文件中未提供的实质性承诺。

### 46. 🆕 系统故障导致解密失败——无"系统故障 vs 供应商过错"责任认定流程

**文件**: `bid.service.ts:417-424`（acceptSupplierDanger）、`bid.service.ts:339-354`（reuploadBidFile）

实际招投标中，解密失败的常见原因包括系统拥堵、CA 证书不兼容、网络中断等，责任认定是争议高发区。当前系统仅有"主持人接受"（单向不可逆）和"管理员补传"两种操作，**缺少**：
- 系统故障证据留存（如时间线、日志快照）
- 供应商自证无过错的通道（如补充提交解密尝试记录）
- 监督人/第三方见证机制
- 部分解密成功的处理逻辑（仅技术文件解密成功但商务文件失败时的处置）

### 47. 🆕 采购人代表可被设为评审组长

**法规依据**: 实务要求——"采购人代表不得担任组长"（多地采购管理办法明确规定）

**文件**: `expert-admin.service.ts:788-789`（setLeader）

`setLeader` 方法直接设置 `isLead: true`，不校验该专家是否为采购人代表（系统未区分"独立专家"与"采购人代表"角色）。虽然 BidExpert 模型有 `expertRole` 字段（正选/候补），但没有"采购人代表"标识，无法阻止采购人代表被设为组长。

## ✅ 合规性验证通过项（代码已正确实现）

以下法律法规要求**经代码验证已正确实现**：

1. ✅ **专家评分独立性** — `getReport`（`expert.service.ts:1531-1534`）仅查询 `where: { expertId: expert.id }`，专家看不到其他专家的评分。符合独立评审准则。
2. ✅ **澄清必须书面** — 所有澄清通过 API 文本记录（`BidClarification` 表），符合《暂行规定》第十九条"应以书面方式进行"。
3. ✅ **中标候选人 1-3 人** — `DEFAULT_WINNER_COUNT = 3`，`recommended` 字段 + 排名，符合《暂行规定》第四十五条。
4. ✅ **评标标准不得自行变更** — `publishScoreStandard` 发布锁 + 事务内 FOR UPDATE 与 `startEvaluation` 互斥。
5. ✅ **评标保密** — 专家 WS 聚合数据仅暴露签到/回避/报告确认的**计数**（`broadcastAggregatePresence`），不暴露个别专家信息给供应商。
6. ✅ **废标条件** — 七种重大偏差通过 QUALIFICATION/RESPONSIVE 类评分项 + 通过性投票机制覆盖。
7. ✅ **归档不可逆** — 状态机棘轮 + 行锁复查防止 ARCHIVED 复活。
8. ✅ **解密双层校验** — AES-256-GCM 解密 + SHA-256 完整性校验，任一文件失败则整体 DANGER。
9. ✅ **供应商签到原子抢占** — `updateMany({ where: { id, checkInAt: null } })` 防并发双签到。
10. ✅ **评标报告签字机制** — `reportConfirmed`（各专家签字）+ `leaderCoSigned`（组长末签），符合《暂行规定》第四十三条签字要求（但缺少书面不同意见结构化存储——见问题 #44）。
