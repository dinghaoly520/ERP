### 2.2 业务需求分析

**为什么需要主持人↔专家沟通？**

- 评标过程中主持人可能需要私信专家组长协调进度或指出问题
- 但不应该让主持人直接干预专家打分（应保持独立）
- 设计原则：**主持人单向发起、专家仅读/回复**，不开放专家主动给主持人发消息
- 消息应为评标记录的一部分（写入监督日志）


## 五、风险与注意事项

1. **P2 的谈判/竞价 UI 差异**：两种模式的交互逻辑不同，需在需求确认阶段明确 UI 原型
2. **D1 的双向消息安全**：专家不可主动发私聊给主持人（防干预打分），仅在主持人先发起后可回复
3. **D1 的 WebSocket 事件**：重新打开旧项目时历史消息需从 `OpeningHallMessage` 表加载
4. **回归测试**：D1 修改了 Gateway 和 ExchangeDrawer 的已有逻辑，需确保供应商→主持人私聊不受影响
5. **跨端一致性**：P2 的报价提交需要同时在 Supplier Portal (:3004, Vue) 和 bid-portal (:3007, Next.js) 都有 UI——但本报告仅覆盖 bid-portal（Next.js）侧。Supplier Portal Vue 侧需单独评估。
