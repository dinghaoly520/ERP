## A 簇：数据清除语义（「设置后不可清」模式）

### A1. ExpertProfile.regionCode / expertLevel 可清除

**定位**：
- `apps/api/src/expert/dto/expert-admin-misc.dto.ts:38,41`——两字段 `@IsOptional`，DTO 无法表达「显式置空」
- `apps/api/src/expert/expert-admin.service.ts:389-390`——`...(dto.regionCode !== undefined && { regionCode: dto.regionCode })`：undefined=跳过，永远写不进 null
- 前端 `apps/web/src/app/(main)/expert/[id]/page.tsx` 编辑表单：空值提交 `undefined`（键被 JSON 序列化丢弃）

**修复方案**：
1. DTO 增加 null 语义（class-validator 允许 `@ValidateIf` 表达「string 或显式 null」）：

```ts
// expert-admin-misc.dto.ts
@IsOptional()
@ValidateIf((o, v) => v !== null)
@IsString() @MaxLength(6) @Matches(/^\d{6}$/, { message: 'regionCode 须为 6 位行政区划代码' })
regionCode?: string | null;

@IsOptional()
@ValidateIf((o, v) => v !== null)
@IsIn(['A', 'B', 'C', 'D', 'E'])
expertLevel?: 'A' | 'B' | 'C' | 'D' | 'E' | null;
```

2. service 改 null-aware 展开（`expert-admin.service.ts:389-390`）：

```ts
...(dto.regionCode !== undefined && { regionCode: dto.regionCode }),   // null 落库为 NULL=清除
...(dto.expertLevel !== undefined && { expertLevel: dto.expertLevel }),
```

（条件展开本身已兼容——`dto.regionCode === null` 时 `!== undefined` 成立、值 null 直接写库。**唯一改动点是 DTO 放行 null**。）

3. 前端编辑表单（`expert/[id]/page.tsx`）：等级/区域输入框旁加「清除」小按钮（或空值提交改 `regionCode: null`）；提交组装处：

```ts
regionCode: form.regionCode.trim() || null,   // 空=清除（原为 undefined=不动）
expertLevel: form.expertLevel || null,
```

**影响面**：管理端编辑 API 语义增强（新增 null 入参），既有调用方（不传 null）行为不变；无 schema 变更。
**测试**：service spec 增两用例——`{regionCode: null}` → update data 含 `regionCode: null`（Prisma 写 NULL）；`{}`（undefined）→ data 不含键。
**风险**：低；回滚=单提交 revert。

### A2. BidExpert.reviewGroup / dutyRole 可清除

**定位**：`apps/api/src/expert/expert-admin.service.ts:1007`——`data: { reviewGroup: a.reviewGroup ?? undefined }`（null 被 `??` 吞成 undefined）；DTO `committee-assignment.dto.ts` 白名单不含 null。

**修复方案**：
1. DTO：

```ts
@IsOptional()
@ValidateIf((o, v) => v !== null)
@IsIn(['技术组', '商务组', '综合组'])
reviewGroup?: string | null;
// dutyRole 同款
```

2. service `:1007` 改 `data: { reviewGroup: a.reviewGroup ?? undefined, ... }` → `data: { reviewGroup: a.reviewGroup === undefined ? undefined : a.reviewGroup, ... }`（即：undefined=不动，null/值=写入）；同处 service 层双白名单守卫（`:996`）放行 null。
3. 前端 `extract/page.tsx` 步骤5 两 select 的空 option 从「不设置」改为双语义：**「不设置（保留现值）」+ 新增「清除」选项**（value=`__CLEAR__`，提交组装映射为 null）；表下提示行同步改文案「清除＝提交 null 清空已保存分工」。
4. docx 名单 `?? '—'` 渲染无需改（null 自然落 '—'）。

**测试**：spec 增「`{reviewGroup: null}` → update data 含 null」与「undefined → 不含键」两用例；前端组装用例（如无前端测试基建则浏览器验收）。
**影响面**：报告名单 7 列中已设值清空后回 '—'——语义正确；无 schema 变更。

## B 簇：A-152 边角

### B1. CN 名源分叉（CERT_DN_MISMATCH 不可自愈）

**定位**：`apps/api/src/expert/expert.service.ts:2452-2458`——校验 `user.displayName || user.username`；而证书创建 label 用 `BidExpert.expertName`（report-step）。专家改过 displayName 后，既有证书重绑/新证书创建即 400。

**修复方案**（后端放宽为「任一合法名源匹配」，兼容历史证书）：

```ts
// :2454 起
const expertName = user?.displayName || user?.username || '';
// B1：名源集合——displayName/username + 该专家历史评委名（BidExpert.expertName 任一）
const aliasNames = await this.prisma.bidExpert.findMany({
  where: { userId }, select: { expertName: true }, distinct: ['expertName'], take: 20,
}).then(rows => rows.map(r => r.expertName)).catch(() => [] as string[]);
const cn = extractDnCn(certDn);
const norm = normalizeExpertCn;
const matched = !cn ? false
  : [expertName, ...aliasNames].some(n => n && norm(cn) === norm(n));
if (!matched) throw new BadRequestException({ error: '证书主体(CN)与专家姓名不一致', code: 'CERT_DN_MISMATCH' });
```

**理由**：取证成本一次 findMany（绑定低频操作）；BidExpert 名册名是法定证据名（报告名单用它）， displayName 变更不应作废按名册名签发的历史证书。**前端同步对齐**：`report-step.tsx` 创建证书 label 改用 `user.displayName || expertName`（与后端主名源一致），新证书天然匹配主校验。
**测试**：spec 三用例——displayName 匹配 ✓；displayName 不匹配但 bidExpert.expertName 匹配 ✓（历史证书场景）；两者皆不匹配 → 400。
**风险**：放宽方向（多接受一种合法情形），无收紧面；别名查询 take 20 防极端膨胀。

### B2. 一气流中断态滞后（bind 成功但签名失败 → 停留 need-cert，重试走换证 churn）

**定位**：`apps/expert-portal/src/components/evaluate/report-step.tsx`——`doEsignWith` 首次路径「创建证书→bindCert→**继续签名**」，签名/提交失败后 `esign.state` 未推进，下次重试再走「创建+绑定」（旧 ACTIVE 置 REVOKED）。

**修复方案**：bindCert 成功后立即固化就绪态，失败分支不再回落 need-cert：

```ts
// 创建+绑定成功后：
setEsign({ state: 'ready', hasCert: true, certSn: created.certSn });
// 随后签名失败（EXPERT_ESIGN_INVALID 等）时保持 'ready'，错误 toast 已有——
// 重试入口即「电子签署」直路（复用已绑证书，不再 createCertificate/rebind）
```

具体实现：把「首次口令对话框」的处理函数拆两段——`createAndBind(pin)`（成功后 `state='ready'` 并落入 pin 会话续跑 `doSign`）与 `doSign(pin)`（ready 态按钮直用）；失败重试只调 `doSign`。
**测试**：手动路径验收（创建→模拟签名失败→按钮应为「电子签署」而非「创建签名证书并签署」）；无前端单测基建则记验收清单。
**风险**：低；口令会话生命周期不变。

### B3. 两错误码 fallback toast

**定位**：report-step 错误映射表缺 `SM2_PUBLIC_KEY_INVALID` / `CERT_SN_EXISTS` 专属文案。
**修复**：映射表补两行——

```ts
SM2_PUBLIC_KEY_INVALID: '证书公钥格式无效，请重新创建证书',
CERT_SN_EXISTS: '该证书序列号已被绑定，请勿重复绑定（或先在 U盾管理解绑）',
```

**风险**：零。

## C 簇：A-105 健壮性

### C1. marker 先写后发（通知失败 → 一次性提醒永久丢失）

**定位**：`apps/api/src/bid/bid.service.ts:5950-5975`——`upsert marker` 在 `sendToRole` 之前且 void+catch。
**修复方案**（调序 + await + 失败不占坑，日调度兜底）：

```ts
if (pending.length > 0) {
  const names = pending.slice(0, 5).map(s => s.supplierName).join('、');
  try {
    await this.notificationService.sendToRole('staff', { /* 原文案 */ });
    await this.prisma.systemConfig.upsert({ /* 原 upsert */ });   // 发送成功才占坑
  } catch (e) {
    // 发送失败：不写 marker（下次触发可重发）；日调度第二通道（bond_return_reminded:*）仍会兜底
    this.logger?.warn?.(`A-105 定标提醒发送失败 project=${projectId}: ${String(e)}`);
  }
}
```

**注意**：`deliverAwardLetter` 可能被重推（幂等 upsert 通知书）——重推时 pending 已变化则重发提醒，符合「发送成功才占坑」语义；通知书重推频率低，无骚扰风险。
**测试**：spec 两用例——sendToRole resolve → marker 写入；sendToRole reject → marker **未**写入 + warn 日志（mock logger）。
**风险**：低；与既有 findUnique 短路幂等兼容。

### C2. 逐家三写无事务（部分写失败留脏态）

**定位**：`bid.service.ts:5788 markSupplierBondReturned`——`bidSupplier.update`(:5804) / `bidOpeningRecord.updateMany`(:5814) / `bidSupervisionLog.create`(:5819) 顺序裸写。
**修复方案**：包 `$transaction`（前两项为强一致必需；监督日志沿用 `.catch` 弱一致风格进事务内亦可——与 unregister/register 家族对齐，进事务）：

```ts
const now = new Date();
await this.prisma.$transaction(async (tx) => {
  await tx.bidSupplier.update({ where: { id: roster.id }, data: returned
    ? { bondReturnedAt: now, bondReturnReason: null }
    : { bondReturnedAt: null, bondReturnReason: dto.reason!.trim() } });
  await tx.bidOpeningRecord.updateMany({ where: { projectId, bidSupplierId: roster.id },
    data: { bondStatus: returned ? '已退还' : '不予退还' } });
  await tx.bidSupervisionLog.create({ data: { /* 原文案 */ } }).catch(() => {});
});
return { success: true };
```

（返回值若前端消费 updated 行则保留查询；当前 :3005 BondReturnBlock 只看 success——已核实。）
**测试**：改造既有三写用例断 `$transaction` 内 tx.* 调用（spec mock 惯例 `prisma.$transaction = cb => cb(prisma)` 自动兼容）。
**风险**：低；监督日志 catch 保留弱一致。
