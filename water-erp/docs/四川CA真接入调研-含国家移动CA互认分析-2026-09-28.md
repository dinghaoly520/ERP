## 路径 A：直连四川CA（介质盾 USBKey）

**机构**：四川省数字证书认证管理中心有限公司（四川CA / SCCA），持工信部《电子认证服务许可证》+ 国密局使用密码许可证。
- 官网 `www.scca.com.cn`（JS 渲染）；自助网厅 `bss.scca.com.cn:8088/selfservice`（含政府采购/公共资源专用入口）
- 热线 **400-028-1130**；窗口：成都高新区交子大道333号中海国际中心E座509；成都市公共资源交易中心3楼设受理点
- 产品：USBKey（国密 SM2 双证书）+「SCCA」客户端程序组 + i信管理工具 + 电子签章 + 签名验签 + 密评密改

**集成形态**：USBKey + 驱动 + 客户端本地服务（浏览器 JS SDK 走 WebSocket/HTTP 127.0.0.1，行业已替代 OCX）——
**与本项目 mock ukey-mw（:17999）架构同构**，`packages/ukey` 适配层 + `vendor-ukey.ts` 替换点设计正好对上。

**⚠️ SDK/对接文档不公开**，须联系商务/技术支持获取：测试盾 + JS SDK + 服务端验签 SDK（签名验签服务器）+ 测试环境。

## 路径 B：国家移动 CA 互认（免介质，扫码）

### 政策脉络
- 2020-11 发改委征集公共资源交易领域 CA 全国互认 → 2023-02 发改委办公厅在**地方公共资源交易平台和企业招标采购平台**试运行跨区域兼容互认（**企业自建平台明确在列，水利发集团属此类**）→ 2024-07《移动数字证书(CA)互认技术标准》及四份接入指南定稿 → 2024–2025 各省落地（湖北/甘肃/深圳/河南/陕西/连云港/泰安…）→ 2025-08 发改委：全国移动 CA「一张网」。
- 四川侧：川办规〔2025〕8号；省平台已要求使用「纳入全国互认范围的证书及签章」。未见四川省单独互认实施方案。

### 技术架构（42 页指南原文要点）
**二维码会话模式 + 平台侧自建「CA互认共享组件」**：

```
供应商手机APP(标证通/数信签/标信签等) --扫码--> 交易平台网页 --HTTPS--> CA互认共享组件(本地部署,开源免费,Java)
私钥运算在手机端安全数字容器完成（密钥分割存储+协同签名，平台接触不到私钥）
```

四大业务模块，统一「生成二维码 → 轮询状态(00未扫/01已扫未授权/02失效/03已授权) → 取结果」三段式：

| 模块 | 接口链 | 关键点 |
|---|---|---|
| 共享登录注册 | generateLoginQRCode → queryQRCodeScannedStatus → getUserAuthInfo | 单位/个人唯一ID、统一社会信用代码、签名证书+SN、CA机构编码 |
| 消息签名验签 | generateMessageSignatureQRCode → getMessageSignatureValue（+verifySignatureValue） | P7 签名值+证书，服务端可验签 |
| 电子签章 | 本地签章工具（Windows 注册表协议 `zzAppSignUtility://` 唤起）或网页签章组件 | PDF/OFD 盖章、扫码撤章、回调上传；详见《签章组件接入指南》分册 |
| 加密解密 | 见下 | **数字信封模式** |

**加密解密（与本项目双信封 dual-v2 同构，最关键发现）**：
- 加密端：`generateMessageEncryptQRCode` → 扫码授权 → `getUserEncryptionCert` 取**加密证书（SM2 公钥）**→ 本地 SM4 加密文件 + SM2 封装对称密钥成**密钥信封**（含 CA机构编码/加密证书SN/密文密钥）
- 解密端（开标）：`generateMessageDecryptQRCode(idCardHash, orgCode)` → 供应商扫码 → `getDecryptUserInfo`(accessToken) → `uploadEncryptedKeyDataEnvelope` 上传信封 → 轮询 `getDecryptedData` 取回**明文对称密钥** → 服务端解密文件
- 状态 `-3：该标段非当前APP账号加密`——与 dual-v2「C_outer 本人解密」语义对齐

**协议与部署**：HTTP POST JSON + HMAC-SM3 签名（clientId/clientSecret/signatureSecret），官方 Java SDK 但协议公开可自行封装（Node 可用 sm-crypto）；组件为 Java 应用（JDK1.8，MySQL/达梦/金仓），生产参考规格 2×32C64G+测试 1×16C32G（大平台口径，可缩配）；组件需公网可达。

### 治理与接入条件
1. 组件与源代码**免费公开**（cashare.cebpubservice.com 互认专栏发布，中国招标投标公共服务平台负责升级）
2. 自助开通管理平台注册取 `tradingSystemCode` + clientId/clientSecret
3. 须接入 **≥3 个互认 APP**，覆盖 **≥30 个移动证书**+国家标准电子印章
4. **与介质盾兼容并存**（移动 CA 不取代路径 A，是叠加）
5. 按监管要求上报移动 CA 使用情况数据

## 对本 ERP 的落地分析

**契合度高**：dual-v2 本质即「SM4 文件加密 + SM2 密钥信封 + 开标取回对称密钥」，与互认加密/解密接口同构；`packages/ukey` SM2/SM4/SM3 直接复用；NestJS 自实现 HMAC-SM3 调用即可，不依赖 Java SDK。

**成本与风险**：
- 多运维一个 Java 组件（Docker 化可解，需公网）
- 开标现场依赖供应商手机在线（弱网/没电风险 → 需保留介质盾兜底，论证 A+B 双轨）
- 签章走本地工具/组件，Windows 协议唤起是传统桌面形态，浏览器端形态待看《签章组件接入指南》分册
- **待确认**：①四川CA是否已入国家互认共享目录（cashare 专栏目录页核对）；②企业自建平台自助开通是否需额外审批

**建议节奏**：四份指南+组件源码 → 自助开通拿测试凭据 → dev 起 Docker 化组件 → 打通扫码登录+消息签名 → dual-v2 投递/解密接密钥信封接口 → 签章最后。同时四川CA 400-028-1130 介质盾方案并行询价，最终 A+B 双轨。

## 附录（2026-09-28 补）：内网部署约束下的网络流向核实

**生产环境约束**：数据机/应用机纯内网互通，仅跳板机可出外网。以下为对 42 页指南逐节核实后的网络模型：

### 组件的真实网络流向（非「整套都要公网」）

| 流向 | 内容 | 证据 |
|---|---|---|
| **入站公网（仅组件需要）** | 手机 APP（供应商 4G/公网）扫码后直接 POST 授权/签名值/解密授权到组件公网地址 | 部署规格「负载均衡 QPS≥3000、**公网带宽≥20M**」；二维码由组件生成（含 tid 会话），`qrCodeJumpUrl` 指向国家平台仅做 APP 目录引导 |
| **ERP → 组件：纯出站** | HTTP POST 轮询拉结果（queryQRCodeScannedStatus 等）+ SDK 消息监听（ERP→组件方向）；**指南中无任何组件→ERP 回调** | 4.1.2 调用入口单向；签章工具 `callbackrequest` 回调目标是组件 serviceUrl（示例 123.56.236.113:8868 / localhost:9291），非交易系统 |
| 组件出站 | 组件 → CA机构/印章机构节点（证书可信性校验等） | 「检查 CA 数字证书是否由可信的 CA 机构签发」+ 泛中心化节点互联 |

### 约束下的部署拓扑

1. **方案一（推荐）：组件上公网云主机，ERP 经跳板机出站**——对接既有云服务器部署方案（2026-09 cloud-deployment-plan）。应用机→跳板机（内网）→云组件 443。内网安全边界零改动，ERP 只需出站 HTTPS。
   - 跳板机打通方式：squid/nginx 正向代理（Node 24 内置 undici EnvHttpProxyAgent 认 https_proxy）或 autossh `ssh -L 18443:云组件:443`（组件地址固定单一，端口转发足够）
   - 规格可缩：集团平台 QPS 远低于 3000，单机 8C16G + 云 MySQL 起步即可（32C64G×2 是全国级平台口径）
   - 附加成本：域名 + ICP 备案 + SSL 证书（自助开通时登记组件 URL）
   - **安全注意**：解密会话的明文对称密钥（getDecryptedData 返回 decryptedKey）会流经云端组件——涉密敏感场景改选方案二
2. **方案二：机房 DMZ/前置机 + 公网端口映射**——仅放行 443 入站到 DMZ；前提是能走通集团公网映射审批（周期不可控）
3. **方案三：随整体公网化路线走**——供应商门户本身生产形态必然公网可达，CA 组件跟着公网入口层部署，不产生「额外」公网需求

### 对 A/B 选型的修正

- 路径 A（介质盾）CA 环节**零公网依赖**：盾在供应商自己电脑（浏览器↔127.0.0.1），服务端验签 SDK 本地内网可跑，CRL/OCSP 可离线文件或经跳板机定期拉取
- 路径 B 依然可行，但**前置条件 = 云/DMZ 有一个公网落点**；纯内网 + 跳板机仅出站的现实下，B 的落点就是既有云服务器
- 修正后建议：**A 先行（内网自洽、周期可控），B 挂到公网化部署路线上择机叠加**——两者本就要求并存（≥3 APP 接入是互认侧要求，不冲突）
