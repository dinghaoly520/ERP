## 二、分工方案

### 2.1 总体原则

1. **按业务域切分，不是按层次切分** — 每个人负责一个完整的业务域，从数据库模型到前端页面全部包揽
2. **共享基础设施由一人主导，另一人遵循规范使用** — 避免在共享层上两人同时改动
3. **通过明确的 API 契约解耦** — 两个业务域之间通过已定义好的 API 接口和数据模型交互
4. **Git 分支策略**：各自在功能分支上开发，通过 PR 合并到 main，减少冲突

### 2.2 分工矩阵

```
┌─────────────────────────────────────────────────────────────┐
│                    开发人员 A (核心交易链)                      │
│  采购管理 + 开评标管理 + 专家管理 + AI引擎 + 管理端主框架       │
├─────────────────────────────────────────────────────────────┤
│  后端模块: bid/, expert/, ai/ (采购模块新建)                    │
│  管理端页面: /procurement, /bid/*, /expert (app-shell主导)     │
│  专家门户: expert-portal/ 全部页面                             │
│  供应商端: 与投标相关的页面 (BidList, BidDetail, BidSubmit)      │
├─────────────────────────────────────────────────────────────┤
│                    开发人员 B (供应商与平台运营)                  │
│  供应商管理 + 公告管理 + 电子商城 + 评价管理 + 公开门户 + 通知   │
├─────────────────────────────────────────────────────────────┤
│  后端模块: supplier/, announcement/, notification/,           │
│           supplier-portal/, upload/  (商城/评价模块新建)       │

│  公开门户: public-portal/ 全部页面                             │
│  供应商端: 信息与运营相关页面 (CompanyInfo, Contacts,           │
```

## 五、共享基础设施协调

### 5.1 共享层清单

| 共享资源 | 主要负责人 | 协调机制 |
|------|:---:|------|
| Prisma Schema | **人员 A** | A 负责 schema 整体结构；B 提交 PR 新增模型时 A review；迁移合并前两人确认 |
| 共享类型 (`packages/shared/`) | **人员 B** | B 负责类型定义的整理和导出；A 新增类型后通知 B 同步更新 |
| 配置 (`packages/config/`) | **人员 A** | 端口、URL 等基础配置；重大变更两人商议 |
| 认证体系 (`auth/`) | **人员 A** | A 维护核心认证逻辑；B 使用 AuthGuard 和 CurrentUser 装饰器 |
| 通知系统 (`notification/`) | **人员 B** | B 维护通知基础服务；A 在需要时注入 NotificationService 发送通知 |
| 文件上传 (`upload/`) | **人员 B** | B 维护上传基础设施；A 调用统一的上传接口 |
| App Shell (管理端导航) | **人员 A** | A 管理 navItems 配置；B 新增导航项时提交 PR |
| Docker Compose | **人员 A** | 基础设施维护（PostgreSQL, Redis, MinIO） |
| CI/CD 与部署 | **人员 A** | 初始搭建后两人共同维护 |

### 5.2 协作关键节点

```
共享层变更流程:
  1. 发起人提出变更方案（issue/文档）
  2. 两人确认影响范围
  3. 发起人实现变更
  4. 另一人拉取最新代码，适配自己的模块
  5. 合并后两人各自验证
```

## 七、开发规范

### 7.1 Git 工作流

```
main ← feature/a-procurement ← PR review ← merge
     ← feature/b-supplier   ← PR review ← merge
```

- 分支命名：`feature/{人员}-{模块名}`，如 `feature/a-procurement-platform`
- Commit 规范：`feat(模块): 描述` 或 `fix(模块): 描述`
- 每日至少一次 `git pull origin main` 同步
- PR 必须经另一人 review 后合并
- **严禁直接 push 到 main 分支**

### 7.2 代码规范

- **后端**：遵循 NestJS 模块化架构，每个模块包含 `module.ts` + `controller.ts` + `service.ts` + `dto/`
- **管理端**：遵循 Next.js App Router 约定，页面放在 `(dashboard)/` 分组下
- **类型定义**：前端类型统一从 `packages/shared` 导出，新增类型必须同步更新
- **API 调用**：统一使用 `lib/api.ts` 封装的 fetch 函数，不要直接调 fetch
- **样式**：统一使用 Tailwind CSS，颜色使用设计令牌变量

### 7.3 数据库迁移协调

由于 Prisma schema 只有一个文件，两人都需要新增模型时必须协调：

```
流程:
  1. 需要新增模型的一方：创建 feature 分支
  2. 修改 schema.prisma，运行 pnpm db:migrate --name xxx
  3. 提交 PR（包含 schema + migration SQL）
  4. 另一方 review 迁移SQL，确认无冲突
  5. 合并到 main
  6. 另一方 git pull 后运行 pnpm db:generate 同步本地
```

### 7.4 API 契约约定

跨域调用时必须通过已定义的接口：

- RESTful 风格，路径统一以模块名开头
- 请求/响应类型在 `packages/shared/src/types.ts` 中定义
- 分页统一格式：`{ total, page, pageSize, items }`
- 错误统一格式：`{ error: string, code: string }`
- API 变更必须先更新 shared types，再实现，最后通知对方

## 八、风险与应对

| 风险 | 概率 | 影响 | 应对措施 |
|------|:---:|:---:|------|
| Prisma Schema 合并冲突 | 高 | 中 | 迁移前沟通、小步提交、及时同步 |
| 共享模块修改影响对方 | 中 | 高 | 共享模块变更先讨论、充分测试 |
| API 接口理解偏差 | 中 | 中 | 接口先行定义在 shared/types.ts 中 |
| 前端组件重复开发 | 中 | 低 | 提取通用组件到 packages/ui/ |
| 数据库迁移出错 | 低 | 高 | 迁移前备份、Docker 环境测试 |
| 供应商端 Vue vs React 技术差异 | 中 | 低 | 通过 API 解耦、各自选择合适技术 |
