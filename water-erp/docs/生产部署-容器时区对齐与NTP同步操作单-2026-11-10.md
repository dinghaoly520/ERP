## 1. 背景：两个独立问题，分开处理

### 1.1 「时区标签」问题（容器 UTC）

容器不继承宿主机时区——时区解析走容器内进程的 `TZ` 环境变量或 `/etc/localtime` 文件，两台机的 run compose 均未配置，镜像默认全部 UTC。后果：

- **所有 `@Cron` 定时任务按 UTC 墙钟跑**：代码意图「每日 08:15」实际在北京 16:15 执行（全表见第 6.1 节）；
- Nest 日志、按日统计日界（`metrics-keys.util.ts` 用本地时间方法）都按 UTC。

> 注：11-09 的 +8h 开标时间漂移是**代码解析问题**（`parseFlexibleDate` 曾按进程本地时区解释无时区墙上时间），已修复为「恒按北京时间、与宿主时区解耦」（462cb58b），且已上生产。本单的 TZ 对齐不依赖该修复、也不会改变其行为（新旧实现在 +8 环境逐位一致），属于让 cron/日志/统计同样归位的运维收尾。

### 1.2 「时钟精度」问题（NTP 未同步）

两台机 `System clock synchronized: no`：chrony 服务在跑，但从没成功同步（典型原因：内网无可达 NTP 源）。系统时钟与 RTC 已差约 17 秒，且会持续漂移。**截标/开标时限校验的时钟权威 = api 进程所在机（10.60.14.14）**，漂移直接影响「到点截标」判定的可信度，优先修复。

## 4. 操作三（两台机）：NTP 同步修复

### 4.1 诊断（两台机各执行一遍）

```bash
systemctl is-active chronyd systemd-timesyncd 2>/dev/null   # 看哪个守护在跑（麒麟通常 chronyd）
chronyc tracking | grep -E "System time|Leap|Stratum"        # Leap: Not synchronised = 未同步实证
chronyc sources -v                                           # 看有无 ^*（已锁定源）；全部 ^? = 源不可达
```

### 4.2 修复（按网络条件三选一）

**选项 A——内网有 NTP 源/网关支持 NTP（优先尝试）**：编辑 `/etc/chrony.conf`，顶部加：

```
server <内网NTP地址或网关IP> iburst
```

```bash
systemctl restart chronyd && sleep 10 && chronyc sources -v    # 出现 ^* 即成功
```

**选项 B——机器可出公网**：`/etc/chrony.conf` 加 `server ntp.aliyun.com iburst` 与 `server ntp.ntsc.ac.cn iburst`，同样重启验证。

**选项 C——彻底无源（内网封闭，兜底方案）**：让两机互相同步、以 api 机为权威：

1. **10.60.14.14（权威，先做）**：对照可信时间（授时中心网页/其他准点设备）手动校准一次：

   ```bash
   timedatectl set-time "2026-11-10 HH:MM:SS"     # 按实际北京时间填
   ```

   `/etc/chrony.conf` 末尾加两行，允许其作为本地授时源：

   ```
   local stratum 8
   allow 10.10.7.20
   ```

   若 firewalld 开着，放行 NTP：

   ```bash
   firewall-cmd --add-service=ntp --permanent && firewall-cmd --reload
   ```

2. **10.10.7.20**：`/etc/chrony.conf` 加 `server 10.60.14.14 iburst`，`systemctl restart chronyd`。

   > 局限：绝对精度取决于第 1 步那次人工校准，之后两机长期保持一致但会一起漂移——**建议每季度人工核对一次权威机**。

### 4.3 验证（两台机）

```bash

chronyc tracking | grep "Leap"                       # 期望 Leap status     : Normal
```

## 5. 明确不做的事与理由

### 5.1 本机 postgres（water-erp-be-postgres，向量库 sidecar）——不改 TZ

Prisma 的 DateTime 落在 `timestamp(3)` 无时区列、按 UTC 墙钟读写（客户端统一转换），应用链路与容器 TZ 无关。把 postgres 会话时区改成 +8 只改 psql 显示，反而引入歧义：任何走数据库端 `now()`/`CURRENT_TIMESTAMP` 默认值的裸 SQL 写入，会以 +8 墙钟落列，与 Prisma 写的 UTC 墙钟混在同一列里。**保持 UTC 是与 Prisma 约定一致的最稳口径。**

### 5.2 redis / minio / erp-ocr / erp-llm / erp-embed——不改

无定时任务、无时区敏感逻辑，改 TZ 仅影响日志时间戳观感；且 OCR/LLM 容器不在 backend-run.yml 编排内（另行管理），改动面不值得。若日后想让日志也统一，做法：在其编排处加 `TZ=Asia/Shanghai`（Debian 系镜像）或挂载 `- /etc/localtime:/etc/localtime:ro`（alpine 系镜像，如 redis）。

### 5.3 金仓（10.60.1.10，不可操作）——留 DBA 沟通项

**无需任何变更**：应用层 Prisma 统一 UTC 落库、绝对时刻语义，金仓会话时区只影响 DBA 手工查询的显示。若 DBA 习惯看北京时间，可请其执行（金仓兼容 PG 语法，以其版本为准）：

```sql
SHOW timezone;                          -- 先看当前值
ALTER SYSTEM SET timezone='Asia/Shanghai';
SELECT pg_reload_conf();
```

不改也不影响系统正确性。

## 9. FAQ 排障

**Q1：宿主机明明是北京时间，容器里为什么是 UTC？**
容器时区解析走容器内进程的 `TZ`/`/etc/localtime`，与宿主机设置无关；镜像默认 UTC，需在 compose 显式配置（本单做法）。

**Q2：TZ 加了但不生效（`docker exec ... date` 仍 UTC）？**
env 变更在容器**创建**时固化——必须 `--force-recreate` 重建，`restart` 不够；compose v1 对 env_file 内容变化也不自动重建。用 `docker inspect -f '{{.Config.Env}}' <容器> | tr ' ' '\n' | grep TZ` 确认容器实际吃到没有。

**Q3：自检行出现 `→ 2026-11-20T14:30:00.000Z`？**
说明在跑旧构建（dist 未含 462cb58b 修复）。走标准链路重部：本机 `部署/backend.sh`（带 GIT_SHA 指纹校验，防旧代码出包）→ 传 tar → 服务器 `backend.sh`。

**Q4：切换后某定时任务当天没跑？**
见 6.1——墙钟型任务切换当日会跳过一次，幂等无损失；次日正点恢复。可用 `docker logs water-erp-be-api 2>&1 | grep <任务日志关键词>` 核对。

**Q5：NTP 一直同步不上？**
`chronyc sources -v` 里源全部 `^?`（Reach 为 0）= 网络不可达该源——换源（A/B）或走选项 C 兜底；firewalld 开着时注意服务器侧要放行 `ntp` 服务（UDP 123）。

**Q6：金仓那边到底要不要动？**
不要（5.3 节论证）。唯一可选动作是请 DBA 把会话时区设为 Asia/Shanghai 方便其人工查询，与系统正确性无关。
