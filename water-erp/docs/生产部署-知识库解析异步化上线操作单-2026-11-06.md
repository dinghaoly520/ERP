## 0. 影响面与铁律（先读）

**本特性动三个容器 + 库表两条迁移：**

| 对象 | 变更 | 不做的后果 |
|---|---|---|
| `water-erp-api:1.0.0` 镜像 | api（202 上传/retry 端点）与 ai-worker（消费 `knowledge-parse` 队列）共用 | 旧 api：同步解析 12 分钟超时事故原样；无新 worker：上传永停「解析中」 |
| `water-erp-portal:1.0.0` 镜像 | :3005 知识库 UI（徽章/轮询/重试） | 功能可用但状态展示错旧（toast 谎报「完成索引」） |
| 金仓 2 条迁移 | `20261106000000_knowledge_file_async_status`、`20261106010000_knowledge_file_active_sha_unique` | 新代码读写 `status` 等列 → P2022 全线红 |

**三条既有铁律（B 机实录踩过）：**

1. **migrate 必须在 up 之前**（11-04 P2022 时序伤：先 recreate 新 api 后迁移的窗口期定时任务报错）。
2. **api 与 ai-worker 必须同批 recreate**——只重建 api 的话，worker 挂在 `rmi -f` 拆 tag 后的悬空旧镜像上**继续跑旧代码且无报错**。
3. **B 机现役 run compose ≠ 仓库副本**（真身含 ai-worker 服务、连接串指金仓）——勿以仓库副本核对 B 机 env；排障先看容器实况 `docker exec <容器> env | grep DATABASE`。

**无需重跑 seed**（生产真实数据；迁移内已把存量 KnowledgeFile 行回填 `status='READY'`）。

## 1. 部署前预检（B 机，2 分钟）

```bash
# 1.1 compose v2 可用性（缺插件则 docker compose -f 报 unknown shorthand flag）
docker compose version || echo "无 v2 插件——需先从 A 机 scp 插件（见 §5 备选）"

# 1.2 现役容器名与镜像核对（ai-worker 是否在、挂在哪个镜像）
docker ps --format '{{.Names}}\t{{.Image}}\t{{.Status}}' | grep -E 'be-api|ai-worker'

# 1.3 ★向量库依赖（worker 新增——以前 worker 不连向量库）
docker exec water-erp-be-ai-worker env | grep -E 'VECTOR_DATABASE_URL|PGVECTOR_ENABLED' ; \
docker exec water-erp-be-api env | grep -E 'VECTOR_DATABASE_URL|PGVECTOR_ENABLED'
```

**1.3 判定（影响功能完整性，二选一处理）：**

- `VECTOR_DATABASE_URL` 已配（指 sidecar）或 `PGVECTOR_ENABLED=true` 且库有 vector 扩展 → ✅ 直接继续。
- 两项皆空 → worker 向量写入将回退 DIRECT_URL=金仓；**金仓 PG 模式通常无 pgvector 扩展** → 症状：解析能 READY、日志见 `Vector insert error (reindex 可补)`、**检索不命中**（半残状态）。处置：
  - 方案 A（推荐）：B 机起 pgvector sidecar 容器并在 run compose 的 api+ai-worker env 补 `VECTOR_DATABASE_URL`（形态见仓库 CLAUDE.md「VECTOR_DATABASE_URL」注：`docker compose --profile vector-sidecar up -d pgvector`，数据面独立于金仓）；
  - 方案 B：接受暂缓向量检索（上传/解析/规则提取不受影响——它们不依赖向量），后续补。
  - 注意：B 机若此前知识库检索本就未通（同因），此为存量问题非本次引入。

## 8. 回滚预案

```bash
docker tag water-erp-api:backup-20261106 water-erp-api:1.0.0
docker compose -f $CF up -d --no-deps --force-recreate api ai-worker
```

- **迁移不回滚**：纯增量列+索引，旧镜像跑在新 schema 上无感（旧代码不读新列）。
- 回滚后知识库回到同步解析（超时问题复现），属可接受的临时态。
- 回滚期间**勿 `docker rmi`** 任何 water-erp-api tag（防悬空镜像坑重演）。

## 9. 备注

- 仓库 `backend/docker-compose.backend.yml` 已补 ai-worker 服务块（`3183ff1b6`）——新机部署起点；B 机现役 run compose 与之独立，下次重生成 run 变体时以仓库版为基。
- worker 可选并发旋钮：`KNOWLEDGE_PARSE_CONCURRENCY`（知识解析，默认 1）、`AI_BID_WORKER_CONCURRENCY`（AI 分析，默认 2）——改 env 须 recreate。
- recreate worker 会中断在途 AI 分析任务（既有代价）；**在途知识解析自愈**——新 worker 启动清扫器会把队列里已无 job 的 PARSING 行自动重入队。
