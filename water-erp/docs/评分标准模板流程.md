## 一、数据模型（`apps/api/prisma/schema.prisma`）

| 模型 | 行号 | 作用 |
|------|------|------|
| `ScoreCategory` 枚举 | `:101` | `QUALIFICATION` / `RESPONSIVE` / `BUSINESS` / `TECHNICAL` / `PRICE` 五大类 |
| `BidProject.scoreStandardPublishedAt` | `:258` | **锁定锚点**——发布后置为时间戳，所有写操作据此判断是否锁定 |
| `BidScoreItem` | `:414` | 评分项（大类下的一条），含 `maxScore`、`scoringCriteria`、`criteriaSource` |
| `BidScorePoint` | `:433` | 得分点（评分项的 checklist 子项），`fullScore` + `objective`(客观/主观) + `seq` |
| `BidScoreRecord` / `BidScorePointDecision` | `:449` / `:467` | 专家实际打分（标准发布后才产生） |
| `ScoreTemplate` | `:2211` | **用户保存的可复用模板**：`payload` 是 JSON，结构为 `{ items: [{ category, name, maxScore, points: [...] }] }` |

关键层次：`BidProject 1—N BidScoreItem 1—N BidScorePoint`；`ScoreTemplate` 是独立的一张表，与项目解耦，便于跨项目复用。

## 三、核心流程（`apps/api/src/bid/bid.service.ts`）

### 1. 锁定与编辑窗口

`assertScoreItemsEditable()` (`bid.service.ts:1932`) 是所有写操作的守卫：

```ts
if (publishedAt || stage === 'EVALUATING' || stage === 'ARCHIVED')
  → 409 SCORE_ITEMS_LOCKED
```

即：**仅在 DOWNLOAD/SUBMIT/OPENING 阶段且未发布时可编辑**。一旦发布或进入评标/归档，全部锁死（`bid.service.ts:1910` 注释说明了原因：评分项是评标前置条件，专家已打分后改标准会破坏数据一致性）。

### 2. 编制 → 发布的完整链路

```
应用默认模板  ──►  逐项 CRUD  ──►  AI 提取得分点  ──►  发布(锁定)
applyScoreItemTemplate   create/update/delete   extract→batch    publishScoreStandard
   :2122(硬编码5类)        :1950/1972/2011       :319/:2104        :2156
```

- **默认模板** `applyScoreItemTemplate` (`:2122`)：硬编码 5 类（资格0/符合0/商务20/技术50/价格30），**按 name 幂等去重**，解决新建项目无评分项导致评标死锁的问题。
- **AI 提取** `ScorePointExtractorService.extractScorePoints` (`score-point-extractor.service.ts:36`)：
  - PRICE 类直接返回空（价格分走报价公式）`:46`
  - 拉取招标文件纯文本 → E1 规则正则定位「评标办法」章节，失败用 embedding 语义搜索兜底 `:161`
  - E2 得分等比缩放（Σ>maxScore 时）`:89`、E4 去重标记（Levenshtein ≤0.3）`:79`、E6 LLM 失败降级返回空数组让管理员手填 `:75`
  - **同步调用、不落库**——结果回前端让管理员审核
- **发布** `publishScoreStandard` (`:2156`)：先过完整性校验 → 置 `scoreStandardPublishedAt` → 锁定。重复发布抛 `SCORE_STANDARD_ALREADY_PUBLISHED`。

### 3. 校验规则（`score-standard-validator.service.ts`）

| 校验 | 方法 | 触发点 | 错误码 |
|------|------|--------|--------|
| 通过性类(QUALIFICATION/RESPONSIVE) `maxScore` 必须 = 0 | `assertPassFailMaxScore` `:13` | create/update/applyTemplate 每项 | `PASS_FAIL_MUST_BE_ZERO` |
| 得分点 ΣfullScore + 增量 ≤ 大类满分 | `assertPointsSumWithinMax` `:23`（事务内） | 得分点 create/update/batch | `POINTS_SUM_EXCEEDS_MAX` |
| 打分类 ΣmaxScore === 100 | `assertScoreStandardComplete` `:43` | 发布时 + 启动评标时(`:579`) | `MAX_SCORE_SUM_NOT_100` |
| 每个打分类项 ≥1 个得分点 | 同上 `:57` | 发布时 | `SCORE_ITEM_HAS_NO_POINTS` |

注意：**启动评标（OPENING→EVALUATING）也会再跑一次 `assertScoreStandardComplete`** (`bid.service.ts:579`)，与发布校验形成双保险。

### 4. 审计

`logScoreStdOp` (`bid.service.ts:1914`) 把每次编制/发布操作写入 `BidSupervisionLog`，带 `operatorId`/`operatorRole`；同时经 `gateway?.notifySupervisionLog` 推监督端实时日志。所有写操作都在 `$transaction` 内，保证审计日志与数据变更原子一致（这正是最近 commit `b1a42b8b` "审计+B1校验+事务一致性" 做的事）。

### 5. 保存的模板（ScoreTemplate，跨项目复用）

- `saveScoreTemplate` (`:2181`)：把当前项目的 items+points 序列化成 `payload` JSON 存表
- `applyScoreTemplateById` (`:2217`)：读模板 → **B1 校验**（每项过 `assertPassFailMaxScore`）→ 事务内按 name 幂等去重创建 items + 批量创建 points → 审计
- `listScoreTemplates` (`:2209`)：返回「自己创建的 + 公共(`createdById=null`)」
- `deleteScoreTemplate` (`:2273`)：仅创建者可删自己的

## 四、前端（`apps/bid-portal/src/app/(dashboard)/bid/standard/`）

- **`page.tsx`**：评分项表格。顶部据 `publishedAt`/`stage` 算 `locked` (`:49`) 决定是否显示「发布 / 应用标准模板 / 新增」按钮；锁定时显示黄色 Lock 横幅 (`:149`)。展开行内嵌得分点编辑器。
- **`score-points-editor.tsx`**：得分点 CRUD + AI 提取建议审核弹窗。E3 按 confidence 排序、E4 重复项默认不勾选 (`:42`)，管理员可逐条编辑后再「导入选中的」(`:57` 调 batch)。

前端只用了「默认模板」按钮（`applyScoreItemTemplate`），**保存模板 CRUD（`score-templates` 四个端点）目前没有任何前端调用方**——`lib/api/bid.ts` 连封装函数都没导出。也就是说：用户保存的可复用模板功能后端完备，但 bid-portal 还没接 UI。

## 五、关键结论

1. **两个"模板"要分清**：`applyScoreItemTemplate` 是硬编码的默认 5 类（有 UI 按钮）；`ScoreTemplate` 表是用户自保存的复用模板（后端完整、**前端未接**）。
2. **锁定机制单一锚点**：`BidProject.scoreStandardPublishedAt` + 阶段判断，所有写路径都过 `assertScoreItemsEditable`。
3. **AI 提取是同步辅助、不落库**：管理员审核后才 `batch` 入库，保证人工把关。
4. **双校验**：发布时 + 启动评标时各跑一次完整性校验。
5. 工作区当前改的 `bid.service.ts` / `bid.service.spec.ts` 正是这块——commit `b1a42b8b` 刚把 apply 模板的事务一致性、B1 校验、审计补齐。
