## P0（阻断法定流程 / 终局状态不可信）

### P0-1 状态机 ARCHIVED→ABORTED 放行：已归档项目可被流标
- **位置**：`apps/api/src/bid/bid-state.ts:6-33`（STAGE_ORDER + assertBidStageTransition）；`bid.service.ts:1279`（abortBidProject 无阶段下限守卫）
- **问题**：STAGE_ORDER 把 ABORTED(5) 排在 ARCHIVED(4) 之后，而校验只拒绝「目标序 < 起点序」。ARCHIVED→ABORTED 属"正序"被放行；`abortBidProject` 仅做棘轮校验，无任何额外闸门。注释宣称"离开 ARCHIVED 抛 409（天然终态）"，实现不成立。
- **后果**：staff/leader/bid_host 对已归档项目调用 `POST /bid/projects/:id/abort` 即可把 ARCHIVED 改为 ABORTED——违反「归档不可逆终局」承诺；归档端列表（stage=ARCHIVED 过滤）丢失该项目而 archiveItems 仍为 ARCHIVED（数据分裂）；此后还能 `reopenFromAborted` 生成第二轮采购，形成"归档后重启"的合规事故。
- **修复方向**：`assertBidStageTransition` 显式拒绝 `from === 'ARCHIVED'`（唯一例外保留既有 ABORTED→ARCHIVED 特例）；或 abortBidProject 增加 `stageAtLeast(stage,'OPENING') && stage !== 'ARCHIVED'` 守卫。同族检查 `archiveAll(scope=full)` 对 ABORTED 起点的放行语义（现由签字闸门兜住，建议一并显式化）。
- **验证**：对 ARCHIVED 项目 POST abort 应 409；补 e2e 断言。

### P0-2 定时发布 cron 绕过全部发布闸门，可致公示期/中标通知书死锁
- **位置**：`apps/api/src/scheduler/scheduler.service.ts:293-311`（publishScheduledAnnouncements 裸 `prisma.announcement.update` 置 PUBLISHED）
- **问题**：手动发布走 `announcementService.update()` 的完整闸门链——B-004/B-009 时限预检、GB 赋码强制闸、PRE_WIN/WIN_NOTICE 的 publicityEnd 推导、BID_NOTICE 建项+BidDocument 联动。定时发布路径只发通知，以上全部缺失。
- **最严重后果**：定时发布的预成交公示 publicityEnd 恒 null → `getPublicityStatus` 按 P1-8 口径"null 视为未满足" → `canIssueAward` 永为 false → **中标通知书永久无法发出**；`confirmWinnerNotice`（两段式第二段）同样被 null 公示期挡死。定时发布的招标公告还可能违反 20 日/5 日法定时限且零拦截。
- **修复方向**：cron 改调 `announcementService.update(id, { status: 'PUBLISHED' })`（该路径已具备 P2025 并发竞争幂等分支）。
- **验证**：定时发布一条 PRE_WIN_NOTICE 草稿，到期后 publicityEnd 非 null、canIssueAward 可翻真。

## P1（法定义务缺口 / 数据矛盾 / 保密边界）

### P1-1 评标澄清「创建」事件向全体投标人广播（含被询供应商名与问题预览）
- **位置**：`bid.gateway.ts:331-334`（notifyClarificationCreated → project 房）；`bid.service.ts:2825`
- **问题**：type=clarification（评标澄清，法定保密）与 type=question（答疑，公开）不加区分地广播到 project 房——全体投标人 socket 均可收到 `supplierName + questionPreview(60字)`。与 2026-08-28 已修复的 notifyClarificationReplied（收口 host+experts 房）口径不一致，属同一泄密面的另一半。
- **修复方向**：type=clarification 改投 host 房 + experts 房 + 当事供应商定向（复用 `supplierSocketsIn` 模式）；type=question 维持公开广播。
- **验证**：EVALUATING 期间发起澄清，非当事供应商 socket 不应收到 CLARIFICATION_CREATED。

### P1-2 手动废标不联动清评标结果/失效签字包（与异议裁决路径双标）
- **位置**：`bid.service.ts:4080`（manualMarkInvalidBid）对照 `:3952`（resolveExpertDispute）
- **问题**：异议裁决采纳废标会：清空评标结果 + 删未闭环签字包 + 重置全员签字状态 + 闭环包拦截（SIGN_PACKET_CLOSED）。手动废标只置 `bidValidity=invalid`，既不清结果也不失效签字包，也无闭环检查。
- **后果**：结果已生成、签字已闭环后手动废标——官方排名/签字包/回流包仍把该供应商当有效候选人，full 归档闸门照常通过，形成「已签字的官方结果与废标事实并存」的法定文件矛盾；同时绕过 spec §10「闭环后不可更正」语义。
- **修复方向**：manualMarkInvalidBid 复用 dispute 路径的结果清除 + 签字包失效事务段（含闭环包 409 拦截）；revokeManualInvalidBid 对应补结果重算提示。

### P1-3 updateProject 无阶段锁：采购方式/资质/保证金/归档后时间可任意改
- **位置**：`bid.service.ts:836-936`
- **问题**：仅 openTime/deadline 有 align/frozen 校验；`procurementMethod`、`qualification`、`bondRequired/Amount`、`budget` 在任何阶段（含 EVALUATING/ARCHIVED）可改。对照同域 `updatePriceConfig` 已对 EVALUATING/ARCHIVED 锁定（P2-17），更核心的采购方式反而未锁。
- **后果**：评标中把采购方式改为「直接采购」可使家数门槛 3→1 事后合法化（getMinBidders 语义随字段漂移）；ARCHIVED 阶段改 openTime/deadline（frozen 分支仅约束相对关系）会污染历史证据——开标文件包/归档包记录的是旧时间。
- **修复方向**：OPENING 起锁 procurementMethod/qualification/bond 字段（409 提示走法定更正）；ARCHIVED 锁全部业务字段。

### P1-4 「依法必招」时限引擎不可达：legalMandatory 全库零写入点
- **位置**：`announcement.service.ts:652`（`legalMandatory = existing?.legalMandatory ?? false`）；全仓 grep 无任何 create/update/DTO 写入该字段
- **问题**：W2 的 B-004（售标→开标 ≥20 日）/B-009（发售期 ≥5 日）强制校验以 legalMandatory=true 为前提，但建项 DTO、公告向导、项目管理均无该字段的录入/推断路径——引擎永不触发，只剩偏离留痕；公告直建路径（existing=null）恒 false。
- **上下文**：2026-08-21 用户曾决定跳过 P0-3 修复；其后 CTS 侧已落地规则引擎——现状是"半实现"。**需用户拍板**：①维持跳过 → 在册注明引擎为占位；②启用 → 补 legalMandatory 录入口径（建议按采购方式默认推断：公开/邀请招标→true，其余→false 可改）。
- **关联**：memory `p0-3-deadline-validation-deferred`。

### P1-5 未投递供应商：批量解密误归因 PLATFORM + 错误赔偿告知；H4 口径语义错位
- **位置**：`bid-decrypt.service.ts:294-342`（decryptAllSuppliers 扫 PENDING 未撤回）+ `:517`（DANGER 分支硬编码 `dangerAttribution:'PLATFORM'`）+ `notifySupplierDecryptFailure` 文案；`bid.service.ts:1707`（getOpeningNotReady）
- **问题 a**：邀请名册中「已下载未投递」家 decryptStatus 恒 PENDING；一键解密把它们送进 decryptSupplier → 无提交记录 → DANGER + **归因硬编码 PLATFORM** + 供应商收到「因平台原因未完成解密…有权要求责任方赔偿（《办法》第31条）」——对从未投标的家是错误归因 + 错误权利告知（旧轨真实解密失败同样被预置 PLATFORM，架空 §5.5 归因矩阵与主持人裁决）。
- **问题 b**：H4 开标完成度守卫把未投递家与未解密家同列阻塞，处置出口是 acceptSupplierDanger「接受未解密」——未投递≠解密异常，开标文件包 summary 将其计入 decryptFailed，语义污染留痕。
- **修复方向**：①decryptSupplier 的 DANGER 归因改 `UNKNOWN`（裁决落 BIDDER/PLATFORM），通知文案按归因分流、未投递家不发赔偿告知；②startOpening 阶段推进时将 submitStatus!=='已提交' 的名册行显式置「未投递」终局（或 H4 口径排除未投递家）。

### P1-6 未中标供应商定向结果通知缺失（《招标投标法》第45条）
- **位置**：`bid.service.ts:3674`（deliverAwardLetter 仅通知中标人）
- **问题**：法 45 条要求中标人确定后「同时将中标结果通知所有未中标的投标人」。现有通道仅公开预成交公示，无定向通知；既往 backlog「落标通知」至今未落地。
- **修复方向**：deliverAwardLetter 事务成功后向其余已递交供应商发结果通知（含中标人名称、感谢语、保证金退还提示），站内信留痕；可在 A-105 提醒同事务段扩展。

## P2（边界 / 保密 / 质量改进）

### P2-1 WS host 房无公司隔离与指派校验
`bid.gateway.ts:246-251`：REST 侧有 BidCompanyScopeGuard（跨公司 403），WS join:project 对 admin/bid_host/leader/staff 只验角色不验公司/指派——B 公司 staff 可挂任意项目 host 房持续接收监督日志/异常事件。修复：join 时镜像守卫语义（admin 放行、:3007 指派、:3005 本公司）。

### P2-2 exportArchivePackage 无阶段闸且绕过评标匿名化
`bid.service.ts:4398`：任意阶段可导出"归档包"；EVALUATING 期间导出的 expertScores 含实名+分数映射，而同期 listScores/getProject 均匿名（EXPERT_SCORE_ANONYMIZED_DURING_EVAL）——导出通道成为匿名化旁路。修复：非全员 reportConfirmed 时对非特权角色脱敏 expertScores，或限制导出至 ARCHIVED/全员确认后。

### P2-3 多轮报价资格口径过松：已撤回/解密失败家可参与报价轮
`bid.service.ts:4170/4355`：createRound 默认名单=bidValidity!=invalid（含已撤回家、解密 DANGER 家）；submitQuote 不校验 submitStatus/decryptStatus——已撤回供应商可继续报价，报价经 syncMultiRoundPrices 写入开标记录污染唱标/评标价格源。修复：默认名单=decryptStatus SUCCESS && 未撤回 && valid；submitQuote 增同口径校验。

### P2-4 评标超时后仍可生成评标结果（绕过延期审批闸）
`bid-evaluation-results.service.ts:107`：专家超时被 EVALUATION_OVERDUE 拦截交分，但 generateEvaluationResults 不检查 evaluationDeadline——主持人可在未审批延期的情况下直接用已有分数出官方结果。修复：generate 前置 assertEvaluationNotOverdue（或超时后要求先延期）。

### P2-5 公式价格分静默 0：唱标金额缺失/非数值无告警
`price-formula.service.ts` + `aggregate-supplier-scores.ts:59`：公式激活时专家 PRICE 打分一律跳过；供应商 bidPrices 缺条目（金额未录/非数值）→ 该家价格分恒 0 且不进 completenessWarnings（仅查通过性项）。修复：PRICE 项+公式激活时对金额缺失家写监督告警或 400 阻断。

### P2-6 开标签字登记无阶段闸：ARCHIVED 后仍可重建开标文件包
`opening-sign.service.ts:136`（registerSign）：仅要求 handoverAssetId+扫描件，不校验 stage——归档后上传新扫描再登记会**重建 MinIO 开标文件包并改写 FileAsset.sha256**，已归档证据件被事后变异。修复：registerSign 增加 `stage !== 'ARCHIVED'` 守卫（归档后补签走数据修正流程）。

### P2-7 会话重组建窗口无「未来值/不可缩短」校验
`bid.service.ts:1536-1574`：同阶段 upsert 会话可把 decryptWindowEnd 改到过去（立即关闭窗口）或大幅缩短——等同提前终止供应商解密权；也不校验新 host 与指派一致。修复：重组建时校验 decryptWindowEnd > now 且 ≥ 现值（延长合法、缩短需显式 reason 留痕）。

### P2-8 杂项代码质量
- `bid.gateway.ts:236`：`procurement_staff` 死分支（角色 2026-08-20 已删）；`tokenFromHandshake` 默认分支注释"web/bid-portal 共用 token_web"已过时（token_bid 独立）。
- `bid.service.ts:5004` notifyScheduleChange：不校验传入 openTime 与项目当前值一致/合法（可广播与真实不符的时间），且无 @Throttle。
- `getRoundQuotes` 以 `req.user?.role ?? 'supplier'` 兜底——语义上应显式 401 而非默认最低权。

### P2-9 已知在册超时处置缺口（确认仍在，勿重复立项）
评标 72h 超时仅每小时告警无自动处置；澄清/动议超时无自动闭环；evaluationDeadline 到期不阻断归档（配合 P2-4 一并定夺）。
