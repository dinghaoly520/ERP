## 二、法规合规对照

依据《中华人民共和国招标投标法》(2017修正)、《电子招标投标办法》(2013年第20号令)、《评标专家和评标专家库管理办法》(2024)：

| 法规要求 | 条款 | 实现状态 |
|----------|------|---------|
| 电子投标文件加密传输与存储 | 电子办法第17条 | ✅ 加密存储 / ⚠️ 密钥明文存库 |
| 开标解密时间窗口控制 | 电子办法第28条 | ✅ 服务器端窗口校验 |
| 投标人数字身份认证 | 电子办法第26条 | ⚠️ 仅JWT认证，无SM2数字证书 |
| 评标专家回避（单位+利害关系） | 招投标法实施条例第34条 | ⚠️ 仅单位名称匹配 |
| 监督端独立、不干预评标 | 电子办法第30条 | ✅ 只读监督端 + 标注 |
| 数据电文可靠性（不可篡改） | 电子签名法第5条 | ⚠️ 有哈希链归档 / 缺数字签名 |
| 评标过程记录、可追溯 | 评标专家办法第24条 | ✅ 监督日志 + 审计 |
| 专家抽取随机性 | 评标专家办法第18条 | ✅ crypto.randomInt() Fisher-Yates |

## 三、关键缺陷详解

### 🔴 缺陷-1：加密密钥明文存储（严重等级）

**文件定位**：
- `apps/api/src/supplier-portal/supplier-portal.service.ts:385-504`（submitBid 加密逻辑）
- `apps/api/prisma/schema.prisma:641-643`（SupplierBidSubmission.*SealedKey）
- `apps/api/prisma/schema.prisma:592`（BidDocument.decryptKey）

**现状描述**：
供应商提交投标时，服务器使用 AES-256-GCM 对上传文件进行加密（Layer B 密封）。加密密钥以 `key:iv:authTag` 格式的 hex 字符串**明文**存储在 `SupplierBidSubmission.technicalSealedKey` / `businessSealedKey` / `coverLetterSealedKey` 字段中。`BidDocument.decryptKey` 同理。虽然 `BidProject.encryptionKeyId` 和 `FileAsset.encryptionKeyId` 字段已预留（Track C），但从未实施。

**安全后果**：
数据库泄露 = 所有已加密投标文件可被解密。不符合《电子招标投标办法》第17条"确保数据电文在发送、接收、存储过程中的安全"要求。

**改进方案**：

```
方案A（最小改动，1-3天）: 环境变量派生密钥的 Envelope Encryption
┌─────────────────────────────────────────────────────┐
│ 1. 生成随机 DEK（数据加密密钥，32字节）              │
│ 2. 用 DEK 加密文件（现有 encryptBuffer 逻辑）        │
│ 3. 用 KEK = SHA-256(KMS_SECRET + projectId) 包裹 DEK │
│    算法: AES-256-GCM(KEK, DEK) → wrappedKey          │
│ 4. DB 存储 wrappedKey（而非明文 DEK）                 │
│ 5. 解密时: wrappedKey → 解包 → DEK → 解密文件        │
│ 6. KMS_SECRET 通过环境变量注入，不存储于任何DB        │
└─────────────────────────────────────────────────────┘

方案B（生产级，1-2周）: 云KMS集成
- 使用阿里云KMS/华为云KMS的 Encrypt/Decrypt API
- 数据库仅存储密钥引用 ID（KMS keyId + ciphertextBlob）
- KMS自动记录每次密钥访问的审计日志
- 支持密钥轮转（定期更换KEK，自动重新包裹DEK）
```

### 🔴 缺陷-2：缺乏密码学抗抵赖（严重等级）

**文件定位**：
- `apps/api/src/announcement/bid-document.crypto.ts:15-25`（classifyDecryptOutcome）
- `apps/api/src/announcement/bid-document.crypto.ts:34-42`（verifyIntegrity）

**现状描述**：
投标文件的 SHA-256 哈希在上传时（明文状态）计算并存储在 `FileAsset.sha256`。加密后（Layer B），完整性校验比对的是**解密后的明文哈希**与原始 `sha256` 值。这意味着：如果攻击者同时替换了 MinIO 中的密文文件和数据库中的 `sealedKey`，校验仍能通过——因为没有供应商侧的密码学签名来证明"这份文件确实是供应商 X 提交的"。

**安全后果**：
在司法争议中无法提供技术证据证明供应商提交了特定内容。不符合《电子签名法》第5条对"数据电文可靠性"的要求。

**改进方案**：

```
供应商数字签名机制:
┌──────────────────────────────────────────────────┐
│ 1. 供应商侧（客户端）:                            │
│    a. 使用 SM2 私钥对投标文件 SHA-256 做签名       │
│    b. 签名 = SM2_Sign(supplierPrivateKey, hash)   │
│    c. 签名随投标文件一并上传                       │
│                                                    │
│ 2. 服务端:                                         │
│    a. 存储签名于 SupplierBidSubmission.signature   │
│    b. 开标时公示签名值                              │
│    c. 任何第三方可用供应商公钥验证                   │
│                                                    │
│ 3. 可信时间戳（可选增强）:                          │
│    a. 接入国家授时中心 TSA 服务                     │
│    b. 签名 + 时间戳 → 证明"何时提交了什么"          │
└──────────────────────────────────────────────────┘
```

### 🟡 缺陷-3：投标提交的 MinIO/DB 事务非原子性（高等级）

**文件定位**：
- `apps/api/src/supplier-portal/supplier-portal.service.ts:428-443`（加密回滚逻辑）

**现状描述**：

```typescript
// 当前流程（简化）:
// 1. 从 MinIO 读取明文文件
// 2. AES-256-GCM 加密
// 3. 将密文 PUT 回 MinIO 原路径  ← 不可逆操作
// 4. Prisma transaction: 存入 sealedKey, 更新状态
// 5. 如果步骤4失败 → catch 块尝试恢复明文（best-effort）
//    → 但如果恢复失败，明文永久丢失
```

**风险场景**：
1. 步骤3成功（MinIO 中已是密文）
2. 步骤4失败（DB 事务回滚，sealedKey 未保存）
3. 回滚（步骤5）也失败（网络瞬断等）
4. **结果**：MinIO 中文件不可解密（没有密钥），供应商需重新上传

**改进方案**：

```
方案A（推荐，2-3天）: 不覆盖原文件
┌─────────────────────────────────────────────────┐
│ 1. 保留原明文文件不动                             │
│ 2. 加密后写入新路径:                               │
│    bids/{projectId}/sealed/{supplierId}/{file}.enc│
│ 3. DB事务成功后 → 异步删除原明文                    │
│ 4. DB事务失败 → 仅删除新路径密文，原文件完好        │
│ 5. 增加定时清理任务：处理超时 ENCRYPTING 状态的记录 │
└─────────────────────────────────────────────────┘

方案B（备选）: FileAsset 事务中间态
- FileAsset 增加 status: UPLOADED | ENCRYPTING | ENCRYPTED
- 标记 + 加密 + 确认 三段式状态机
- 清理线程处理 ENCRYPTING 超过N分钟的记录
```

### 🟡 缺陷-4：专家回避机制过于狭窄（高等级）

**文件定位**：
- `apps/api/src/expert/expert-conflict.service.ts:1-54`（detectConflicts, normalizeName）
- `apps/api/src/expert/expert-admin.service.ts:169-302`（previewExtraction 中的 employer 过滤）

**现状描述**：
回避检测仅做**单位名称重叠**匹配——剥离公司后缀（有限公司、有限责任、集团等）后做双向子串匹配。未覆盖：

| 回避类型 | 法规来源 | 实现状态 |
|----------|---------|---------|
| 工作单位与投标人相同 | 招投标法实施条例第34条 | ✅ 已实现 |
| 投标人的控股股东/实际控制人关联 | 同上 | ❌ |
| 与投标人法定代表人/高管有近亲属关系 | 同上 | ❌ |
| 3年内与投标人有合同关系 | 同上 | ❌ |
| 其他可能影响公正评标的利害关系 | 同上 | ❌ |

**改进方案**：

```
短期（1周）: 扩展现有检测
1. ExpertProfile 增加字段:
   - relatedCompanies: string[]     // 曾任职单位
   - declaredConflicts: string[]    // 手动申报的利害关系
2. 供应商侧申报:
   - 供应商报名时填写"已知回避专家/单位"清单
   - 交叉校验：专家声明 ∩ 供应商声明

中期（2-4周）: 工商数据对接
3. 接入国家企业信用信息公示系统 API
   - 自动查询法人、股东、高管关联关系
   - 专家身份证号 → 工商登记信息 → 交叉比对

长期: 专家利益冲突知识图谱
4. 构建专家-单位-项目三维关联图谱
   - 单位关联（任职/曾任/控股）
   - 人员关联（近亲属/师生/合作）
   - 项目关联（曾参与/待参与/合同关系）
   - 自动发现隐性关联路径
```

### 🟡 缺陷-5：评分偏差检测仅为被动诊断（中等级）

**文件定位**：
- `apps/api/src/expert/expert-deviation.ts:1-57`（computeExpertMeanDeviations）
- `apps/api/src/expert/expert-admin.service.ts:371-384`（getEvaluationStats）

**现状描述**：
`computeExpertMeanDeviations()` 计算每个专家与组平均值的偏差，但**仅在管理后台展示**，不触发任何实时告警。异常评分（过高/过低/趋同）只能在事后发现。

**改进方案**：

```
实时偏差告警机制:
┌──────────────────────────────────────────────────┐
│ 检测规则:                                         │
│ a. 单专家与组均值偏差 > 20% → 黄色告警             │
│ b. 单专家与组均值偏差 > 30% → 红色告警             │
│ c. 专家间评分方差 < 极小阈值 → 协同偏差告警        │
│                                                    │
│ 告警通道:                                         │
│ - WebSocket BID_EVENT.ANOMALY_DETECTED (已预留!)   │
│ - 推送至监督端（不阻断评分，保持独立性原则）        │
│ - 记录至 BidSupervisionLog                         │
│                                                    │
│ 强制复核:                                          │
│ - 偏差 > 30% 的评分项 → 监督人手动确认后纳入汇总    │
│ - 协同偏差项 → 触发专家重新独立评分请求             │
└──────────────────────────────────────────────────┘
```

## 四、行业趋势与技术展望

### 4.1 区块链存证

当前系统已实现基于 SHA-256 的梅克尔-达姆加德链式哈希归档（`bid-archive.digest.ts`），这本质上是区块链的核心数据结构。下一步可将根哈希锚定到联盟链（如人民法院司法区块链、天平链），实现：

- 归档哈希的不可篡改时间戳证明
- 第三方独立验证（无需信任服务器）
- 满足最高人民法院《关于互联网法院审理案件若干问题的规定》中对电子证据的要求

### 4.2 国密算法迁移

当前使用 AES-256-GCM（国际算法）。中国《密码法》第27条要求关键信息基础设施使用商用密码（SM系列）：

- SM2 替代 RSA/ECDSA 用于数字签名和密钥交换
- SM4 替代 AES 用于数据加密（已有标准化 Node.js 实现 `sm-crypto` 包）
- SM3 替代 SHA-256 用于哈希（用于归档链和完整性校验）

### 4.3 隐私计算在评标中的应用

- **联邦学习**：多家采购单位的评标数据联合训练异常检测模型，不共享原始数据
- **安全多方计算（MPC）**：多专家评分在加密状态下汇总，任何单一专家/管理员无法窥视他人评分
- **可信执行环境（TEE）**：加密标书在 TEE 中解密和评审，操作系统层面不可窥视

## 六、架构亮点（值得保留和推广）

以下现有设计值得肯定和继续投入：

1. **Socket.IO 角色隔离房间** (`bid.gateway.ts:42-57`)：host 房间仅限管理员，评分数据永不通过 WebSocket 传输——设计精良的安全隔离
2. **哈希链归档** (`bid-archive.digest.ts:61-79`)：梅克尔-达姆加德链式结构，排序输入确保确定性——为区块链锚定提供了完美数据基础
3. **WebSocket 客户端健壮性** (`use-bid-websocket.ts`)：指数退避重连、20s心跳、stale-closure 安全——生产级质量
4. **5步向导渐进解锁** (`expert-portal evaluate page`)：身份核验→保密承诺→纪律守则 三级递进——符合心理认知模型
5. **AES-256-GCM 正确使用** (`bid-document.crypto.ts`)：随机密钥+随机IV+authTag 验证——密码学实现正确
