# 评标专家身份核验设计（身份证号登录 + 必拍留档照 · 最终方案）

> **日期**: 2026-09-18
> **状态**: **已批准最终方案**（2026-09-18 用户裁定）——**不采用人脸识别、不做工位分配**；登录 = 账号 + 身份证号默认口令，签到 = 必拍留档照（遮挡检测）；主持人核验登记保留为可选强化模式
> **关联文档**: `docs/鉴权门户边界与硬编码假功能复核清单-2026-08-14.md`（D2 假人脸）、`docs/superpowers/specs/2026-08-13-expert-paper-signing-design.md`（签字包证据体系）、`CLAUDE.md` 分工 v3
> **法规依据**: 《评标专家和评标专家库管理办法》（2024 年第 26 号令）第七条（采集人脸系「**宜**具备」——推荐性条款）、第二十一条（人脸门禁系「**可以**依托」的**可选**技术手段，证件凭证+留痕同构成防请托管理措施）；国办发〔2024〕21 号（远程异地评标）
> **决策沿革**: 人脸方案（否决存档）→ 方案 A 主持人人证+工位绑定（多轮细化：无手机/无平板/评标室码防幽灵工位）→ **用户最终简化：登录页账密登录 + 拍照，不用分配**——工位绑定机制整体移除，误开页面无干扰面问题随之消失

---

## 1. 背景与现状

**现状**（2026-09-18 分析定稿）：专家身份核验实际强度 = 一组账号密码——`signin-camera.tsx` 拍照留痕不比对、可跳过；专家短信链路已随 `4d224c65` 删除（`phoneVerified` 列暂留 schema 待本设计删除）；签到照片/IP/UA 落库 `signInMeta` 但 :3007 只显示布尔「已签到」，证据存而不示；`globals.css:907` `face-scan-line` 死动画残留。

**最终路线**：26 号令「宜/可以」措辞表明人脸非法定强制；零生物特征采集 = 个保法 §28/29 敏感数据义务不触发。本人性证明 = **身份证号口令（凭证与法定身份证件绑定，本人自知的秘密）+ 每次核验必拍留档照（遮挡检测保证照片可用，事后追责证据）+ :3007 被动可视与异常处置**。主持人现场人证保留为可选强化模式（host 态）。

## 2. 最终方案总览

```
工位/平板开机 → :3006 登录页（普通账密页——误开者面对的就是登录表单，无任何可干扰面）
专家输入：账号（姓名）+ 密码（默认 = 身份证号）
  → 登录 → 评审向导第 1 步【身份核验】：
      ① 必拍留档照：摄像头引导 → 人脸遮挡检测通过方可拍下（无跳过入口）
      ② 确认照片 → 完成签到（photoAssetId 必填；signInMeta 记 IP/UA/检测结论）
      ③ 回避确认 → 保密承诺（法定须本人操作）
  → 开始评审
:3007（主持人桌面端）：核验矩阵被动展示签到状态/留档照/时间/IP
      可主动处置：核验异常登记 → 异议裁决 / 流标（既有路径）
可选强化（EXPERT_IDENTITY_VERIFY=host）：签到前另需主持人登记核验闸门
```

## 3. 设计原则与决策记录

| # | 决策 | 结论 |
|---|---|---|
| **R1** | 人脸识别 | **最终否决**（2026-09-18）。零生物特征；§7「宜」条款偏离留痕（§8）；历史研究存档见文末附注 |
| **R2** | 登录凭证 | 账号 + 密码登录（登录页保持普通账密页，不新增任何设备注册/扫码机制）；**默认口令 = 身份证号**（`ExpertProfile.idNumber` 已有列；种子/抽取/入库时置为口令哈希，专家可走既有改密审批流程变更） |
| **R3** | 签到留档照 | 每次身份核验**必拍一张**留档（不可跳过），拍照时做**人脸遮挡检测**。检测 ≠ 识别（R1 不破）：不建模板、不比对、判定即弃帧，仅存最终一帧照片——防「拍墙/拍纸」把留档变废纸 |
| **R4** | 主持人核验 | **可选强化模式**（`EXPERT_IDENTITY_VERIFY=host` 时签到前另需主持人在 :3007 登记人证核验）；默认 `self` 态不启用——用户裁定简化主流程 |
| **R5** | 异常处置 | 核验异常登记（人证不符/照片异常/到场异常，监督日志高风险事件）；**评标中不得替换专家**——2026-09-20 用户裁定：专家提前抽取，开标后不可替换（业务规则优先于早期 D1 设想），异常处置走异议裁决/流标既有路径；评标前替换仍在 :3005 开标确认面板（swapExpertRole 既有能力，开标前窗口） |
| **R6** | 模式闸 | `EXPERT_IDENTITY_VERIFY=self`（默认：必拍+检测）/ `host`（强化：另需主持人登记）/ `off`（应急：留档照降为可选，签到不阻塞——摄像头故障场景）；admin 切换留审计痕 |
| **R7** | 工位绑定 | **否决**（2026-09-18 用户裁定「不用分配」）。曾设计工位点选免密登录（含评标室码防幽灵工位），机制整体移除；「误开页面干扰」问题随之消失——登录页无物可注册、无列表可污染 |
| **R8** | 设备约束 | 评标室内专家无手机、主持人无平板——方案零移动设备、零扫码、零服务端摄像头依赖（工位摄像头仅用于拍照留档） |
| **R9** | 摄像头故障降级 | **主持人手动确认签到（2026-09-20 用户裁定）**：单工位摄像头故障由主持人（:3007，admin 兜底）**逐人**确认放行——理由必填 + 监督日志 + 签字包披露；对比后否决「admin 全局 off 开关」为主通道（粒度粗：一个摄像头坏全场免照片；决策者不在现场；证据为零），全局 off 仅留作大面积故障的最后手段（env 级，暂不做运行时开关） |

## 4. 核心流程

### 4.1 主流程（self 态，默认）

```
登录：账号（姓名）+ 密码（默认身份证号）→ token_expert 会话（既有链路，限流 10/min 已有）
向导第 1 步【身份核验】：
  ① 必拍留档照（SigninCamera 升级）：
     - 「开启摄像头」→ 检测引导：遮挡检测通过方可拍下（拍下前可无限重试），无跳过入口
     - 遮挡检测（客户端）：MediaPipe tasks-vision face detector/landmarker（Apache-2.0，含模型），
       WASM + 模型自托管 :3006 /public（内网不依赖 CDN）；
       判定 = 人脸框尺寸达标 + 眼/鼻/嘴关键点可见度 + 连续 N 帧通过 → 亮「拍照」按钮；
       不达标给具体提示（「请摘下口罩/帽子」「请正对摄像头」「光线不足」）
     - 降级：模型加载失败/老旧浏览器 → 仍必拍但 signInMeta 标注 occlusion: unchecked，
       :3007 矩阵照片标「未过检测」——不阻塞现场
  ② 确认签到：照片上传（expert_signin_photo）→ POST sign-in（photoAssetId 必填）
     → signInMeta 记 IP/UA/遮挡检测结论/时间
  ③ 回避确认 + 保密承诺（法定须本人操作）→ 进入评审
```

### 4.2 强化模式（host 态，可选启用）

`EXPERT_IDENTITY_VERIFY=host` 时，在 4.1 的 ① 之前加主持人闸门：向导第 1 步锁定显示「待主持人核验」；主持人（:3007 桌面端）核对 人↔证件↔名单 后「核验登记」（证件类型**不存号码**+备注）→ 专家端 10s 轮询自动解锁（实施注 2026-09-20：WS 未接，轮询覆盖时效）；误登记可撤销（原因必填，**已签到专家 409 `VERIFY_LOCKED` 拒撤**——防证据链回退）。核验权 = 主持人 primary + admin 兜底，核验人落库（identityVerifiedBy/ByName）。**默认不启用**；需要更严场次的集团/项目自行开启。

- 端点：`POST .../expert-verification/:expertId/verify`（docType 白名单 + note?）/ `unverify`（reason 必填）；登记与撤销写监督日志（`身份核验登记`/`身份核验撤销·关注`）；
- signIn 闸门顺序：host 态先查 `identityVerified`（403 `IDENTITY_NOT_VERIFIED`）→ 再查照片（`PHOTO_REQUIRED`）——与 spec「拍照前拦截」一致；
- 专家端 `getProject` 下发 `identityMode` + myExpertRecord 的 identity 字段（P3 起）；self 态恒 self、字段恒 false/null，无行为变化。

### 4.3 模式闸

`EXPERT_IDENTITY_VERIFY=self|host|off`（env，重启生效，对齐 `BID_DUAL_ENVELOPE` 先例）。`off` 仅限应急（摄像头故障）——留档照可选、签到放行，切换与使用均落监督日志。

### 4.4 核验异常登记（R5）

```
主持人从矩阵发现：留档照与专家不符 / 照片异常（遮挡未检出、明显非本人）/ 到场异常
  → :3007「核验异常登记」：异常类型（人证不符/照片异常/到场异常）+ 说明
    → 监督日志异常事件（riskFlag=高风险）+ 监督视图时间线
    （实施注 2026-09-20：WS 广播未接——:3007 矩阵经 onChanged 即时刷新 + 30s 轮询覆盖时效，
     监督视图时间线读日志表；不动共享 socket 文件，如现场要求秒级推送再补）
  → 处置走既有路径：异议裁决 / 流标（:3007）
```

- **闭环修复（2026-09-20 评审后）**：① 登记幂等——同一专家存在未撤销异常时重复登记返回 already（防重复高风险记录污染证据）；② **撤销异常登记**（`unreject`，reason 必填）——误报可更正：不删原记录，追加「核验异常撤销·关注」更正日志，两条并载监督时间线/签字包；矩阵按时间序折叠显示生效状态（异常徽章+tooltip，撤销后按钮还原为「异常」）；③ 权限放宽 leader/staff 可登记/撤销（监督身份多为此角色，纯留痕低风险；manual-confirm 仍主持人专属）；④ 异常按钮仅正选行；⑤ 按钮定位=事后抽查/举报记录工具（非逐人巡检——40px 缩略图不足以支撑巡检定位）；
- **评标中不设专家替换**（2026-09-20 用户裁定，业务规则优先）：专家提前抽取、开标后不可替换——曾实现的评标中替换端点/按钮/弹窗已按此规则**整组移除**（服务端/DTO/测试/前端/签字包过滤）；早期 D1 决策（评标中替换仅归 :3007）随本条作废；
- 评标前替换不变：:3005 开标确认面板「正选候补替换」（`swapExpertRole`，开标前窗口——EVALUATING/ARCHIVED 拒 409 `EXPERT_SWAP_LOCKED` 既有禁令，符合「开标后不可换」）；
- 核验事件证据链：`身份核验降级/核验异常` 两类监督日志随签字包「核验记录表」附注披露（verifyEvents）。

### 4.5 证据链：签字包 / 回流包 / 归档

- :3007 核验矩阵（新，被动展示）：专家 × 签到状态 × 留档照（缩略可放大）× 拍照时间 × 检测结论 × IP/UA；host 态另示核验人/证件类型；
- 个人评分确认表「身份核验」行：`身份证号登录 + 留档照（遮挡检测通过）· 2026-09-18 09:12`（host 态追加 `主持人核验 · 核验人`）；历史数据 null 渲染「未记录」；
- 签字包监督附件「核验记录表」：全专家 × 登录方式 × 留档照 × 时间 × 检测结论；**手动确认行**：方式列「主持人现场确认（理由）」、留档照列「无（主持人确认）」；
- 回流包 JSON 同步核验摘要；归档闸门**不变**（核验完成度只读展示，不设新闸门）。

### 4.6 摄像头故障降级：主持人手动确认（R9，2026-09-20 裁定）

**背景**：单工位摄像头损坏时，self 态拍照硬闸（400 PHOTO_REQUIRED）会阻塞该专家签到。现场出路按优先级：① 换有摄像头设备登录签到（签到态在 DB，换设备不阻塞评标）；② 插 USB 摄像头重试；③ 本节的手动确认通道。

**通道设计**：
- 端点 `POST /bid/projects/:id/expert-verification/:expertId/manual-confirm`（:3007，`@Roles('bid_host','admin')`——主持人 primary、admin 兜底；leader/staff 不给）；
- 入参：`reason` 必填（≤200 字，如「摄像头故障」）+ 可选 `docType`（身份证/护照/其他，不存号码）；
- 校验：阶段 OPENING/EVALUATING；仅正选（对齐 signIn 门控）；已签到幂等返回（不重复写）；
- 落库：`BidExpert.signedIn=true` + `signInMeta={method:'manual_confirm', timestamp, confirmedByName, reason, docType?}`（signInIp=null，确认人信息入 meta）+ `BidSupervisionLog`（action=`身份核验降级`，含确认人/理由，`riskFlag='关注'`）——监督视图时间线可见；
- 矩阵/签字包渲染：矩阵徽章「主持人确认」+理由 tooltip；核验记录表方式列「主持人现场确认（理由）」；留痕行「无留档照（主持人现场确认）」——证据自含；
- 专家端：签到态在 DB，刷新即走「已签到」分支继续评审，前端零改动；
- **为什么不是 admin 全局 off**：粒度粗（一人坏全场免照片）、决策者不在现场、证据为零；全局 off 仅作大面积故障的最后手段（env + 重启，暂不做运行时开关，详见 R9）。

## 5. 数据模型（Prisma 增量）

```prisma
model BidExpert {
  // ... 现有字段
  // ── phoneVerified 列删除（4d224c65 已删链路；历史数据无真实核验语义，不迁移）──
  // ── 以下四列仅 host 态使用（默认 self 态为 null；列保留供强化模式，避免二次迁移）──
  identityVerified       Boolean   @default(false)
  identityVerifiedAt     DateTime?
  identityVerifiedBy     String?   // 核验人 userId（主持人/admin）
  identityVerifiedByName String?   // 核验人姓名快照（签字包证据自含）
  identityDocType        String?   // 身份证 | 护照 | 其他（不存号码——最小化）
  identityNote           String?   // 核验备注 / 撤销原因
}
```

- `signInMeta` 存照片 assetId/IP/UA/遮挡检测结论诊断明细；签字包/报表读端只读显式列；
- `ExpertProfile.idNumber`（已有列）为默认口令来源（R2），入库完整性审核（A-218 既有概念）应覆盖「身份证号非空」；
- 无新表（工位绑定相关模型随 R7 移除，不落地）；
- 共享 `schema.prisma` 高危文件：并行会话约定（对方工作区干净时改 + 提交内附迁移 + `npx prisma validate`）。

## 6. API 设计（摘要）

| 端点 | 门户 | 鉴权 | 说明 |
|---|---|---|---|
| `POST /expert/projects/:id/sign-in` | :3006 | bid_expert | photoAssetId 必填（400 `PHOTO_REQUIRED`；off 态除外）+ 归属校验；host 态另校验 identityVerified（403 `IDENTITY_NOT_VERIFIED`）|
| `GET /bid/projects/:id/expert-verification` | :3007 | admin/bid_host/leader/staff | 核验矩阵：签到状态/留档照/检测结论/IP/UA（host 态含核验字段）|
| `POST .../expert-verification/:expertId/verify` | :3007 | 主持人/admin | host 态核验登记（docType 白名单 + note?）|
| `POST .../expert-verification/:expertId/unverify` | :3007 | 主持人/admin | 撤销误登记（原因必填，签到重锁）|
| `POST .../expert-verification/:expertId/reject` | :3007 | 主持人/admin | 核验异常登记 → 异常事件 + 处置联动 |
| `POST .../expert-verification/:expertId/manual-confirm` | :3007 | 主持人/admin | **R9**：摄像头故障等降级——主持人手动确认签到（reason 必填 + docType?；监督日志；逐人） |

- 登录链路**零改动**（账密登录既有）；无设备注册/轮询/凭证端点（R7 移除后不复存在）；
- 阶段前置：verify/unverify/reject/manual-confirm 仅 OPENING/EVALUATING；新路由显式 `@Roles`；curl 调试带 `X-Portal`。

## 7. 安全设计

- **误开页面零干扰面**：登录页即普通账密页——无工位注册、无列表、无可领内容；试错有限流（10/min 已有）、口令哈希既有；
- **R2 凭证权衡（如实记录）**：身份证号默认口令是便利性换口令熵（姓名+身份证号对内部知情人可猜）——已知弱点，接受理由：留档照提供事后追责证据、:3007 现场可视、更严场次可开 host 态；改密走既有审批流程。可选加固（backlog）：登录异常告警、异地/非评标时段登录提醒；
- **R3 检测的执行边界（如实记录）**：遮挡检测跑在客户端，防的是「废照片」（拍墙/拍纸/遮挡），不防蓄意攻击（决心造假者可绕过客户端检测）——它保证的是**证据可用性**而非身份真伪；身份锚点 = 身份证号口令 + host 态人证 + 事后追责；
- 照片归属校验（uploaderId=本人、类目正确）沿用既有 `expert_signin_photo` 机制。

## 8. 合规

- **零生物特征**：个保法 §28/29 敏感个人信息义务不触发。R3 的遮挡检测是**检测非识别**——运行于浏览器、判定即弃帧、不产生任何生物模板/特征/比对记录；留档照为普通个人信息（沿用既有类目与权限），与今日已有的签到照同性质；
- 证件信息最小化：口令只以哈希形态参与认证；host 态仅记证件类型不存号码；
- **26 号令 §7「宜具备人脸功能」偏离留痕**：本系统未采集（推荐性条款），决策记录在案（R1），对齐 GB/T 43711「非依法必招放行+偏离写监督日志」分级先例；
- §21 防请托管理措施：证件凭证绑定 + 逐次留档照 + 全程留痕 + 异常处置闭环 ✓。
