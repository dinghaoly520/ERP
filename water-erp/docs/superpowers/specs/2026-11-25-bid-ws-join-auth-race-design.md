# 设计：开标实时通道「入会先于连接鉴权完成」竞态修复

> **状态**：待用户审核（方案已选定，2026-11-25：方案甲——服务端让入会等鉴权完成 + 前端入会检查应答并重试）。本文件只含设计，不含实施计划；批准后再写实施计划。
> **来源**：2026-11-25 修 e2e 时发现 `opening-hall` 套件间歇失败，追查出开标实时网关的时序漏洞；经复现实验核实后用户要求修复。
> **用户裁定（2026-11-25）**：① 按方案甲做，服务端与前端都改；② 入会因业务原因被拒时前端表现维持现状（界面不提示）；③ 范围只限入会这一个处理。
> 下文 `bid.gateway.ts` 指 `apps/api/src/bid/bid.gateway.ts`；四个 hook 指 `apps/{bid-portal,web,supplier-portal-next}/src/hooks/use-bid-websocket.ts` 与 `apps/expert-portal/src/hooks/use-expert-websocket.ts`。行号以提交 `e6d79d4f1` 为准。

## 1. 要达成什么

客户端连上开标实时通道后立刻申请加入项目房间，不再因为「服务端还没完成身份校验」被误判为未授权。

- **校验慢也要入会成功**：只要令牌有效，无论身份校验花多久，入会最终必须成功。
- **校验失败的口径不变**：无效令牌、被顶掉的会话，仍然连不上或入会被拒，应答格式不变。
- **旧页面也受益**：服务端修复上线后，已经部署的前端不改也能好。

**为什么是现在**：这是一个静默故障——出错时界面显示「已连接」，但页面不再实时更新，用户只能靠刷新发现。受影响的是供应商、评审专家（含平板）和采购管理工作台的内部账号，场景是开标大厅和评分室。

**怎样算失败（反目标）**

- 修复后任何现有的鉴权口径变松：不该连的连上了，不该入会的入会了。
- 应答格式或事件名变化，导致已部署的页面需要跟着改才能用。
- 界面上「已连接 / 重连中 / 已断开」的含义变化，或新增界面状态。
- 为了这个修复去重构整个连接处理，或改动通知、聊天两个网关的行为。
- `opening-hall` 的 e2e 继续间歇失败。

## 2. 现状（读码与实验）

### 2.1 服务端时序

`bid.gateway.ts` 的 `handleConnection`（L195–288）是异步的，身份要经过两步 `await` 才写到连接上：

1. `await jwt.verifyAsync(token)`
2. 令牌带会话编号（`sid`）时，`await prisma.user.findUnique` 与库里的 `webSessionId` 对账（平板配对令牌还会再查一次 Redis）
3. 之后才写 `socket.data.userId / role / isHost`

`handleJoinProject`（L377 起）一进来就读 `socket.data.userId / role`，缺任何一个就返回 `{ error: 'UNAUTHORIZED' }`。连接被放进项目房间只发生在这个方法里，被拒后没有任何地方会重做。

框架侧已核对已安装源码（Nest 11.1.26、Socket.IO 4.8.3）：

- Nest 在命名空间的 `connection` 事件里**同步**调用 `handleConnection`，不等待它返回的 promise（`web-sockets-controller.js` 的 `subscribeConnectionEvent`）。
- Socket.IO 在 `namespace.js` 的 `add()` 里，先 `socket._onconnect()`（写入连接成功包），再触发 `connection` 事件——两者与 `handleConnection` 的同步部分在同一个调用栈里。
- 因此客户端收到「连接成功」并发出第一条消息，必然在之后的一轮事件循环。**只要在 `handleConnection` 的第一个 `await` 之前把东西挂到连接上，入会处理执行时它一定在。**
- Nest 在实时通道上不挂任何中间件，全局的认证与角色守卫也只管 HTTP，不经过这里。

### 2.2 受影响范围

| 登录身份 | 令牌 | 带会话编号 | 是否受影响 |
|---|---|---|---|
| 供应商（:3004） | `token_supplier` | 是 | **受影响** |
| 评审专家、平板（:3006） | `token_expert`、配对令牌 | 是 | **受影响** |
| 工作台内部账号（:3005） | `token_web` | 是 | **受影响** |
| 开评标管理端主持人与内部角色（:3007） | `token_bid` | 否 | 不受影响（校验不查库，只有一个微任务） |

通知网关和聊天网关不受影响：通知由服务端在鉴权完成后直接把连接放进用户房间，不靠客户端申请；聊天的校验不查库，它的客户端也不在连接时发消息。

### 2.3 前端

四个 hook 的写法一致：`connect` 回调里先把状态置为 `connected`，随即 `socket.emit('join:project', projectId)`，**不带应答回调**。

- 服务端回了「未授权」前端不知道，界面仍显示已连接。
- 心跳的 `ping` / `pong` 不依赖身份，也不依赖是否在房间里，所以照常通过，不会触发断线重连。
- 页面切到后台会断开、切回来重连——这是一次新的连接，又是一次新的机会，而不是对失败连接的补救。

各门户的 hook 没有任何单测；`bid-portal` 没有测试脚本。

### 2.4 复现实验（2026-11-25，隔离环境，供应商令牌）

| 条件 | 结果 |
|---|---|
| 把连接校验里的数据库查询人为放慢到 80ms，连上立即入会 | 10 次中 9 次被拒 |
| 同样条件，连上后等 400ms 再入会 | 5 次全过 |
| 同样条件，主持人令牌 | 10 次全过 |
| 不加延迟，连上立即入会，580 次 | 41 次被拒，约 7% |

线上发生频率没有数据。本机约 7% 是因为校验查询与入会申请都是一两毫秒量级；线上有网络延迟应该更低，但数据库变慢时会升高。

## 3. 方案比较

| 方案 | 做法 | 取舍 |
|---|---|---|
| **甲（选定）** | 服务端让入会等鉴权完成；前端入会带应答、被拒则重试 | 改动小、协议不变；服务端上线即对所有客户端生效，前端重试在新前端对旧服务端时兜底 |
| 乙 | 把鉴权前移到握手阶段，连接建立前就验完 | 概念上最干净，但要重构整个连接处理，坏令牌的报错方式也会变，在开标这种关键通道上回归风险高 |
| 丙 | 只改前端，加延时或重试 | 服务端的漏洞还在，旧页面和其他调用方照样会撞上 |

## 4. 服务端设计（`bid.gateway.ts`）

**1. 把鉴权主体抽成私有方法，并在第一个 `await` 之前挂到连接上。**

```
async handleConnection(socket) {
  const authReady = this.authenticateHandshake(socket);   // 现有鉴权逻辑原样搬入
  socket.data.authReady = authReady;                       // 必须先于本方法的任何 await
  await authReady;
}
```

- `authenticateHandshake` 的内容就是现在 `handleConnection` 的主体：无令牌、验签失败、载荷缺字段、会话对账失败、配对已失效，一律照旧 `socket.disconnect(true)` 后返回。每条路径都以返回结束，promise 必然结束，不会悬挂。
- 不改变任何鉴权口径，只是换了位置。

**2. `handleJoinProject` 开头先等鉴权。**

```
await this.awaitHandshakeAuth(client);
// 之后是现有逻辑，不动
```

- 有 `authReady` 就等它结束再往下；没有（单测里直接构造的连接对象）就跳过，行为与现在完全一致。
- 鉴权失败时连接已被断开，等到的是「身份缺失」，往下走仍返回 `{ error: 'UNAUTHORIZED' }`，与现状一致。
- 鉴权慢时入会相应延后，完成后正常入会。
- 等待期间鉴权万一抛错，不向外抛，按身份缺失处理，同样落到未授权分支。
- 应答格式、进房逻辑、`leave:project` 和其他处理都不变。

**3. 不做的事。** 不改 `leave:project` 等其他处理（它们只在入会成功后才有意义）；不改通知与聊天网关；不给 `socket.data` 引入完整类型（现有二十多处 `as any`，不为这个修复做大范围改写）。

## 5. 前端设计（四个 hook）

**1. 每个门户放一个小的纯函数文件（暂定 `src/lib/ws-join.ts`）**，不依赖 React，便于单测：

- `joinProjectWithRetry(socket, projectId, options)`：带应答地发 `join:project`；应答是 `UNAUTHORIZED` 且还有次数就隔一会儿重发；否则把应答原样返回。
- 默认值：最多 3 次，间隔 150ms → 300ms → 600ms；等应答最多 5 秒。
- 提供 `isStale()` 回调：连接已不是当前连接（重连、切项目、手动关闭）时立即停止，不再重发。

**2. hook 的 `connect` 回调改用它。**

- 把状态置为 `connected` 的时机不变，界面语义不变。
- 重试耗尽仍是 `UNAUTHORIZED`，或等不到应答：断开这条连接，走现有的断线重连路径（已有退避与次数上限）。
- 应答是其他错误（「不是本项目成员」「跨公司无权访问」等）：保持现状，不重试、不提示，只记一条控制台告警。
- 连续几次连接都入会失败时停止自动重连，状态停在 `disconnected`，避免新前端对旧服务端时陷入紧密重连。

**3. 四份保持一致。** 项目惯例是各门户自包含、`bid-portal` 与 `web` 两份 hook 双向同步，所以不抽共享包。`bid-portal` 今天不受这个漏洞影响（主持人令牌不查库），改它只为四份代码一致。

**4. 调用方不用改。** hook 的入参、返回值、事件回调都没变；受影响的页面有：采购管理工作台的开标确认面板，开评标管理端的项目工作区与交流抽屉，供应商门户的开标大厅、轮次报价与聊天面板，专家门户的桌面与平板评分页。

## 6. 测试与验收

**先写失败的测试，再改代码。**

| 层 | 内容 | 修复前 |
|---|---|---|
| 网关单测（`bid.gateway.spec.ts` 新增一组） | 会话对账故意放慢 30ms，不等待 `handleConnection` 立即入会，必须返回成功 | 必红 |
| 同上 | 会话对账不匹配，入会返回未授权且连接被断开 | 已绿（回归保护） |
| 同上 | 不带会话编号的主持人令牌，立即入会成功 | 已绿（回归保护） |
| 同上 | 现有「无身份连接入会被拒」用例 | 必须仍然绿 |
| e2e（`opening-hall.e2e-spec.ts` 新增一条） | 会话对账放慢到 300ms，供应商连接后立即入会，必须成功 | 必红（实验中放慢 80ms 时 10 次有 9 次被拒，加大延迟以确保必红） |
| 前端单测（纯函数，用假连接对象） | 未授权两次后成功；业务错误不重试；等不到应答；连接已作废 | 新增 |

纯函数文件的位置要让各门户的测试脚本能扫到：`web` 放 `src/lib/`，`supplier-portal-next` 与 `expert-portal` 放 `src/lib/__tests__/` 对应目录。`expert-portal` 用 Node 直接跑 TypeScript，纯函数文件不能用到需要转译的语法。`bid-portal` 没有测试脚本，不加测试文件，靠类型检查和与其他三份逐字一致来保证。

**验收：**

- 上述测试由红变绿；API 全量单测、四个门户的类型检查与单测都过。
- 隔离环境里从空库全量跑 e2e，本机时区与 UTC 各至少两轮，`opening-hall` 不再出现入会未授权。
- 推送后 CI 的 e2e 作业转绿。

## 7. 兼容、部署、风险

- **协议不变**：应答格式、事件名都没变，已部署的页面不改也能用。
- **部署顺序随意**：服务端先上线，对所有页面生效；前端单独上线，带重试的版本对旧服务端也兜得住。
- **风险低**：服务端只增加「等待」。唯一的新情形是鉴权一直不结束时入会也一直等——现有代码里对账抛错会落到断连分支、使 promise 结束，连接池取连接也有超时，前端等应答另有 5 秒上限。

## 8. 不在范围

- 入会因业务原因被拒时在界面上提示（用户裁定维持现状）。
- 重连后的全量刷新目前发生在「连接成功」时，略早于入会完成，有一个很小的丢事件窗口。这次不动，记为后续项。
- 上传恰好 500MB 整被拒的边界问题，另行处理。
