# 智慧水发·蜀水云采 ERP 功能板块与泳道图规划

- 编制日期：2026-09-01
- 文档状态：泳道图绘制前规划稿
- 适用对象：业务汇报、产品需求评审、研发与测试交接
- 当前范围：只规划图谱、泳道、节点和边界，不绘制图形
- 术语说明：本文将需求中的“甬道图”统一按业务流程“泳道图”理解

## 1. 规划结论

本系统不适合按前端门户“一端一张图”直接绘制。当前业务跨越采购管理端、公共门户、供应商端、专家端、开评标端、商城、AI 助手、大屏和统一 API，同一项目还会在多个角色、多个状态机和多个文件体系之间流转。若按门户分图，图容易对应代码，但会切断真实业务；若只画一张端到端大图，又会因节点过多而失去可读性。

建议采用“1 张总览图 + 9 个功能板块 + 17 张专项泳道图”的混合图谱，共 18 张图：

1. 总览图负责解释平台全生命周期和各门户分工。
2. 专项图按业务闭环拆分，不按页面或 API 机械拆分。
3. 每张专项图同时标出参与角色、承载门户、关键系统动作、数据产物和异常分支。
4. 登录鉴权、通知、文件、AI、审计、监督等横向能力在相关流程中落点，不再单独画成脱离业务的技术图。

## 2. 项目现状取证与边界

### 2.1 本次规划依据

本规划以 2026-09-01 当前工作区代码为主，重点核对了：

- `apps/api/src/app.module.ts` 中的 50 余个业务模块装配关系。
- `apps/api/prisma/schema.prisma` 中的项目、采购、供应商、投标、开标、专家、评分、合同、目录、档案、审计等实体和状态机。

- 各 NestJS Controller 的实际端点，而非只参考旧版项目概览。

### 2.3 当前代码与旧文档的主要差异

- 采购管理工作台已经包含项目全生命周期、采购文件编写/审查、阶段合规、归档、账号与企业管理等能力，不再只是供应商/专家/公告后台。
- 专家评审实际已超过早期“五步评审”，当前应按七步主链理解：身份与承诺、标书获取、AI 辅助、条款响应核对、独立评分、评分复核、报告确认。
- 开评标端当前包含开标大厅、评标管理、评分标准只读、评标签字、报价轮次、监督视图等工作区。
- 供应商端已经扩展到 U 盾、双信封投标、在线开标确认、异议投诉、供货申请、框架协议、合同履约等能力。
- 归档已经形成以 `ProjectManagementItem` 为卷、阶段材料归集、四性检测、ASIP 导出、移交登记和长期保留闸门的独立业务域。

因此，后续泳道图必须以当前实现为基线，并在图上明确“业务现状”与“异常/待确认分支”，避免继续传播旧版五阶段或五门户口径。

## 3. 方案比较与推荐

| 方案 | 组织方式 | 优点 | 主要问题 | 结论 |
|---|---|---|---|---|
| 按门户分图 | 公共端、供应商端、专家端等各一张 | 容易对应代码和责任团队 | 同一业务被切成多段，跨端交互难理解 | 不作为主方案 |
| 按生命周期分图 | 需求、立项、投标、开标、评标、合同、归档 | 业务汇报清晰 | 账号、资源库、商城、AI 等横向能力易遗漏 | 可作为总图结构 |
| 混合图谱 | 一张总图，专项图按业务闭环拆分，并标注门户/服务 | 同时兼顾业务可读性和系统可追溯性 | 需要统一图例和编号管理 | 推荐方案 |

## 5. 统一绘图规范

### 5.1 图面结构

- 时间方向统一为从左到右，泳道自上而下排列。
- 一张图控制在 4～7 条泳道、12～24 个主节点。超过 7 条泳道或 24 个主节点时，应拆成主图和子图。
- 角色泳道在上，门户/业务服务泳道居中，数据/审计/外部系统泳道在下。
- 业务动作使用“动词 + 对象”，例如“提交立项审核”“生成投标回执”；避免只写页面名或按钮名。
- 跨门户跳转必须在连线上标注目标端，例如“跳转供应商门户”“推送至开评标端”。
- 每张图只表达一个清晰闭环。跨图衔接使用统一连接点编号，如 `E01-END → E02-START`。

### 5.2 推荐图形语义

| 图形 | 语义 |
|---|---|
| 圆角矩形 | 人工或系统处理动作 |
| 菱形 | 业务判断、状态闸门、是否通过 |
| 文档形 | 公告、采购文件、投标文件、报告、合同、归档包等成果物 |
| 数据库形 | Prisma 业务记录、对象存储、日志/归档库 |
| 消息形 | 站内信、短信/邮件、WebSocket 事件、邀请链接 |
| 粗边框节点 | 法规/合规硬闸或不可跳过的阶段门 |
| 红色旁路 | 失败、拒绝、退回、超时、争议、流标等异常分支 |
| 虚线节点 | 外部依赖、规划能力或生产环境替换点 |

### 5.3 颜色建议

- 深蓝：采购方/内部管理动作。
- 青蓝：平台自动处理、状态机和数据同步。
- 绿色：供应商动作或成功闭环。
- 紫色：专家、AI 辅助和评审动作。
- 橙色：审核、监督、合规检查和人工复核。
- 红色：驳回、超时、异常、争议、废标/流标。
- 灰色：归档、只读回看、外部系统或暂不实施能力。

### 5.4 现状与规划标记

- `[现]`：当前代码存在真实页面、端点或数据模型。
- `[自动]`：调度器、队列、状态机或事件驱动自动完成。
- `[人工]`：线下或人工判断后在系统登记。
- `[异常]`：必须画出的失败/争议分支。
- `[外部]`：CA、短信、监管平台、档案系统等外部依赖。
- `[待确认]`：业务规则尚需业主或制度明确，不能假定为系统自动决定。

## 6. `G00` 平台采购全生命周期总览图

### 6.1 图的目的

用一张图回答“平台有哪些参与方、一个采购项目如何从需求走到合同和归档、各门户分别在什么时候介入”。该图用于领导汇报和全项目开篇，不承载字段级或异常级细节。

### 6.2 建议泳道

1. 需求部门/采购申请人
2. 采购经办/项目负责人（`:3005`）
3. 审批人/监督人
4. 供应商（`:3004`）
5. 开标主持人（`:3007`）
6. 评标专家（`:3006`）
7. 平台服务/AI/档案

### 6.3 主干节点

`提出采购需求 → 编制立项 → 审核通过 → 生成项目与阶段计划 → 编写/审查采购文件 → 发布公告或定向邀请 → 供应商获取文件 → 加密投标/报价 → 在线开标与确认 → 专家抽取与评审 → 生成评标结果 → 公示与异议处理 → 发出成交通知书 → 合同签署与履约 → 项目评价 → 四性检测与归档移交 → 驾驶舱沉淀指标`

### 6.4 必画分支

- 采购方式分支：谈判采购、竞价采购、直接采购、邀请招标、询比采购的阶段不同。
- 审核驳回返回需求/立项修改。
- 公告型项目与定向邀请型项目分流。
- 投标不足、解密失败、评审废标、流标后再次采购。
- 公示期异议未闭环时不得直接进入最终结果闭环。
- 合同终止与正常履约验收分流。

### 6.5 图面建议

总图最多保留 16 个主节点；文件、通知、日志等横向能力只用底部能力带表示，不展开细节。图尾列出本图向 `A01`～`I01` 的下钻索引。

## 7. A 板块：平台入口与治理

### `A01` 统一登录、账号企业与权限治理泳道图

**目标与边界**

覆盖用户注册/登录、企业选择、角色识别、门户跳转、账号审核冻结、资料/密码变更审批、会话失效和审计留痕。它不展开供应商企业准入细节，供应商注册业务转入 `D01`。

**建议泳道**

1. 用户/注册申请人
2. 公共门户或各专属登录页
3. Auth/Verification API
4. 管理员/企业管理员
5. 角色与端口守卫
6. 目标业务门户
7. OperationLog/AuditLog

**主流程**

1. 用户选择登录或注册，并选择/识别所属企业。
2. 注册时校验验证码、用户名、企业、角色和重复信息，生成待审核记录。
3. 管理员审核注册申请；通过后激活账号，拒绝则记录原因并通知申请人。
4. 登录时校验密码、账号状态和目标门户来源。
5. Auth 服务签发对应门户 Cookie，解析角色和企业范围。
6. `ROLE_PORTAL`/落地规则将用户送入采购、供应商、专家、商城或开评标门户。
7. 全局 `AuthGuard`、`PortRouteGuard`、`RolesGuard` 在每次请求执行身份、门户和角色校验。
8. 登录、审批、冻结、重置密码、资料变更等动作写入操作日志。

**必须画出的判断与异常**

- 账号待审核、已冻结、已停用、密码错误、目标门户不匹配。
- 同一用户名存在多角色时的角色/入口选择。
- Session 过期、心跳失败后重新登录。
- 密码修改、密码找回、个人资料变更需要审批的分支。
- 管理员冻结、解冻、删除账号以及公司数据范围更新。

**关键数据产物**

`User`、`Company`、`Department`、`RegistrationReview`、`PasswordChangeRequest`、`PasswordResetRequest`、`ProfileChangeRequest`、登录历史、操作日志。

**当前实现映射**

`apps/api/src/auth/*`、`apps/api/src/company/*`、`apps/api/src/common/guards/roles.guard.ts`、`packages/config/src/urls.ts`、公共门户登录页、采购管理端 `/admin/accounts` 与 `/admin/companies`。

## 8. B 板块：采购协同与项目管理

### `B01` 采购需求、立项、计划、团队与工作协同泳道图

**目标与边界**

覆盖采购项目进入正式招采流程之前和全过程中的内部协同：需求资料、立项申请、审核受理、采购方式确定、项目编号、阶段计划、项目团队、工作安排和进度反馈。采购文件的具体编写审查转入 `C01`。

**建议泳道**

1. 需求部门/申请人
2. 采购经办人
3. 项目负责人/审批人
4. 采购管理工作台
5. OCR/AI 辅助
6. 项目计划与工作安排服务
7. 通知/流程中心

**主流程**

1. 上传采购需求或立项材料，也可手工录入需求字段。
2. OCR/AI 提取项目名称、预算、采购范围、供方要求等结构化信息。
3. 经办人核对并补充采购方式、类别、组织形式、风险措施、标段方案和时间安排。
4. 创建 `ProjectManagementItem`，生成项目编号和九阶段时间轴。
5. 提交审核；审批人受理、通过或驳回。
6. 审核通过后建立项目计划项和项目团队，明确负责人、成员、截止时间和依赖。
7. 系统根据阶段、模板和到期时间生成工作安排、待办与提醒。
8. 经办人执行任务、记录进展/洞察、调整计划；负责人复核计划或阶段成果。
9. 阶段完成时执行材料/合规闸门，解锁下一阶段并更新进度驾驶舱。

**必须画出的判断与异常**

- 采购方式决定阶段集合：是否需要供应商邀请、公开公告、采购文件。
- 审核驳回后返回修改并再次提交。
- 阶段必备材料缺失时禁止完成；有制度依据时可填写理由豁免并留痕。
- 工作安排阻塞、逾期、延期提醒、依赖任务未完成。
- 流标后“再次采购”创建新轮次并复用早期材料。
- 项目回收、恢复、完成、归档后的只读状态。

**关键数据产物**

`ProjectManagementItem`、`ProjectManagementStage`、`ProjectPlanItem`、`ProjectTeamMember`、`WorkArrangement`、阶段附件及版本、审核意见、项目时间线。

**当前实现映射**

`:3005 /projects`、`/procurements`、`/work-arrangements`、`/workflow`、`/progress`；API `project-management`、`project-plan`、`work-arrangements`、`workflow`、`procurements`。

## 9. C 板块：采购文件与信息公开

### `C01` 采购文件编制、AI 辅助与合规审查泳道图

**目标与边界**

说明采购文件如何从历史资料/模板形成草稿，经 AI 辅助、规则审查、人工整改和版本固化后进入项目阶段。公告发布另见 `C02`。

**建议泳道**

1. 采购经办人
2. 采购文件编写工作区
3. OCR/AI/知识库
4. 合规规则与审查任务
5. 审查人/项目负责人
6. 项目管理与文件存储

**主流程**

1. 选择空白模板、历史文件、样本库或导入现有 DOCX。
2. OCR/结构提取形成字段和章节草稿。
3. AI 生成/润色需求、评审办法、合同条款、公告字段等内容。
4. 经办人编辑并导出草稿，上传到采购文件阶段。
5. 发起合规审查，规则引擎与 AI 识别问题、风险等级和法规依据。
6. 审查人逐项确认：接受、整改、说明或误报。
7. 经办人修订文件，系统保留版本、差异和修改摘要。
8. 全部关键问题闭环后生成审查结果，固化采购文件版本并允许阶段完成。

**必须画出的判断与异常**

- 文件格式不支持、OCR 失败、AI 超时或仅部分章节解析成功。
- 高风险问题未解决时禁止提交正式版本。
- 已发布或后续阶段已启动时，修改必须走版本/补遗流程，不能覆盖历史文件。
- 审查规则来自内置基线或数据库配置的分支。

**关键数据产物**

采购文件 DOCX、`ReviewTask`、`ComplianceRule`、问题清单、审查报告、`AttachmentVersion`、字段样本和历史文件记录。

**当前实现映射**

### `F03` 委员会议事、澄清、结果生成与评标签字泳道图

**目标与边界**

覆盖独立评分完成后的集体议事：澄清、动议、投票、异议、结果生成、报告确认、组长末签、纸质/扫描签字登记和回流移交。

**建议泳道**

1. 普通专家
2. 评标组长
3. 专家门户
4. 开标主持人/评标管理端
5. 供应商书面答复端
6. 议事与结果服务
7. 签字/回流/审计

**主流程**

1. 全部正选专家完成评分和复核。
2. 专家可发起澄清、程序/评分异议或委员会动议。
3. 需要供应商答复时发送书面澄清，供应商在线签名答复或主持人登记线下答复。
4. 委员会查看原文、附件和 AI 摘要；动议进入投票并由有权人关闭。
5. 未解决异议、废标决议和澄清未闭环时阻断结果生成。
6. 系统聚合有效专家评分，应用价格公式、废标状态和排名规则，生成评标结果。
7. 每位专家查看报告并确认或填写不同意见。
8. 组长完成末签；评标管理端生成签字包。
9. 扫描签字页/不同意见书，逐专家登记签字状态。
10. 全部签字闭环后生成评标回流包，交采购管理端定标和归档。

**必须画出的判断与异常**

- 澄清是否改变投标文件实质性内容，由委员会人工判断并留痕。
- 动议法定人数、赞成/反对/弃权和票数不足。
- 未解决专家异议、供应商未答复、评标超时。
- 评标结果重新生成后，旧签字包应失效并重新签字。
- 专家拒绝确认报告或提交不同意见。
- 签字扫描缺失、人员登记不一致、回流包未完成。

**关键数据产物**

`BidClarification`、供应商答复签名、`BidMotion`、`BidVote`、`ExpertDispute`、`BidEvaluationResult`、评标报告、`BidSignPacket`、签字扫描件、评标回流包。

**当前实现映射**

专家端报告/澄清/动议/异议，`:3007` 评标管理与评标签字，供应商端项目澄清页；API `expert`、`bid/clarifications`、`bid/evaluation-results`、`bid/sign-packet`、`supplier-portal/bid-clarifications`。

## 13. G 板块：定标、履约与归档

### `G01` 定标、公示、异议投诉与成交通知书泳道图

**目标与边界**

覆盖评标结果回流后，从候选人/预成交公示到异议闭环、最终成交公告和通知书送达签收的过程。

**建议泳道**

1. 采购经办/定标责任人
2. 采购管理端
3. 公告服务/公共门户
4. 供应商门户
5. 异议投诉处理人
6. 通知与审计

**主流程**

1. 接收评标回流包，核对排名、报价、资格复核和签字状态。
2. 生成定标文件并确认推荐成交供应商。
3. 发布预成交公示，设置公示截止时间。
4. 供应商或利害关系人提出文件、资格或结果异议并上传附件。
5. 采购方答复；必要时升级为投诉并登记监管处理结果。
6. 公示期届满且异议已闭环后确认成交供应商。
7. 发布成交公告，生成成交通知书。
8. 通知书送达到中标供应商；供应商打开、签收并确认已收到。
9. 项目进入合同准备阶段。

**必须画出的判断与异常**

- 公示期是否届满、是否存在未办结异议。
- 异议答复、转投诉、关闭三种路径。
- 定标与评标推荐不一致时的审批和说明留痕。
- 通知书送达失败、未打开、未签收和重新发送。
- 流标公告与正常成交公告分支。

**关键数据产物**

预成交公示、异议/投诉工单、答复记录、成交公告、`AwardLetterDelivery`、签收时间、定标附件和通知记录。

**当前实现映射**

`:3005` 项目定标/文件制作、公告中心、异议看板；供应商端 `/objections`、`/award-letters`；API `announcement`、`objections`、`bid/award-letter`。

### `G02` 合同编制、审查、签署、履约验收与供应商评价泳道图

**目标与边界**

覆盖成交后合同从草拟到验收/终止，并将履约结果反馈到供应商绩效与保证金退还。

**建议泳道**

1. 采购经办人
2. 合同管理服务
3. 审计/法务/审批人
4. 成交供应商
5. 履约与验收责任人
6. 供应商绩效/通知

**主流程**

1. 从项目、采购文件、响应文件和通知书生成合同草稿与关键条款。
2. 执行合同一致性检查，识别金额、标的、期限等实质性差异。
3. 经办人修订并提交内部审查。
4. 审批人通过或退回；通过后上传/生成签署版合同。
5. 双方签署，合同状态进入履行中，并可发布合同公告。
6. 按履约节点登记进度、证明材料和问题。
7. 供应商上传履约证明，采购方验收通过或要求整改。
8. 验收完成后生成质量、效率、合规等项目/供应商评价。
9. 满足条件后登记投标/履约保证金退还，合同进入已验收状态。

**必须画出的判断与异常**

- 一致性检查不通过时禁止签署。
- 内审退回、签约超时、供应商拒签。
- 履约延期、证明不足、验收不通过和整改重验。
- 合同变更或终止，需记录原因并影响项目/供应商评价。
- 保证金不退或延期退还必须留说明和监督日志。

**关键数据产物**

`Contract`、合同草稿/签署件、`ContractFulfillment`、验收记录、合同公告、`SupplierEvaluation`、`ProjectEvaluation`、保证金退还记录。

**当前实现映射**

项目合同阶段、采购管理端合同弹窗，供应商端 `/contracts`；API `contract`、`performance`、`bid/bond-return`、`announcement/CONTRACT_NOTICE`。

### `G03` 材料归集、四性检测、ASIP 导出、监管推送与长期保管泳道图

**目标与边界**

覆盖项目终结后的电子文件归集、缺件整改、元数据补录、四性检测、ASIP 包生成、纸电关联、移交确认、监管推送和长期审计。

**建议泳道**

1. 采购经办人
2. 各业务系统/开评标回流
3. 归档服务
4. 档案管理人
5. MinIO/哈希与操作日志
6. 外部监管平台
7. 调度器/通知中心

**主流程**

1. 项目各阶段附件、公告、投标密文/明文、开标记录、评分、签字包、合同和审计留痕汇入归档范围。
2. 归档服务按项目阶段和范围表勾稽材料，生成卷快照与档案元数据。
3. 经办人补传缺件、补录责任者/形成时间等元数据，或凭制度理由申请豁免。
4. 系统执行完整性、可用性、安全性、真实性检测并重算哈希。
5. 检测不通过返回整改；通过后选择保管期限并生成 ASIP 离线包。
6. 下载/打印移交登记表，线下签章后扫描回传，完成纸电关联。
7. 采购经办人发起档案移交，档案管理人二次确认接收。
8. 按监管平台规范生成签名载荷并推送，保存回执和凭证。
9. 已归档材料进入长期保管和删除保护；后续可验证归档包、查看审计、取消标记后重归档。
10. 调度器对终结后未及时归档项目分级提醒和升级通知。

**必须画出的判断与异常**

- 范围项是否适用于本采购方式/阶段。
- 必备材料缺失、对象存储不可达、哈希不一致、格式不可读。
- 人工豁免必须有理由并写日志。
- 归档包生成失败不得留下“已归档”假状态。
- 监管推送失败可重试，必须保留每次日志和最终凭证。
- 已导出 ASIP 或处于保管期的项目禁止物理删除。

**关键数据产物**

`ArchiveScopeItem`、`ArchiveMetadata`、`ArchiveCheckResult`、`BidArchiveItem`、ASIP ZIP、移交登记表、`ArchiveTransfer`、监管推送日志/凭证、`OperationLogArchive`。

**当前实现映射**

`:3005 /archive`、项目归档区、`:3007 /bid/archive`；API `archive`、`bid/archive-all`、`bid/archive-transfer`、`supervision-push`、`operation-log`、`scheduler`。

## 14. H 板块：集中目录、商城与框架协议

### `H01` 集中目录治理、供应商供货、预算清单与采购立项泳道图

**目标与边界**

覆盖目录分类、目录项和价格治理，供应商申请供货，商城采购人比价形成预算清单，并将清单转换为采购立项的闭环。

**建议泳道**

1. 目录管理员
2. 集中目录管理服务
3. 供应商/供应商门户
4. 商城采购员
5. 商城/预算服务
6. AI 价格分析与预警
7. 采购管理工作台

**主流程**

1. 管理员维护分类树、集中/分散采购级别、属性模板和目录版本。
2. 新增/导入目录项，补充规格、价格来源、有效期、附件和关联替代品。
3. 目录项审核上架；版本发布后向商城和供应商端开放。
4. 供应商浏览目录并提交供货申请、报价和证明材料。
5. 管理员审核、议价/还价；供应商接受反报价或撤回申请。
6. 通过后形成目录供应关系和合同价格。
7. 商城采购员按分类、供应商、价格、区域和状态检索、对比并收藏。
8. AI/规则分析价格趋势、异常波动、供应商集中度和预算风险。
9. 采购员将目录项加入预算清单，保存、克隆或导出。
10. 确认清单后转换为采购立项，跳转采购管理端继续 `B01`。

**必须画出的判断与异常**

- 目录版本草稿、发布、过期/停用。
- 分类是否达到集中采购金额阈值。
- 供货申请待审、反报价、接受、拒绝、撤回。
- 价格过期、异常波动、供应商单一来源预警。
- 预算清单转换后禁止继续修改，需克隆新清单。

**关键数据产物**

`CatalogCategory`、属性模板、`CatalogItem`、目录版本、供货申请、目录供应商、合同价格、询价、价格历史/预警、`BudgetList`、`BudgetItem`、`ProcurementProject`。

**当前实现映射**

`:3005 /mall-management/*`，`:3003` 商城，供应商端 `/catalog`、`/catalog-applications`、`/supply`；API `catalog`、`budget`、`supplier-portal/catalog-*`、`procurement`。

### `H02` 框架协议一阶段入围与二阶段订单泳道图

**目标与边界**

覆盖框架协议采购的一阶段入围、协议生效和二阶段直接选定/再次竞争形成订单合同的流程。

**建议泳道**

1. 采购经办人
2. 框架协议管理服务
3. 候选/入围供应商
4. 集中目录
5. 二阶段采购/竞争流程
6. 合同与履约服务
7. 审计与通知

**主流程**

1. 经办人从项目/目录品类创建框架协议，设置开放/封闭入围、定商/定价/定量、有效期和二阶段规则。
2. 通过既有招采或线下结果登记入围供应商、价格和份额。
3. 系统检查淘汰比例和必要规则；满足条件后协议生效。
4. 协议有效期内，开放式可增补供应商，封闭式原则上不新增。
5. 二阶段需求到达时，按规则直接选定或发起二次竞争。
6. 选定供应商后生成订单型合同并回链框架协议。
7. 合同进入履约、验收和评价。
8. 协议期内可登记供应商退出、价格调整、份额变化；到期或终止后停止下单。

**必须画出的判断与异常**

- 开放式/封闭式、定商/定商定价/定商定价定量的规则差异。
- 协议是否有效、供应商是否仍在有效入围集合。
- 二阶段直接选定条件是否满足；否则进入二次竞争。
- 份额/数量超限、价格规则失效、供应商退出。

**关键数据产物**

`FrameworkAgreement`、`FaEntry`、价格/份额规则、变更记录、二阶段项目或订单型 `Contract`、履约记录。

**当前实现映射**

采购管理端框架协议弹窗，供应商端 `/frameworks`；API `framework-agreements`、`contract`，并与 `catalog`、`project-management`、`bid` 关联。

## 15. I 板块：智能化与决策

### `I01` 水叮当助手、业务分析、预警与驾驶舱泳道图

**目标与边界**

覆盖用户通过自然语言查询采购数据/知识、获取分析和可视化、确认执行受控动作，以及业务数据如何沉淀到驾驶舱、大屏和预警中心。

**建议泳道**

1. 普通用户/领导
2. 水叮当助手或采购工作台
3. Assistant/AI 编排服务
4. 知识库/OCR/LLM
5. 核心业务服务与数据库
6. 动作确认与审计
7. Dashboard/Bigscreen/Alerts

**主流程**

1. 用户提问、选择快捷问题或从具体业务页面唤起助手。
2. 助手识别用户身份、企业范围、当前页面和意图。
3. 查询知识库、采购台账、项目、供应商、专家、目录、进度或开评标数据。
4. LLM 生成解释、对比、风险提示或图表数据，并标注依据和数据时间。
5. 纯查询直接返回；涉及修改/发送/创建的动作先生成待确认动作。
6. 用户确认后调用业务 API，取消则不执行；结果和失败原因回写会话。
7. 所有 AI 请求保留模型/时间/采用情况或动作审计。
8. Dashboard/Bigscreen 聚合项目进度、预算、供应商、专家、商城和风险指标。
9. 规则/AI 发现逾期、资质、价格、评标时限等风险后生成预警和待办，用户处理后闭环。

**必须画出的判断与异常**

- 用户是否有权查看目标企业/项目数据。
- 知识问答、数据查询、分析建议、执行动作四类意图分流。
- AI 无数据、数据过期、模型超时、结果低置信度时诚实降级。
- 任何写操作必须二次确认，不能由 LLM 直接落库。
- 大屏聚合数据不得泄露投标密文、未公开评分或跨企业数据。
- 预警是否自动消解、需人工确认或升级给上级。

**关键数据产物**

`AssistantConversation`、`AssistantMessage`、`AssistantActionLog`、知识库/文档块、AI 分析快照、风险预警、Dashboard 聚合指标、用户徽章和处理记录。

**当前实现映射**

`:3008` 助手、`:3005 /assistant` 与页面内助手、`:3010` 大屏、`:3005 /dashboard`、`/progress`；API `assistant`、`ai`、`knowledge`、`dashboard`、`progress`、`alerts`、`badge`。

6. 所有菱形判断的“是/否”去向。
7. 失败、退回、超时、撤回、争议和重试分支。
8. 关键成果物、状态和审计记录。
9. 对应门户、页面、API 模块和核心数据模型。
10. 与其他图的连接点。

建议文件命名：

- 可编辑源文件：`G00-platform-lifecycle.drawio`
- 评审版：`G00-platform-lifecycle.svg`
- 汇报版：`G00-platform-lifecycle.pdf`

其余按同一图号规则命名。推荐优先使用 diagrams.net/draw.io 保存可编辑源，同时导出 SVG 用于文档和 PPT，必要时再导出 PDF。

## 19. 绘图验收清单

### 19.1 业务完整性

- 每张图有明确起点、终点和业务成果。
- 角色动作与系统自动动作不混写。
- 所有审核/判断节点都有完整的通过与不通过去向。
- 撤回、退回、超时、失败、重试、争议、废标/流标等重要异常没有被省略。
- 跨门户动作明确标注发送方、接收方和承载通道。
- 项目阶段、投标阶段、供应商状态、合同状态和归档状态不互相混用。

### 19.2 系统一致性

- 图中的角色名称与当前角色体系一致：`admin`、`leader`、`staff`、`bid_host`、`bid_expert`、`supplier`、`mall`。
- 图中的项目阶段与当前九阶段项目管理口径一致；按采购方式删减不适用阶段。
- 开评标主状态与 `DOWNLOAD → SUBMIT → OPENING → EVALUATING → ARCHIVED/ABORTED` 一致。
- 供应商、公告、合同、框架协议和归档状态使用当前模型语义。
- 只读监督、AI 辅助、人工裁决、外部 CA/监管依赖均明确标识，不能画成系统自动决定。
- 当前实装和未来规划不使用同一种实线节点，避免汇报时误认为全部已上线。

### 19.3 图面可读性

- 单图不超过 7 条泳道和 24 个主节点。
- 连线尽量单向，避免大面积回折和交叉。
- 分支返回点有编号，不用长线穿越全图。
- 图例、颜色和节点动词在 18 张图中保持统一。
- 业务人员不看代码也能理解，研发人员能据图定位到门户和服务模块。

## 20. 需要业务方最终确认的口径

下列事项不阻碍开始绘制，但在形成最终版前应由业务/制度负责人确认，并在图上使用 `[待确认]` 标记：

1. `leader`、`staff`、`bid_host` 在采购管理端与开评标端的最终门户边界。
2. 监督人员是否使用独立角色/账号，还是由现有内部角色只读进入监督视图。
3. 不同采购方式的法定最少供应商数、流标条件和再次采购审批规则。
4. 公示期异议是否强制阻断成交确认，以及投诉转线下后的系统闭环口径。
5. 评标动议法定人数、弃权票计算、同分排名和组长裁决规则。
6. 合同变更、验收不通过、保证金不退的审批层级。
7. Mock U 盾在演示材料中的标注方式，以及生产 CA/签章接入边界。
8. 监管平台和档案系统最终是离线包/人工登记，还是在线接口对接。

## 21. 规划完成标准

当 18 张图全部按本规划绘制并通过验收后，系统应形成三层可阅读体系：

1. `G00`：领导和新成员能在 3 分钟内理解平台全貌。
2. `A01`～`I01`：产品、业务和测试能按功能板块走查主链和异常链。
3. 图后说明页：研发能从节点定位到当前门户、API 和核心数据模型，并识别业务规则待确认项。

本规划不要求下一阶段一次性画完全部图。建议先完成第一批核心链路，在评审中锁定统一图例和业务口径，再批量绘制第二、第三批，减少后续返工。
