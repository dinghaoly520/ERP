# 设计：项目管理慢接口「处理中 + 自动重取」（不让 OCR / 大模型拖垮请求）

> **状态**：已批准（2026-11-25，范围：14 条结果型路由全部接入）。下一步写实施计划。
> **来源**：2026-11-24 生产日志排查。项目管理步骤上传扫描件附件，后端在上传请求内同步 OCR，被门户代理 15 秒档掐断；操作人看到「后端响应超时…超过 15 秒代理时限」「N 个文件上传失败」，而后端其实成功。
> **用户裁定（2026-11-24）**：① 上传不等 OCR；② 同族接口这批一起修；③ 结果型接口走「先回『处理中』，前端自动重取」，不采用「放宽代理超时」。
> **评审后的裁定**：见第 8 节，随本文件一并批准。
> 下文省略 `apps/api/src/` 前缀的路径均在该目录下；前端路径省略 `apps/web/src/`。

## 0. 范围：14 条结果型路由全部接入

起草期间，另一会话于 11-24 18:00 提交了 `05dcdc8a3`（已推送）：把 14 条结果型路由里的 13 条放进了 `apps/web/src/proxy.ts` 的长档（10 条 120 秒、`extract-tender-fields` 与 `analyze-direct-procurement` 330 秒）。仍走 15 秒档的只剩「标记完成」（`PATCH :id/stages/:stageKey`）和附件上传。

**用户裁定（2026-11-25）：全部接入。** 机制做成通用的之后，多接入一条路由只是加一个装饰器。接入后这些请求不再依赖代理档位，超长扫描件也不会在 120 秒或 330 秒处假失败。现有长档保留作为兜底。

## 1. 要达成什么

项目管理（`/api/project-management/*`）下所有会同步跑 OCR 或大模型的接口，HTTP 请求不再被慢计算拖到超时。

- **快的照旧**：计算在等待上限内完成，响应与今天完全一样。
- **慢的不假失败**：超过等待上限，请求立即返回，计算转后台继续，前端自动重取结果。
- **上传不等**：附件落盘即返回上传成功；正文提取慢时转后台，结果出来后界面自动更新。

**为什么是现在**：生产 OCR 实测 36 页扫描件 157 秒；OCR 服务被大批次占用时单页也要 20–44 秒。附件上传和「标记完成」至今仍只给 15 秒档；其余 13 条靠 `05dcdc8a3` 的长档撑着，超过档位照样假失败。

**怎样算失败（反目标）**

- 任何项目管理慢接口再因为慢计算向用户报超时。
- 快路径的响应结构或行为变化，导致现有 e2e、单测或前端调用方需要跟着改。
- 人工确认或录入的值（尤其是开标时间）被晚到的机器结果覆盖。
- 操作日志里慢操作只剩 202，看不到最终成败（法定留存要求）。
- 后台任务的异常浮出，导致 API 进程崩溃或刷屏。
- 为了这个改动去动 BullMQ 或数据库结构，或再新增代理长档。

## 3. 三条做法与取舍

1. **放宽代理超时**：改一行就能让慢请求多等一会儿，但界面要一直等到算完；超过档位仍是假失败；生产反代自身的超时上限没有档案记录。**用户已否决把它当作修法**。`05dcdc8a3` 事后给 13 条路由加的长档，在本设计里只作兜底保留。
2. **处理中 + 自动重取（选定）**：首次请求限时等待，等不到就转后台并立即返回，前端凭单号自动重取。任何时长都不假失败。代价是要引入一个进程内的任务登记表，并改前端封装层。
3. **BullMQ 后台任务 + 轮询或推送**：跨进程、可恢复，最稳。但 15 条路由的契约和界面都要重做，是一个独立项目；当前生产只有一个 API 容器，进程内登记表已够。**本次不做**。

## 4. 设计

### 4.1 统一机制：限时等待 → 转后台 → 凭单号重取

新增 `PmiPendingJobService`（进程内，`ProjectManagementModule` 内提供），只有一个入口：

```
run(ownerId, label, compute) →
  等待上限内完成：照常返回结果或抛出原错误（与今天一致）
  超过等待上限：返回 { pending: true, jobId }，compute 继续在后台跑
```

- **等待上限**：任务最多等到「请求到达 API 后第 13 秒」，且不超过 `PM_PENDING_WAIT_MS`（默认 8000）、不少于 2000。不取固定值是因为附件上传的 15 秒里还包含请求体转发和落盘（上限 500 MB），固定等 8 秒在大文件上会撞上代理档。请求头到达时刻由一个全局中间件打点（早于请求体解析）。
- **任务记录**：`id`（`randomUUID`，不可猜）、`ownerId`（发起人 `user.sub`）、`label`、`status`（`running` / `done` / `failed`）、`createdAt`、`settledAt`、`result` 或 `error`。
- **异常不浮出**：`compute` 的 Promise 由登记表接管，成功和失败都落进记录；`main.ts` 的 `unhandledRejection` 处理器不应被这些任务触发。
- **容量**：`PM_PENDING_MAX_RUNNING`，默认 16 个在途任务；超出时新请求直接 503 `PM_SYSTEM_BUSY`（文案「系统繁忙，请稍后重试」）。已结束的记录保留 `PM_PENDING_TTL_MS`（默认 10 分钟）后清理；在途任务不清理。上传的提取任务不计入这个上限：它们按项目串行、只持有文件元信息；计入的话一次批量上传就会占满名额，让其他人的操作报「系统繁忙」。（2026-11-25 代码评审后补。）
- **进程关闭**：在途任务随进程丢失。关闭时对每个在途任务打一条 WARN 应用日志（任务标签、已运行时长），便于事后核对。
- **错误保存**：任务失败时保存原始异常对象，不自行转成响应体；非 HTTP 异常的对外文案由全局异常过滤器负责，不外泄内部信息。
- **单进程假设**：登记表在内存里。生产只有一个 API 容器；`nest --watch` 重启或部署会丢失在途任务，由 4.6 的「处理被中断」文案兜住。日后多副本时要换 Redis，本次不做。

**重取端点** `GET /project-management/pending-jobs/:jobId`

- 继承控制器类级的 `@Roles('leader','admin','staff')`；只有 `ownerId` 等于当前登录人的请求能读，其他人一律 404 `PM_JOB_NOT_FOUND`（不区分「不存在」和「不是你的」）。
- **长轮询**：任务未结束时最多等 `PM_PENDING_POLL_WAIT_MS`（默认 10000）再返回，减少往返次数。
- 任务未结束返回 `200 { status: 'running' }`，结束返回 `200 { status: 'done', result }`。任务失败时直接抛出保存的原始异常，由全局异常过滤器按今天的格式返回：状态码和错误体与同步时一致。（2026-11-25 写实施计划时修订，取代原定另存错误体、返回 `200 { status: 'failed', error }` 的写法。）
- 该端点加入 `operation-log.filter.ts` 的 `DEFAULT_EXCLUDE_PATHS`（轮询不进操作日志）。全局限流是每人每分钟 120 次，长轮询下每个在途任务每分钟约 6 次，实施时核对是否需要对该端点免限流。

### 4.2 结果型路由：整个处理函数转后台（14 条）

用装饰器加拦截器实现，控制器构造函数和各处理方法的签名都不变：

```
@PmiPending('analyze')   // 等不到即 202 { pending: true, jobId }；等得到则与今天一致
@Post(':id/analyze')
analyzeProject(...) { return this.projectManagementService.analyzeProject(id, stageKey, refresh); }
```

- 选拦截器而不是在控制器里显式调用，是因为 `project-management.controller.spec.ts` 手工 `new` 控制器（三处）；往构造函数里加依赖会让这些用例在运行时拿到 `undefined`。
- 角色守卫、归属守卫照常在请求进入时执行（守卫先于拦截器）；`@CurrentUser()` 由拦截器从请求上下文取。
- 这 14 条路由的控制器方法都不使用 `@Res()` 或流式响应（已核对），处理函数可以在响应发出后继续跑。
- `extract-initiation`、`extract-demand` 的文件是 `memoryStorage`，缓冲区被闭包持有到任务结束，不受请求结束影响。
- `PATCH :id/stages/:stageKey` 整体转后台，包含商谈报告闸、写入步骤状态、`refreshProjectAnalysis`。它原来的响应 `updatedStage` 由重取端点原样返回。步骤状态在任务中途就已写入，这一点与今天「代理掐断后后端照常跑完」一致。
- 不做相同请求的去重合并：重复点击会起两个任务，与今天并发两次请求等价；OCR 层本身有内容哈希合并和分析缓存。

### 4.3 上传：落盘即返回，提取转后台

把 `addStageAttachment`（`:1655`）拆成两段，服务对外行为不变：

- **同步段**：规则校验、可变性校验、轮次定位、历史轮只读闸、同名覆盖删除、落盘并建附件记录（`:1662` 到 `:1712`）。
- **提取段**：五段按步骤的正文提取与字段写入（`:1714` 到 `:1973`）、`archiveFlow.onTerminalAttachmentUploaded`、组装 `extractedInfo`（`:1975` 到 `:2011`）。提取段作为任务运行，任务结果就是 `{ extractedInfo }`。

响应分两种：

- 等待上限内提取完成：与今天完全一样，`{ ...附件记录, extractedInfo }`。
- 没完成：`{ ...附件记录, extractedInfo: null, extractedPending: true, pendingJobId }`。
- 等待期内提取意外失败：`{ ...附件记录, extractedInfo: null, extractedFailed: true }`。附件记录已经建好，上传仍算成功，但要让前端知道提取没成。

三种情况的状态码都与今天一致（201）。（2026-11-25 代码评审后补。）

规则：

- **同项目串行**：同一项目的提取任务按发起先后排队，后一个等前一个结束（成功或失败）再开始。这样机器结果之间「后上传者的值生效」与今天一致。不同项目互不等待。
- **提取失败不算上传失败**：今天五段提取各自 `try/catch` 后只打警告，这个口径保留。任务正常结束，`extractedInfo` 取当时库里的值。
- **只留文件元信息**：排队中的提取任务只持有文件名、类型、大小，不持有上传缓冲区。请求结束后缓冲区即可回收，一次批量上传不会在内存里压住十几份文件。
- **文本缓存**：上传采购文件主文件时立即清掉项目的 `tender-text` 缓存；提取任务只在自己是该步骤最新的主文件时才回写缓存。否则换文件名再上传时，「AI 提取」会在新文件识别完成前读到旧文件的文本，并把据此算出的值写进库。（2026-11-25 代码评审后补。）
- 其余上传调用方只读附件记录字段，多出来的两个字段不影响它们。

### 4.4 晚到的写入不得覆盖任务启动后的改动

**问题**：今天上传请求一直阻塞到提取结束，用户在提取完成前做不了别的，「后写的生效」天然成立。转后台后请求几秒就返回，用户可以在识别完成前确认开标时间、点「AI 提取」或手改字段。上传提取对项目概况和开标时间是无条件覆盖，并联动改写投标项目的开标与截止时间（`:1830`–`:1847`）；其他写入方有直接采购「谈判文件」完成时的确认值（`:3698`–`:3706`）和「AI 提取」落库（`:1002`–`:1007`）。不处理的话，人工确认的开标时间会被静默改写。

**规则**（适用于所有转后台任务里的字段写入：上传提取、「标记完成」里的直接采购确认值、「AI 提取」落库）：

1. 任务**开始执行时**给要写的字段拍一份基线。排队中的任务在出队时才拍，不是入队时；否则前一个任务刚写的值会被误判成「被人改过」。
2. 写入时逐字段判断：字段当前值仍等于基线才写；自任务启动以来被改过的不写。
3. 后一步依赖前一步时，只有前一步真的写了才做。例如开标时间没写进去，就不调 `syncBidProjectOpeningFromPmi`。
4. 上传提取的任务记下自己的附件 id。每次写入前确认该附件仍在；已被删除（同名替换或手动删除）就放弃后续写入，包括 `tender-text` 缓存回写。否则旧文件会在被删之后把缓存写回去，让「AI 提取」「供应商核对」读到旧文件的内容。

效果：没有人同时改动时，行为与今天一致（重新上传采购文件仍会刷新概况和开标时间）；有人在识别期间录入了值，以人的为准。「标记完成」把步骤置为完成这类不属于提取字段的写入不受此限，照常生效。

**对操作的影响**：识别未完成时用户可以继续操作。直接采购「谈判文件」的完成确认弹窗在识别未完成时给一句提示（如「文件文字识别中，完成后可自动带入」），字段可以手填。

### 4.5 操作日志

- **上传**：附件记录在响应时已经写入且结局恒为成功，操作日志照今天在响应时记（状态码随响应，今天是 201）。之后的提取是这次上传的后续，不单独记。
- **14 条结果型路由**：第一次响应（202）不记；任务结束时记一次，状态码取最终结果（成功 200，失败取错误码），耗时取任务实际耗时，请求体等字段取原请求。
- **进程关闭丢任务**：这次操作在操作日志里没有记录。这与今天「请求进行中进程重启」的结果相同，接受。
- 实施建议：日志拦截器把「记录函数」挂在请求对象的一个约定槽位上，任务服务在结束时调用；两边只认这个槽位，互不依赖。`http-exception.filter.ts` 用 `__oplogRecorded` 防重复记录，新机制要与之兼容。

全量请求指标拦截器没有排除表，重取请求会被计入总量。长轮询下数量很小，接受。

### 4.6 前端：封装层统一处理，调用方基本不改

新增 `lib/api/pm-pending.ts`，在 `parseJsonResponse`、两个 `api.upload` 调用处（`extract-initiation`、`extract-demand`）以及 `tender-file-editor-modal.tsx` 的两处直接调用处接入：

- 收到 `202 { pending: true, jobId }` → 调重取端点，直到拿到 `done`（返回 `result`）。任务失败时重取请求返回错误状态码和标准错误体，按今天的通道抛出同格式的错误，保留 `code`，例如 `ARCHIVE_GATE_MISSING`。
- 长轮询每次最长 10 秒，两次之间停 1 秒。
- 总时长上限 20 分钟，超过抛「处理时间过长，后台仍在执行，请稍后刷新查看结果」（`PM_PENDING_TIMEOUT`）。
- 收到 `404 PM_JOB_NOT_FOUND`（服务刚重启，在途任务丢失）抛「处理被中断，请重试」（`PM_JOB_LOST`）。**不自动重发原请求**：`PATCH stages` 这类写操作可能在中断前已经生效，自动重发会误报。
- 调用方传入的 `AbortSignal` 原样生效：取消时停止重取并保持 `AbortError` 语义。
- `extractTenderFields`、`analyzeDirectProcurement` 自带 150 秒、180 秒的客户端超时（`proxy.ts:69` 的注释有记录）。转后台后任务可能更久，转后台期间要挂起这个超时，或把上限放宽到与 20 分钟一致。

上传单独处理：

- `uploadProjectStageAttachment` 拿到 `extractedPending` 时立即返回结果，上传行显示成功。跟踪做在封装层：不经过详情面板上传队列的调用方（招标文件编写、正式文件向导、流标重启等 8 处）上传后转后台的提取，同样被登记，任务结束后通知详情面板刷新。（2026-11-25 代码评审后补。）
- 详情面板对这类行显示「文字识别中…」，并调重取端点等任务结束：成功则按今天 `onEachDone` 的同一逻辑合入 `extractedInfo` 并刷新父组件；失败则提示「文字识别失败，可重新上传或使用 AI 提取」。
- 晚到的结果按 4.4 的规则只带回真正写进库的字段；任务结果里的 `extractedInfo` 就是写完之后库里的值，前端照此合入。

调用方无需改动，但要逐个核对调用点对「晚到的成功」是否安全。今天这些请求超过代理档会报错，改造后会晚一些成功返回；已有序号守卫的调用点（如详情面板的 `analysisSeqRef`）天然安全，其余由实施时核对。

界面文案遵守文案战役的口径：面向用户不说 OCR、代理、大模型，统一说「文字识别」「处理」。

## 7. 验收场景

1. 上传 36 页扫描件到「专家抽取」步骤：13 秒内返回成功，上传行显示成功并带「文字识别中…」；提取信息在识别完成后自动出现；全程不出现代理超时提示。
2. 上传数字版 PDF 或 docx：响应仍带 `extractedInfo`，界面与今天一致。
3. 上传接近上限的大文件（请求体转发和落盘本身耗时数秒）：响应仍在 15 秒内返回。
4. 「标记完成」触发商谈报告闸且识别结果未缓存：界面保持等待不报错；识别完成后正常放行，或返回「尚未上传《直接采购商谈报告》」原文。
5. 对大扫描件做 AI 分析：界面保持加载直到结果返回，不报超时。
6. 识别未完成时在完成确认弹窗里手填开标时间并确认：识别完成后该值不变，投标项目的开标与截止时间不被改写。
7. 同名替换：旧文件识别未完成时上传新文件，最终库里的值和 `tender-text` 缓存都来自新文件。
8. 后台任务抛错：前端收到与今天同格式的错误；API 不崩；日志一条。
9. 慢的「标记完成」在操作日志里记为最终状态码（200、400 或 409），不是 202；上传照旧记响应的状态码（201）。
10. API 重启时在途任务丢失：前端提示「处理被中断，请重试」；应用日志里有进程关闭时的 WARN。
11. 在途任务超过上限：新请求返回 503「系统繁忙，请稍后重试」。
12. 现有 e2e 与单测不改即绿；唯一例外是上传拆段直接涉及的用例（被测处理函数都很快，走同步路径）。
