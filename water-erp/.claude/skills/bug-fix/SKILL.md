# 票修流水线

把禅道 bug 导出材料变成**逐票、受控、可多机并行**的修复流水线。跑本流水线的会话称为**票修会话**，可分布在本机与其他开发机（同一 git origin 同步）。

**三条铁律（贯穿全程，先记牢）：**

1. **两道强制闸门，不过不动**：修复方案未经用户明确确认，不得写工作区一行；验收未经用户明确确认，不得进入下一票。
2. **git 网络操作必问**：本地 commit 自由做；**push / pull 一律先问用户**（fetch 只读远端、可自由——用来在问之前看清领先/落后多少）。每次问要带建议：领票标记建议推（防别机撞票）、验收 commit 建议推（让别机看到进度）、换票前建议拉。**pull 前工作区必须干净，绝不带 autostash / 脏树 pull**（会卷走并行会话未提交改动）。
3. **环境与领域权威是仓库 CLAUDE.md**：本手册只管流程，不复制其内容。涉金额看「唱标金额单位铁律」、涉文案术语看「采购口径与命名裁定」、修复建议先过其裁定区防撞车、测试命令、账号口令、端口对照都在那。

## 资产

| 资产 | 位置 |
|---|---|
| 票修队列（唯一状态面） | `docs/bugs/<日期>-<负责人>/票修队列.md`（当前批次 `2026-11-11-yuanguoyu`；可多批并存，见 ① 取票） |
| 票面详情（v2 逐条核查+修复建议） | 同目录 `清单.md`；`清单.csv`；`images/`（压缩参考件） |
| 验收截图存放 | 同目录 `evidence/bug{ID}/`（按票建目录） |
| 原始材料（md5 原件、禅道库、OCR） | 仅本机 `~/桌面/禅道/bug-export/`——其他机器没有，别依赖 |
| 测试账号 / 端口 | 仓库 `ACCOUNTS.md` 与 CLAUDE.md 种子表 |

## 材料包入列（`/bug-fix <材料包路径>`）

用户带路径参数进入（bug 导出包经机器间直发：逐票清单 MD/CSV + images/），**先入列、再进循环**。材料已在 `docs/bugs/` 里的批次不需要此步——直接 pull 就有。

1. **验包**：路径下应有逐票清单（MD 或 CSV）与 `images/`；缺什么如实报告，别硬猜格式。
2. **落位**：拷贝到 `docs/bugs/<导出日期>-<负责人>/`。清单 MD+CSV 原样；images 里宽 >1600 的 PNG 压成 JPEG（q82、宽 1600）并**同步改写两份清单里的引用**——大体积原件不入库。
3. **建队列**：同目录新建 `票修队列.md`，沿用现行格式；组/级/标题/联动备注从清单的汇总分组抄录，无汇总则整列「待处理·待分组」（首轮 ② 复核时再定组）。
4. **入列 commit**：只 add 本批次目录（`chore(bugs): 入列 <日期>-<负责人> N 票`）→ 问用户是否推送。
5. 回到 ⓪ 开工自检 → 逐票循环。

## ⓪ 开工自检（每会话一次）

1. **同机避让**：`git status` 查并行会话有无未提交改动 → 有的话记下它碰的文件，全程不 add 不改；共享高危文件（`schema.prisma`/`app.module.ts`/`bid.controller.ts`/`bid-confirm-panel.tsx`/`packages/shared`）只在对方工作区干净时才碰。
2. **同步队列**：`git fetch` → 落后则问用户「拉取最新队列？」（建议拉）。
3. **环境就绪**（已在跑且健康可跳过）：仓库根 `pnpm install` → `apps/api` 下 `npx prisma migrate status`（pending 则 `migrate deploy` + `generate`）→ `pnpm dev:kill && pnpm dev` → 10 端口全监听 + `curl localhost:4001/api/docs` 200。详细排障按 CLAUDE.md。
4. **浏览器可用**：chrome-devtools-mcp `list_pages` 试探；被同机并行会话占用 → 互斥是 profile 级的，先协商等待，**勿擅杀活跃会话的进程树**；实在不行裸 CDP（:9333）兜底。

之后进入逐票循环 ①→⑦。

## 逐票七步

### ① 取票 + 展示

- 读票修队列，按行序取第一张「待处理」（跳过他人已领取行）。`docs/bugs/` 下多批次并存时：问用户修哪批，无偏好则按目录日期从旧到新。
- 从 `清单.md` 找该票详情，向用户**完整展示**：票面问题（报告人/日期/截图/OCR 实证括注）→ v2 代码核查结论（根因链/锚点）→ 修复建议 → **拟修改方式**（改哪些文件、怎么改、风险点、是否涉共享高危文件/裁定区）。
- 联动票一并展出（#61↔#126、#115↔#166、#121↔#147、#96↔#150、#142↔#43/#44）。

### ② 现场复核（只读，不动工作区）

v2 核查基准是 `ddf1cade0`，代码可能已前进，逐项重验：

- file:line 锚点逐个重定位（漂移不影响结论但要用现行号）；
- 根因链跨文件重走一遍；
- 修复建议过 CLAUDE.md 裁定区防撞车（实录：#73 建议撞 2026-11-03 裁定 #3）；
- 「无此机制」类断言全仓反证（`rg -n`，勿 `rg -rn`——`-r` 是替换标志）。

复核与资料不符 → **如实改口**，带着修正后的方案进 ③。

### ③ 强制确认闸门 · 方案

明确问用户：「确认按此方案修复 bug#NNN？」（方案有实质修订须重新过闸）。

- **确认 = 授权领票**：队列该行改「已领取@<机器名>」→ 本地 commit（`chore(queue): 领取 bug#NNN@<机器名>`）→ 问「推送领票标记？」（建议推；不推则撞票窗口=整票时长，须用户知情）。
- 不确认 → 按反馈改方案重过闸门；用户弃票 → 队列标「搁置(原因)」。

### ④ 修复

- **后端优先测试先行**：先写复现 bug 的失败测试（单测/既有 e2e 模式），再修，测试转绿。前端无测试基建的票以 ⑤ UI 验收代替，但提交前必须过 `tsc --noEmit`/lint。
- 只 add 自己明确改动的文件，**禁 `git add -A` / `git add .`**；commit 前核对分支（应在 main）。
- schema.prisma 改动必须随附迁移 + `npx prisma validate`，且仅当并行会话工作区干净。
- 小步提交不攒大跨度；完成即本地 commit `fix(bug#NNN): <一句话>`（不 push）。

### ⑤ 双验收

**代码审查**——派**全新上下文**的评审子代理（Agent 工具；只喂：本票 diff + 清单详情 + 修复方案，不给会话历史），要求找正确性/回归/边界/安全/约定违背。高置信问题必须处理；低置信/风格问题列表呈用户裁决。**禁止自审自过。**

**有头浏览器 UI 验收**——按票面复现步骤在本地 dev 环境实演：

1. 种子账号登录对应门户（账号/端口见 ACCOUNTS.md 与清单头）；
2. 重演 bug 场景验证已修复，顺带查邻近功能无回归；
3. 截图 2-3 张（问题定位处/修复后效果/关联页）存 `evidence/bug{ID}/`；
4. 涉及特定数据态的票（如开标中项目），用种子项目或按 CLAUDE.md/记忆中的 DB 配方构造，勿凭空 mock。

验收发现新问题 → 回 ④ 迭代（仍本地 commit），直到双验收都过。**不凭代码推断交验收。**

### ⑥ 强制确认闸门 · 验收

向用户呈**验收包**：审查结论与处理情况、验收截图、本地测试结果、本票 commit 列表。明确问：「验收通过？」

- **通过** → 队列行改「已验收待关单」+ 证据列填 `evidence/bug{ID}/` → commit（`chore(queue): bug#NNN 已验收待关单`）→ 问「推送本票 commits？」（附未推送数，建议推）。
- **不通过** → 按反馈回 ④。

### ⑦ 换票

问用户「拉取最新队列取下一票？」（建议拉；树须干净才 pull）→ 回 ①。用户喊停即停；会话中断后重进本 skill，从队列读状态续跑。

## 特殊泳道

| 票型 | 走法 |
|---|---|
| ✅ 半程票（#59/#69/#99/#142） | 只走 ①②⑤(仅UI验收)⑥：复核确认已修复成立 + UI 实演通过 → 直接标「已验收待关单」。不复现（如 #142 英文残留）→ 转正常票补齐再验收 |
| ⚠️ 裁定票（#98/#151/#60/#140a/#97、#69 可选项） | ③ 变**裁定门**：清单已备好路线 A/B 与代价，呈用户拍板。裁定=实施方案 → 转正常票入列；裁定=维持现状 → 队列标「已裁定·维持现状」待关单 |
| #96（未核查） | 联动 #150 同文档链路，修 #150 时顺带补核查再定去向 |
| 联动票组 | 按组推进、一起验收（#61+#126 两端、#121+#147 并票） |

**禅道关单由人在禅道操作**（库仅本机 docker），流水线最多标到「已验收待关单」。

## 队列与撞票

- 一票一行、一次一改，状态随当票 commit 走（详见队列文件头部维护规则）。
- push 冲突落在队列同行 = 撞票：fetch 对比，后到者弃票取下一张；已做的本地 commit 保留，呈用户裁决。

## 红线速查

- 两道闸门不过不动手；push/pull 必问；pull 绝不 autostash/脏树。
- 禁 `add -A`；commit 前后 `git status` 核对；同机并行会话的文件不碰。
- 修复建议先查 CLAUDE.md 裁定区；金额看单位铁律；术语看口径裁定。
- 评审子代理必须全新上下文；UI 验收必须有头浏览器实演 + 截图证据。
- 不造 mock 数据兜底；无把握的「无此机制」断言必须全仓反证。
