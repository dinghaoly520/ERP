## 与 ERP 项目的对应关系

本文档分析的 procurement 项目 `ai-bid-analysis` 模块，是本 ERP 项目（`/home/asus/桌面/ERP`）**专家门户辅助评标功能**的详细实现参考。

| | ERP 项目（简化版） | Procurement 项目（完整版） |
|---|---|---|
| **入口** | 专家端 Step 3 `http://localhost:3006/evaluate/<projectId>` | `apps/web` → AI投标分析 |
| **后端模块** | `apps/api/src/ai/ai.service.ts` | `apps/api/src/ai-bid-analysis/` (14个服务) |
| **评分方式** | 基于规则 + 统计分析 | DeepSeek LLM 驱动的多维评分 |
| **文件处理** | 无（使用 DB 中已有数据） | Python OCR + mammoth 文档解析 |
| **异步处理** | 同步 HTTP 请求 | BullMQ 队列 + 独立 Worker 进程 |
| **串通检测** | 无 | 6维度算法检测（价格/联系/文档/元数据） |
| **报告导出** | 无 | DOCX 生成 + MinIO 存储 |
| **核心分析维度** | 符合性检查 + 风险分析 + 评分建议 | 资格评审 + 技术评分(50) + 商务评分(30) + 报价分析(20) + 串通检测 + 横向对比 |

**对应关系**:
```
ERP 专家端 辅助评标 (Step 3)          Procurement 投标文件分析
─────────────────────────────        ───────────────────────────
符合性检查 (complianceCheck)    ←→   资格评审 + ★号响应检查
风险分析 (riskAnalysis)         ←→   风险等级 + 风险因素分析
评分建议 (scoreSuggestion)      ←→   技术/商务/价格三维 LLM 评分
—                                ←→   串通检测（纯算法）
—                                ←→   横向对比评分（第二轮）
—                                ←→   DOCX 报告导出
```

> **简言之**: ERP 项目的 `AiService.analyzeBid()` 是 MVP 阶段的规则引擎实现；procurement 项目的 `ai-bid-analysis` 模块是其完整的 AI+队列+OCR 生产级版本。两者核心分析逻辑（符合性→风险→评分→报告）一致。

### 状态机

**任务状态**（`AiBidTaskStatus`）:
```
CREATED → TENDER_UPLOADING → TENDER_PROCESSING → ANALYZING → COMPLETED
                                                      ↓
                                                  CANCELLED / FAILED
```

允许启动分析的状态（`ALLOWED_START_ANALYSIS_STATUSES`）:
`CREATED`, `TENDER_UPLOADING`, `TENDER_READY`, `BIDDERS_UPLOADING`

**投标单位状态**（`AiBidderStatus`）:
```
PENDING → OCR_PROCESSING → OCR_COMPLETED → EXTRACTING → EXTRACTED
  → SCORING → SCORED → DEVIATION_ANALYZING → COMPLETED
  任意步骤可转为 FAILED
```

进度百分比映射:
```
PENDING: 0%, OCR_PROCESSING: 20%, OCR_COMPLETED: 25%,
EXTRACTING: 40%, EXTRACTED: 45%, SCORING: 60%,
SCORED: 80%, DEVIATION_ANALYZING: 90%, COMPLETED: 100%
```

#### 关键实现细节

**一键导入（import bidder）**:
```
POST /tasks/:id/bidders/import
1. 上传文件到MinIO
2. 以文件名（去扩展名）作为初始名称创建立即返回
3. 后台异步调用LLM从文件名提取单位全称
4. AI失败则正则fallback（括号提取、分隔符最后一段）
5. 更新投标单位名称
```

**Multer Latin-1 修复**:
```typescript
// 修复multer对中文文件名的Latin-1编码
file.originalname = Buffer.from(file.originalname, 'latin1').toString('utf-8');
```

**启动分析的入队策略**:
```typescript
// 招标文件需要处理时，只入队招标处理任务；
// TenderProcessor完成后会自动级联入队投标单位。
if (needsTenderProcessing) {
  await tenderQueue.add('process', { taskId: id });
} else {
  // 招标文件已处理，直接入队投标单位

    await bidderQueue.add('process', { bidderId: bidder.id, taskId: id });

### 4.2 任务管理服务 — TaskService

**文件**: `services/task.service.ts` (536行)

核心方法:

| 方法 | 功能 |
|------|------|
| `create(dto, userId)` | 创建任务，状态CREATED |
| `findAll(userId, isAdmin)` | 管理员看全部，普通用户看自己的 |
| `findOne(id)` | 含bidders、report、tenderFiles |
| `delete(id)` | 级联删除所有MinIO文件+DB记录 |
| `startAnalysisWithLock(id)` | **乐观锁启动分析** |

#### 乐观锁实现

```typescript
async startAnalysisWithLock(taskId: string) {
  return this.prisma.$transaction(async (tx) => {
    // 1. 获取任务当前状态
    const task = await tx.aiBidAnalysisTask.findUnique({ where: { id: taskId } });

    // 2. 检查状态是否允许启动
    if (!ALLOWED_START_ANALYSIS_STATUSES.includes(task.status)) {
      return { success: false, message: '状态不允许' };
    }

    // 3. 验证投标单位（至少1个、都已上传文件）
    if (bidders.length === 0) return { success: false, message: '请先添加投标单位' };
    if (bidders.some(b => !b.fileId)) return { success: false, message: '请先上传所有投标文件' };

    // 4. 乐观锁：条件更新
    const result = await tx.aiBidAnalysisTask.updateMany({
      where: { id: taskId, status: task.status },  // ← 乐观锁条件
      data: { status: AiBidTaskStatus.ANALYZING },
    });

    // 5. 如果被其他请求抢先，返回错误
    if (result.count === 0) {
      return { success: false, message: '任务状态已变更，请刷新后重试' };
    }

    return { success: true, message: '分析启动成功', bidders };
  });
}
```

### 4.3 招标文件提取 — TenderExtractorService

**文件**: `services/tender-extractor.service.ts`

```
流程: OCR文本 → DeepSeek JSON提取 → TenderRequirements
```

- 使用 `TENDER_REQUIREMENTS_PROMPT` 提示词
- 提取：项目名称/类型/投标截止日/最高限价/估算成本
- 资质要求：分类（营业执照/资质证书/业绩/财务/信誉/人员）+ 门槛值 + 证明材料类型
- 技术要求：分类（技术方案/设备/人员/工期/质量/安全）+ ★号标注 + 权重 + 验收标准
- 商务要求：分类（售后/质保/付款/保险）
- 评分规则：技术/商务/价格满分 + 各维度权重 + 评分方法
- 使用确定性种子（`deterministicSeed`）保证幂等重放

**提示词核心规则**:
- 带★号条款标注 `isStarred: true`（实质性要求）
- 尽可能提取量化的门槛值和验收标准
- 不得自行估算招标控制价、预算价、成本或市场价
- 只能提取文件明确载明的数据

### 4.4 投标文件提取 — BidderExtractorService

**文件**: `services/bidder-extractor.service.ts`

```
流程: OCR文本 → DeepSeek JSON提取 → BidderKeyInfo + 完整提取信息
```

- 使用 `BIDDER_INFO_PROMPT` 提示词
- 提取超过20个维度的信息

**`keyInfo`（关键信息摘要）**:
- 单位名称、法定代表人、注册资本、成立日期
- 报价（万元+中文元）、报价有效期
- 资质等级/名称/状态（通过/不通过/待审查）
- 业绩数量+关键业绩（项目名/合同金额/完工日期/关键指标）
- 项目经理/职称、团队人数
- 工期、质保期
- 联系方式（电话/邮箱/地址 → 用于串通检测）
- 缺失项列表

**`extractedInfo`（完整提取）**:
- `license`: 营业执照/法人证书信息
- `qualifications[]`: 全部资质证书（名称/等级/编号/有效期/范围）
- `performance[]`: 全部业绩（项目/业主/合同日期/金额/工作内容/关键指标/验收结果）
- `team`: 项目经理+核心成员（姓名/角色/职称/资格/经验）
- `technicalProposal`: 技术方案概述/设备清单/质控/安全/环保/工期/关键技术点
- `commercial`: 报价/报价分项/质保承诺/售后服务/付款条件
- `attachments[]`: 附件清单
- `documentMetadata`: 总页数/格式版本/编制软件/创建日期/修改日期

### 4.5 三维度评分

三个评分服务 `Promise.all` 并行执行：

#### TechnicalScorerService — 技术评分（满分50）

| 维度 | 满分 | 要点 |
|------|------|------|
| 可行性方案 | 20 | 技术方案合理性、创新性 |
| 设备配置 | 10 | 设备数量、型号、新旧程度 |
| 人员配置 | 10 | 项目经理、核心成员、团队规模 |
| 质量保障 | 10 | 质量控制、安全措施、环保措施 |

- 额外检查★号实质性响应是否全部满足

#### CommercialScorerService — 商务评分（满分30）

| 维度 | 满分 | 要点 |
|------|------|------|
| 资质 | 10 | 资质完整性、有效性 |
| 业绩 | 10 | 相关业绩数量、质量 |
| 服务 | 10 | 服务承诺、质保期 |

#### PriceAnalyzerService — 报价分析（满分20）

- 报价价格、报价比例、基准价偏离度
- 报价分项分析（人工/材料/设备/管理/利润占比合理性）
- 市场对比（估算市场价、偏离度评估）
- 报价策略识别（低价/平衡/高价策略+置信度）
- 风险预警

### 4.6 竞争分析服务 — CompetitiveAnalysisService

- 综合分析各投标单位的竞争优劣势
- 输出：`strengths[]`（优势依据，含标题+详情+证据+影响力），`weaknesses[]`（需关注事项），`overallComment`（综合评价）
- **有确定性回退算法**：当LLM调用失败时，使用评分阈值生成 fallback
  - 技术分≥45 → "技术评分达到高分区间"
  - 商务分≥25 → "商务评分达到较高区间"

### 4.7 对比评分服务 — ComparativeScoringService

- 当所有投标单位处理完成后由 `BidderProcessor.tryComparativeScoring()` 自动触发
- 将所有投标单位摘要（报价/资质/业绩/团队/设备/方案/服务/质保/首轮评分）送入LLM
- LLM横向对比，给出第二轮评分
- 合并：保留首轮详细评分（breakdown），更新总分

### 4.8 串通检测服务 — FraudDetectorService

**文件**: `services/fraud-detector.service.ts` (560行) — **纯算法驱动，不调用LLM**

#### 6大检测维度

| 检测项 | 方法 | 阈值 | 规则码 | 严重度 |
|--------|------|------|--------|--------|
| **报价离散度** | 离散率 = stdDev/mean × 100 | <10% | `PRICE_CONCENTRATION_HIGH` | high |
| | | 10%–20% | `PRICE_CONCENTRATION_MEDIUM` | medium |
| **报价规律性** | 相邻差值/比值一致性 | 等差/等比模式 | `PRICE_PATTERN_ARITHMETIC/GEOMETRIC` | medium/high |
| **联系方式重叠** | 电话/邮箱/地址归一化精确匹配 | 精确相等 | `CONTACT_PHONE/EMAIL/ADDRESS_OVERLAP` | high |
| **文档相似度** | LCS综合相似度 | >90% | `DOCUMENT_SIMILARITY_HIGH` | high |
| | | 70%–90% | `DOCUMENT_SIMILARITY_MEDIUM` | medium |
| **报价结构相似** | 分项比例向量余弦相似度 | ≥98% | `PRICE_STRUCTURE_SIMILARITY` | medium |
| **暂估价一致** | 暂估价精确匹配 | 相等 | `PRICE_PROVISIONAL_SUM_MATCH` | low |
| **文档元数据一致** | 作者/创建软件/创建时间对比 | ≥2项相同 | `DOCUMENT_METADATA_CONSISTENCY` | low/medium |

#### 风险等级判定

```
任何高风险指标 → riskLevel = 'high'
≥2 个中风险指标 → riskLevel = 'medium'
其余 → riskLevel = 'low'
```

#### 投标单位数量对置信度的影响

- ≤3 家投标单位: 离散度检测置信度 × 0.6，规律检测降为medium/低置信度
- ≤5 家: 离散度检测置信度 × 0.8

### 4.9 文档元数据提取 — DocumentMetadataExtractorService

从PDF/DOCX文件中提取:
- 作者、创建者、生产者
- 创建时间、修改时间
- 页数、文件格式

这些元数据用于串通检测中的「文档元数据一致性」维度。

### 4.10 报告生成 — ReportGeneratorService

- `ranking`: 投标单位综合排名
- `keyInfoComparison`: 关键信息对比表
- `priceAnalysis`: 报价分析汇总
- `strengthsWeaknesses`: 各投标单位优劣势
- `riskStats`: 风险统计
- `highRiskDetails`: 高风险详情
- `reviewSuggestions`: 评审建议
- `fraudIndicators`: 串通检测结果
- `conclusion`: 结论
- `recommendation`: 推荐

### 4.11 DOCX生成 — DocxGeneratorService

### 4.12 缓存服务 — CacheService

### TenderProcessor 处理流程

**文件**: `queues/tender.processor.ts`

```
Step 1: 获取任务信息（含tenderFiles和bidders）
Step 2: 更新任务状态 → TENDER_PROCESSING
Step 3: 下载主招标文件（从MinIO）
Step 4: 文件→文本转换（DOCX: mammoth库; PDF: Python OCR服务）
Step 5: LLM提取招标要求（TenderExtractorService）
Step 6: 保存需求、OCR文本
Step 7: 更新任务状态 → ANALYZING
Step 8: 入队所有投标单位到 ai-bidder-processing 队列
```

失败处理: 更新任务状态为 FAILED，抛出异常让BullMQ重试（最多3次，指数退避5s）

### BidderProcessor 处理流程

**文件**: `queues/bidder.processor.ts` (423行) — concurrency: 2

```
Step 1:  获取投标单位信息（含关联任务）
Step 2:  状态 → OCR_PROCESSING
Step 3:  下载文件
Step 4:  并行: 文档元数据提取 + OCR文本提取
Step 5:  保存OCR文本，状态 → OCR_COMPLETED
Step 6:  获取招标文件要求（从任务中读取）
Step 7:  状态 → EXTRACTING
Step 8:  LLM提取投标单位信息（BidderExtractorService）
Step 9:  规范报价分项（normalizePriceBreakdown）
Step 10: 合并团队信息到keyInfo
Step 11: 状态 → EXTRACTED → SCORING
Step 12: 并行评分: 技术(TechnicalScorer) + 商务(CommercialScorer) + 价格(PriceAnalyzer)
Step 13: 计算总分 = technical + commercial + price
Step 14: 状态 → SCORED → DEVIATION_ANALYZING
Step 15: 偏差分析（analyzeDeviation，结构化算法）
Step 16: LLM竞争分析（CompetitiveAnalysisService），含fallback
Step 17: 提取风险等级、风险因素
Step 18: 保存全部结果到数据库
Step 19: 状态 → COMPLETED
Step 20: tryComparativeScoring() → 检查是否所有投标单位完成
         → 是: 触发对比评分 + 任务状态 → COMPLETED
```

`normalizePriceBreakdown`: 将LLM返回的各种格式（数字、"30万元"、"占比30%"）统一规范为数字。

async function processFile(ocrService, buffer, fileName?, maxPages = 200) {
  const ext = fileName?.toLowerCase().split('.').pop();

  // DOCX: mammoth 直接提取文本（无需OCR）
  if (ext === 'docx' || ext === 'doc') {
    const result = await mammoth.extractRawText({ buffer });
    return { text: result.value, pages: [{ page: 1, text: result.value }], pageCount: 1 };
  }

  // PDF/图片: Python OCR服务 (RapidOCR)
  const ocrResult = await ocrService.ocrPdf(buffer, maxPages, 300);
  return { text: ocrResult.text, pages: ocrResult.pages, pageCount: ocrResult.pageCount };
}
```

## 十、核心设计决策

### 1. Worker进程分离

评分等重计算在独立Worker进程中异步执行，避免阻塞HTTP请求。Next.js的rewrite代理超时是主要驱动因素。

### 2. 确定性种子

所有LLM调用使用 `deterministicSeed(taskId + context)`:
- 相同输入 → 相同输出
- 支持缓存和重放
- 支持幂等重试
- 节省API费用

### 3. 两轮评分机制

- **首轮（独立评分）**: 每个投标单位独立评分，关注自身响应质量
- **第二轮（对比评分）**: 所有单位横向对比，LLM综合考虑差异后重新打分
- 最终合并首轮详细breakdown + 第二轮对比总分
- 模拟真实评标流程

### 4. 串通检测纯算法化

6个检测维度全部使用统计算法（标准差、余弦相似度、LCS、正则匹配）:
- 不依赖LLM → 零API延迟，即时响应
- 结果稳定，可解释性强
- 置信度可量化
- 按投标单位数量自适应调整置信度

### 5. 乐观锁防止竞态

`startAnalysisWithLock()` 使用 Prisma 条件更新（`WHERE status = task.status`），避免重复启动。

### 6. 孤儿任务恢复

Worker启动时自动扫描 `TENDER_PROCESSING`/`ANALYZING` 状态的任务并重新入队，保证系统重启后的任务连续性。

### 7. 多文件招标文件模型

- 主文件（`isMain: true`）用于提取需求
- 补充文件（`isMain: false`）提供额外参考
- 可切换主文件、单独删除、重新解析

### 8. 渐近状态机

投标单位有9个细化状态（PENDING→OCR_PROCESSING→...→COMPLETED），前端可展示精确的实时进度百分比。

### 9. 文件类型自适应

```
DOCX → mammoth 直接提取文本（快速，无OCR开销）
PDF/图片 → Python OCR服务
```

### 10. 文件名AI提取

一键导入时，后台异步使用LLM从文件名中提取投标单位全称:
- LLM优先 → 正则回退 → 保留文件名
