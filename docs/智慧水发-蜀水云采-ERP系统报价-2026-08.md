## 2. 测算范围与方法

### 2.1 范围

- **纳入**：API 主应用（44 控制器 / 673 REST 端点 / 126 Prisma 模型）、8 个业务门户（:3002-:3008）、大屏（:3010）、ai-bid 分析 worker（同源代码，不重复计）、OCR 微服务（Python，1 个业务端点）
- **排除**：`water_erp_web/`、`apps/web-erp-old/`（废弃原型）；健康检查端点 2 个；WebSocket 事件通道（已有基本过程的交互通道）
- **应用边界**：整个系统为**一个应用边界**。9 门户是同一应用的交互通道（共享 API 与数据库），跨门户暴露的同一功能只计一次基本过程

### 2.2 计数方法（估算功能点计数法 QFP + 代码实测）

- **数据功能**：126 个 Prisma 模型逐个按 ILF/EIF 识别规则判定（剔代码表/纯关联表/技术表，强依赖主从实体按 RET 归并）→ **77 个 ILF，EIF=0**（系统自包含，外部依赖为 LLM/OCR 服务调用而非数据组引用——举证见附录 A）
- **事务功能**：673 API 端点 + 1 OCR 端点，按处理本质分类（维护数据/改变行为→EI；含计算/衍生输出→EO；简单提取→EQ），按 C.7 基本过程归并（同资源 list/detail 合并、同数据多门户视图合并、draft 并入提交等）→ **615 个基本过程（EI 333 / EO 104 / EQ 178）**，明细见附录 B
- 计数全程脚本化提取 + 人工逐端点判定，判定规则与人工覆盖表留痕于测算脚本

## 8. 验证记录（spec §10）

1. **抽样复核（bid + auth）**：两模块在分类表构建过程中逐端点人工复核，与脚本聚合数经三轮对账（通用组 EI 39↔手算 38、核心组 EI 267↔手算 262 等），差异全部来自可解释的归并粒度判断（如 expert 模块门户端 GET 明细保留独立基本过程），已在附录 B 逐行留痕
2. **链路复算**：§3.1 表每步公式可手算复现（例：核心业务组 UE = 6.54×2560 = 16742.4 人时；AE = 16742.4×1.10 = 18416.6；人月 = 18416.6÷174 = 105.84）
3. **sanity 对照（参考性）**：git 记录显示实际开发跨度 2026-06-10 → 2026-08-25（约 2.5 个日历月，2117 次 commit，AI 辅助高强度开发）。测算 133.68 人月为**标准度量下的市场公允工作量**，实际投入远低于公允值系 AI 辅助开发的效率增益，不影响按标准定价的成立性——这正是功能点法「按交付功能定价、与实际投入解耦」的特性
4. **端点提取完整性**：提取脚本三版迭代，最终 673 API 端点与全库 grep 计数完全一致，0 个未识别 handler
