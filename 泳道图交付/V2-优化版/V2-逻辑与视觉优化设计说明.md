# 泳道图 V2：业务逻辑清晰度与视觉系统优化设计

**日期：** 2026-09-01  
**状态：** 已完成方案确认，待用户复核书面规格  
**适用范围：** `G00` 总览图与 `A01`～`I01` 17 张专项泳道图  
**基线版本：** `codex/swimlane-diagrams` 分支，V1 共 18 张 SVG 与 18 张 4800×2700 PNG

## 1. 设计结论

V2 不采用精简版，也不删除 V1 已规划的业务节点、判断、异常、回退、产物或系统映射。整套图同时服务两种阅读方式：

1. 领导沿 `M01 → M02 → …` 编号主线，在 30 秒内讲清业务如何从开始走到结果。
2. 业务专家继续沿 `S` 支撑节点、`D` 判断、`E` 异常与回退、`O` 产物追读完整业务规则。

已确认的设计选择如下：

| 维度 | 采用方案 | 结论 |
|---|---|---|
| 信息结构 | 主线骨架 + 分层支路 | 主流程粗线连续编号，完整细节保留但降低视觉层级 |
| 母风格 | 精密工业蓝图 | 冰灰纸面、藏蓝主线、细线网格、白底节点、DIN 风格编号 |
| 模块差异化 | 中度变化 | 共同骨架不变，九个功能板块拥有专属强调色、纹理和构图重点 |
| 内容策略 | 完整型 | 不把异常、重试或专家规则移出主图，也不只保留汇报摘要 |

## 2. 使用场景与读者

### 2.1 首要场景

- 集团领导、采购管理层的系统能力与业务闭环汇报。
- 采购、开标、评标、供应商和档案等领域专家的专题评审。
- 产品、实施与研发团队对照门户、API 和数据产物进行方案确认。

### 2.2 读者任务

| 读者 | 首要问题 | V2 提供的阅读路径 |
|---|---|---|
| 领导 | 谁负责、经过哪些关键阶段、何处决策、最终形成什么结果 | 编号主线、阶段标尺、关键判断和结果带 |
| 业务专家 | 规则是否完整、异常如何恢复、责任是否清楚 | 支撑支路、判断出口、异常回退和完整产物 |
| 实施与研发 | 业务动作对应哪个门户、服务和数据对象 | 系统映射、产物索引、节点语义标识 |

## 3. V1 设计体检

### 3.1 反模式结论

V1 具有明显的通用自动制图痕迹：深色到青色渐变标题、饱和色圆角节点、统一投影、胶囊式页脚和几乎等权的多色块。信息齐全，但图面更像“把节点放进泳道”，还没有形成稳定的叙事主线。

### 3.2 设计健康度

| # | 启发式 | 分数 | 主要问题 |
|---|---|---:|---|
| 1 | 流程状态可见性 | 3/4 | 阶段清楚，但主线步骤没有连续编号 |
| 2 | 符合真实业务语言 | 3/4 | 角色和业务术语准确，部分技术异常过早抢占注意力 |
| 3 | 回退与恢复自由度 | 2/4 | 回退线存在，但恢复目标常需沿长线寻找 |
| 4 | 一致性与标准 | 3/4 | 颜色语义统一，但同阶段节点顺序和连线方式不稳定 |
| 5 | 错误预防表达 | 2/4 | 判断存在，但部分出口没有明确写出条件与结果 |
| 6 | 识别优于记忆 | 2/4 | 读者必须自行推断主流程和次要支路 |
| 7 | 兼顾不同读者效率 | 2/4 | 领导与专家共用同一视觉层级，无法快速切换阅读深度 |
| 8 | 美观与克制 | 2/4 | 饱和色块、投影、胶囊和连线同时竞争注意力 |
| 9 | 异常诊断与恢复 | 2/4 | 异常名称清楚，恢复动作和责任方仍不够稳定 |
| 10 | 图例与文档帮助 | 2/4 | 图例齐全但字号偏小，底部信息呈碎片化胶囊 |
| **总计** |  | **23/40** | **可用，但需要系统重构** |

V2 的目标为 **34/40 以上**。本次优化不针对交互功能，而是将上述启发式映射为静态流程图的可见性、业务顺序、恢复路径、视觉层级和帮助信息。

### 3.3 认知负荷

V1 的 8 项检查中有 5 项失败：单一焦点、分块、视觉层级、一次只处理一个判断、渐进揭示。主要原因不是节点数量，而是主流程、异常、系统动作和产物处于近似相同的视觉权重。

### 3.4 读者风险

- **领导：** 难以在首次观看时确认从哪个节点开始讲，遇到长纵向线时容易失去叙事位置。
- **业务专家：** 能看到规则，但需要反复追踪跨泳道连线，难以快速判断某个异常回到哪一步。
- **实施团队：** 底部系统映射和产物胶囊字号较小，难以把节点与门户、API 和归档对象对应起来。

## 4. 信息架构

### 4.1 五类图元

| 编码 | 名称 | 作用 | 视觉权重 |
|---|---|---|---|
| `M` | Main 主线 | 承担汇报叙事的关键业务节点 | 最高，连续编号与粗线 |
| `S` | Support 支撑 | 系统自动、通知、审计、校验和协同动作 | 中等，浅色节点与细线 |
| `D` | Decision 判断 | 改变业务去向的人工或系统判断 | 中高，琥珀描边菱形 |
| `E` | Exception 异常 | 阻断、退回、失败、超时和风险处置 | 次要但醒目，淡红底与虚线 |
| `O` | Output 产物 | 回执、报告、通知、签字包、合同、归档包等 | 页脚结果带，完整列出 |

### 4.2 主线定义

每张图在数据中增加显式 `mainPath`，按业务顺序列出 6～10 个主线节点。`mainPath` 必须满足：

1. 第一个节点能回答“由谁、因为什么触发”。
2. 最后一个节点能回答“形成什么结果、交给下一张图什么内容”。
3. 相邻主线节点之间存在一条明确主线边，不通过异常节点绕行。
4. 主线在图面上只从左向右推进，不使用反向主线箭头。
5. 主线跨泳道时优先采用一次垂直交接，不穿越第三个节点。

`mainPath` 可以包含承担关键分流的 `D` 判断，但不能包含 `E` 异常节点；其他 `M`、`S`、`D`、`E` 节点仍完整保留在同一张图中。

主线编号使用 `M01`～`M10`。图面可仅显示 `01`～`10`，数据和无障碍描述保留完整编码。

### 4.3 判断规则

每个 `D` 判断必须具备至少两个带语义标签的出口。禁止仅写“是 / 否”而不说明业务结果；优先使用“审核通过 / 退回修改”“完整性通过 / 人工裁决”“需要预审 / 有效期内免审”等结果型标签。

判断出口遵循以下顺序：

- 正常推进从菱形右侧或下游方向离开，并可继续进入主线。
- 退回从菱形下侧进入异常或修改节点，再通过专用回退通道返回。
- 终止、流标、废标和再次采购必须明确标出最终去向或跨图连接。

### 4.4 异常与回退

异常不删除，也不放入图外附录。V2 在泳道区设置三类专用走线通道：

1. 节点之间的主线通道，仅承载 `M` 边。
2. 泳道边界附近的支撑通道，承载 `S` 边。
3. 阶段下边缘或对应泳道下侧的异常回退通道，承载 `E` 和 `return` 边。

每个异常节点必须回答“发生什么、由谁处理、处理后回到哪里或转向哪个终止/跨图去向”。回退线使用低饱和红或紫灰虚线，不覆盖主线节点，不穿过节点正文。

### 4.5 完整性要求

- V1 的节点与业务事实全部保留；允许改写文案、重新分类和改变显示位置，不允许无说明删除。
- 系统自动校验、日志、通知、哈希、审计和外部回执等技术细节归入 `S`，仍保留在图中。
- 所有产物归入 `O` 结果带，并保留与形成节点的对应关系。
- 每张图仍保留跨图连接，明确上游输入和下游去向。

## 5. 画布与布局

### 5.1 固定规格

- 独立横版画布：4800×2700 px，16:9。
- 同名 SVG 与 PNG 各一份。
- 4～7 条泳道，4～6 个业务阶段。
- 中文字体回退：`Source Han Sans SC`、`PingFang SC`、`Microsoft YaHei`、sans-serif。
- 编号与技术元数据：`DIN Alternate`、`Arial Narrow`、sans-serif。

### 5.2 画布分区

| 区域 | 建议范围 | 内容 |
|---|---:|---|
| 标题与图号 | `y=0～250` | 板块、图号、标题、副标题、版本 |
| 阶段标尺 | `y=270～410` | 阶段编号、阶段名、动态阶段宽度 |
| 泳道与流程 | `y=430～2200` | 角色、主线、支撑、判断、异常与回退 |
| 产物与系统映射 | `y=2220～2580` | 完整产物、系统门户/API、图例 |
| 跨图连接 | `y=2600～2700` | 上游输入与下游连接点 |

### 5.3 动态阶段宽度

V1 按阶段平均分配列宽，导致同一阶段的连续动作堆在同一列。V2 根据该阶段的主线步数与支撑密度分配宽度：

```text
阶段权重 = 主线节点数 × 1.0 + 支撑节点数 × 0.35 + 判断数 × 0.55
阶段宽度 = 可用宽度 × 阶段权重 / 全图总权重
```

每个阶段内部再形成 1～3 个顺序位。主线节点根据 `mainPath` 顺序落位，支撑节点靠近其服务的主线节点，不再只按 `phase` 固定同一横坐标。

### 5.4 连线路由

- 主线：藏蓝 7～9 px，优先水平推进，90° 正交转折不超过两次。
- 支撑线：蓝灰 3～4 px，进入主线时使用短垂直接口。
- 判断出口：4～5 px，并在第一段旁显示结果标签。
- 异常与回退：3～4 px 虚线，沿异常通道返回明确节点。
- 任何连线不得穿越节点正文；标签不得与节点或其他标签重叠。
- 同一节点入线与出线使用独立锚点，避免多条线叠在同一点。

## 6. 精密工业蓝图视觉系统

### 6.1 视觉基调

V2 使用浅色精密工业风：冰灰纸面、细线网格、藏蓝文字与主线、低饱和模块强调色。整体参考瑞士工程制图、JIS 技术图纸和现代水利数字化产品，不使用通用管理后台式的大圆角、厚投影、发光渐变和多色实心卡片。

### 6.2 色彩语义

| 语义 | 建议色 | 用法 |
|---|---|---|
| 页面基底 | `#F5F8F8` | 带蓝灰倾向的纸面 |
| 标题与主线 | `#0B3B5E` / `#245A78` | 最高层级信息 |
| 系统支撑 | `#1D7680` + 淡青底 | 自动处理和接口服务 |
| 审核判断 | `#A86722` + 淡琥珀底 | 人工判断与监督 |
| 异常恢复 | `#B14949` + 淡红底 | 阻断、退回、失败 |
| 归档外部 | `#5F6E75` + 暖灰底 | 文档、存储、外部平台 |

颜色不是唯一语义载体；节点编码、形状、线型和文字标签同时表达含义。

### 6.3 形状与质感

- 主线节点：3～6 px 小圆角或直角白底矩形，藏蓝描边，不使用大面积实色。
- 支撑节点：淡青或模块淡色底，细描边。
- 判断节点：白或淡琥珀菱形，内部保留判断短句。
- 异常节点：淡红底、红色虚线描边，并显示 `E` 编号。
- 产物：折角文档或页脚结果带，不再使用大量胶囊。
- 阴影只用于整体纸张或极少数重点节点，方向性且低于 12% 不透明度；普通节点保持平面精确感。

### 6.4 排版层级

| 层级 | 字号建议 | 字重 | 用途 |
|---|---:|---:|---|
| 图名 | 58～66 px | 800 | 一眼识别主题 |
| 板块与图号 | 24～28 px | 700 | 导航与归类 |
| 阶段名 | 27～31 px | 700 | 横向进程 |
| 泳道名 | 27～31 px | 700 | 责任主体 |
| 主线节点 | 25～29 px | 650～700 | 汇报叙事 |
| 支撑 / 异常节点 | 21～25 px | 600～650 | 专家细节 |
| 线标签 / 元数据 | 18～22 px | 550～650 | 条件、系统与版本 |

文字以左对齐或节点内居中为主，标题区避免重复说明。正文最多三行，业务术语不在不自然位置断行。

## 7. 模块差异化系统

V2 采用“共同骨架 + 中度变化”。以下内容在 18 张图中保持一致：画布分区、字体、主线编号、节点编码、线型语义、泳道标签、图例和交付规格。

以下内容按板块变化：强调色、微型背景纹理、阶段标尺细节、一个构图重点和页脚产物表达。

| 板块 | 强调色 | 构图重点 | 识别性元素 |
|---|---|---|---|
| A 平台入口与治理 | 钢蓝 `#416681` | 权限闸门 | 门禁刻度、身份范围框 |
| B 采购协同与项目管理 | 钴蓝 `#235F8D` | 阶段时间轴 | 里程碑刻度、依赖接口 |
| C 采购文件与信息公开 | 墨蓝 + 琥珀 `#31536B / #9A6A2D` | 文档批注 | 版本角标、批注线、发布印记 |
| D 供应商全生命周期 | 松柏绿 `#36705C` | 生命周期状态 | 状态标尺、准入与退出门 |
| E 投标与开标执行 | 深青 `#0F7784` | 安全协议 | 双信封层、哈希刻度、解密窗口 |

## 9. 数据与渲染器设计

### 9.1 数据结构新增字段

```js
{
  mainPath: ['claim', 'ready', 'signin', 'integrity', 'announce', 'finishGate', 'packet'],
  nodes: [{
    id: 'claim',
    role: 'M',
    sequence: 1,
    supports: [],
    recoveryTarget: null,
  }],
  edges: [{
    from: 'claim',
    to: 'ready',
    role: 'main',
    outcome: '准备检查',
  }],
  moduleTheme: 'secure-protocol',
}
```

V1 的 `lane`、`phase`、`kind`、`status`、`artifacts`、`systems` 等字段继续保留。新增字段用于表达主次关系，不以渲染器猜测代替业务定义。

### 9.2 渲染器职责

1. 根据阶段权重计算动态阶段宽度。
2. 根据 `mainPath` 和阶段内顺序位布局主线。
3. 将 `S` 节点靠近其支撑的 `M` 或 `D` 节点布局。
4. 为主线、支撑、判断、异常、回退分配独立锚点和通道。
5. 应用公共母版与板块主题变量。
6. 输出 SVG、PNG、清单、联系表和 V1/V2 对比联系表。

## 10. 验证与验收

### 10.1 自动验证

- 18 个图 ID 完整且顺序不变。
- 每张图具备 `mainPath`，长度为 6～10，且相邻节点存在主线边。
- 每个判断至少有两个出口，所有出口都有结果型标签。
- 每个异常具备处理责任，并具备恢复目标或明确的终止/跨图去向；所有回退边能定位到存在的节点。
- 主线没有反向边，也不经过异常节点。
- 所有节点位于画布和对应泳道内；节点之间不重叠。
- 连线不穿越非端点节点；标签不超出画布。
- 每张 SVG 不含 `undefined`、`NaN` 或外部资源。
- 每张 PNG 为 4800×2700；18 个 SVG 与 18 个 PNG 全部存在。

### 10.2 视觉验收

- 在 25% 缩放下可辨认标题、阶段、泳道、主线编号和主线方向。
- 在 50% 缩放下可读取支撑、判断出口、异常恢复和结果带。
- 10 秒内可定位开始节点、结束节点、责任主体和跨图去向。
- 30 秒内可沿编号主线完整讲述流程，不需要追踪支撑线。
- 专家能够从任何异常节点找到责任方、处理动作和恢复目标。
- 九个板块能够通过强调色和构图重点区分，但核心图元语义保持一致。
- 不出现大面积饱和色卡片、装饰性渐变文字、厚重全向投影和胶囊堆叠。
